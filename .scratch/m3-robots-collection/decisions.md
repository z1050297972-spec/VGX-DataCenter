4. 采集方式、用途的初始词表 → **按草案**：

   - 用途：训练、评测、演示、试采。

## 决定

- **采集任务不再是单独的对象**。一个采集任务就是导航层里的一个数据集：同样的 14 项、同样的顶层字段（robot_model、fps、data_origin、scene、tasks、subtask_notes），全部可编辑；采集到的数据放在第 2 项"地址"指向的目录下，每天或每次采集是其中一个子目录（数据块）。
  - 数据集多出一组**采集信息**（`数据集信息.json` 顶层新键，名字由拆票时定）：用途、采集方式、所用机器人（平台编号，可多台）、状态（计划中 / 采集中 / 已完成）。没有采集信息的数据集（开源下载等）照旧。
  - 选了采集方式，数据来源按对应关系自动带出（仍可改）。
  - 场景、任务（子任务）用数据中心现有的候选，不另起词表。
- **转换产物用血缘连回去**：例如 R1_lite_table_withdrawing_lerobot 在 `来源.json` 里记"由 R1_lite_table_withdrawing_mcap 转换"，两边详情页都能看到。M3 只做人工登记这一条关系；转换作业自动写血缘留到 M4。
- **机器人登记在数据库**（ADR 0005：几秒内做完、只读写数据库的事 Web 当场做）。字段照「核心领域模型与术语」：平台编号（不改、不复用）、名称（不重复）、型号、序列号（可空）、每块网卡的 MAC、地址、SSH 端口（默认 22）、SSH 用户；使用中 / 停用；创建人、修改人和时间。平台不存密码。没被引用过可以删除，被数据集的采集信息引用过只能停用。
  - **型号**：沿用 M1.5 决定，不建型号表；机器人的型号就是和数据集 `robot_model` 同一套字符串，候选取已有值。
- **采集方式、用途两个词表在数据库**：可新增、改名、停用；被引用过的不能删。新建采集方式时必须选对应的数据来源。

## 要改的旧结论

- `GLOSSARY.md`："采集任务"改为"带采集信息的数据集"；"一个采集任务可以产出多个数据集"改为"转换产物通过血缘连回原始数据集"；受控词表只剩采集方式、用途（场景归数据集）。
- 「核心领域模型与术语」对象表里的"采集任务"行、"机器人型号"行（M1.5 已改）由 M3 的 ADR 修订节覆盖。
- ADR 0008：`来源.json` 的 `collection_task_id` 不再需要（采集任务就是数据集本身）。

## 拟拆的票（顺序即建议的开工顺序）

1. **机器人登记**：数据库表、接口、"机器人"页面（列表、新建、编辑、停用/恢复、删除未引用的）、操作日志。
2. **采集方式与用途词表**：数据库表、初始取值迁移、管理页面（新增、改名、停用；采集方式带数据来源）。
3. **数据集的采集信息**：`数据集信息.json` 顶层新键；编辑器里编辑（走写导航层的预览 → 确认流程）；采集方式带出数据来源；数据中心加"采集方式、用途、机器人、状态"筛选；机器人被引用计数。依赖 1、2。
4. **新建采集任务**：数据中心"新建采集任务"，用现有"新增数据集"的流程加采集信息；数据目录还没有数据时也能先建（状态"计划中"）。依赖 3。
5. **转换关系登记**：在数据集详情里登记"由哪个数据集转换"，写进 `来源.json` 血缘，两边显示。
6. **术语表、ADR 修订、手册**：随 1–5 各自写；最后一张统一核对。

每张票照 M1.5 的做法：Codex 实现、执行线评审、只做关键测试、副本演练（写导航层的票）、负责人点名合并。
