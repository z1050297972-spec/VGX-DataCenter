# 调研任务：现成的 Python 任务队列能否替代我们自己写的"作业表 + worker"

你是一名调研员，只做只读调研，最后交一份中文 Markdown 报告。

## 背景

我们在做一个单机部署的机器人数据管理平台（Ubuntu，几个人使用，一个人维护，代码全部由 AI 编写）。技术栈已定：

- Python 3.12；数据库是 SQLite（WAL 模式），用 **同步** SQLAlchemy 2 + Alembic，不用 async；
- 不加 Redis、RabbitMQ、PostgreSQL 之类要另外运维的服务；
- Web（FastAPI + uvicorn）和 worker 各是一个 systemd 用户服务；
- 类型检查用 basedpyright 严格模式，所以库有没有类型标注（`py.typed`）也有影响。

平台的长任务（下载要跑几天、调用外部命令行工具做格式转换、重新扫描、写文件系统里的"导航层"、定时备份）都做成"作业"，交给独立的 worker 进程执行。目前的计划是自己写"作业表 + worker"。项目规则要求"先用现成的"：标准库 → 已批准的依赖 → 成熟的第三方库 → 最后才自己写。此前只比较过需要 Redis 的 Celery、RQ。这次要补上：**有没有能用 SQLite、不需要额外服务的现成 Python 任务队列，能明显减少我们要写的代码。**

## 需求清单（逐条评估用，编号请照用）

- **R1 独立 worker 进程，只经作业表通信**：worker 是独立于 Web 的长驻进程，Web 重启不影响正在跑的作业。Web 和 worker 只通过 SQLite 里的作业表联系，不另开通道（不加消息代理、RPC、socket）。Web 提交作业就是插一行，取消作业就是在那一行上写一个取消请求。worker 每秒查一次有没有新作业和取消请求。
- **R2 六种作业状态**：排队中、运行中、正在取消、已完成、已取消、已中断。只有"已完成"带作业结果（成功、带警告成功、部分成功、失败四种，由计数算出）。"已取消"和"已中断"也要能显示做到了哪一阶段、多少条目。
- **R3 中断识别与按类型恢复**：worker 启动时，要能识别出上一个 worker 实例留下的"运行中"作业（包括被 `kill -9`、整机断电的情况），把它判为中断，并在作业日志里写明中断在哪一步、最后进度是多少。然后按每类作业声明的恢复方式三选一处理：
  - **续跑**：下载作业重新排队，由外部工具自带的断点续传接着下；
  - **重跑**：重新扫描作业从头再跑；
  - **标记中断**：转换作业和写导航层的作业变成"已中断"，等人重新提交。写导航层的作业还要先跑完平台自己的恢复流程，才放行别的写操作。

  排队中的作业，重启后照常排队。
- **R4 取消**：
  - 排队中的作业，取消后立刻变成"已取消"。
  - 运行中的作业先进入"正在取消"。worker 先请工具（外部子进程）停下（例如发 SIGTERM），约 10 秒后还没停就强制结束（SIGKILL）。
  - 作业正处在"写导航层"那一步时不打断，等这一步写完再停。
  - 取消不清理产物。
- **R5 按类型的并发上限**：每类作业有各自的并发上限，默认 1，可以在配置里改。不同类型的作业之间可以并行，例如一个下载和一个转换同时跑。某一类达到上限时，它的作业继续排队，不能占住别的类型的执行位。
- **R6 GPU 名额**：两张卡算两个名额，一张卡同一时间只给一个作业。worker 分配卡并告诉工具用哪张（例如设 `CUDA_VISIBLE_DEVICES`），作业结束后收回。没有空卡时，需要 GPU 的作业排队等待。
- **R7 进度**：worker 把进度写进数据库里的作业记录，包括阶段的序号、总数和名称，已完成数、总数和单位，警告数、失败数，更新时间。每秒最多写一次，并且一直保留最后一次进度：工具突然退出时，平台要靠它补诊断。Web 从数据库读进度。
- **R8 心跳**：worker 定时往数据库写心跳。心跳过期时，网页提示"worker 不在线，作业不会开始"。
- **R9 单实例文件锁**：worker 启动时先拿平台状态目录里的一把排他文件锁，拿不到就直接退出，保证不会有两个 worker 同时跑。运维命令也会拿这把锁。
- **R10 定时提交作业**：worker 到点自动提交定时作业（例如每天备份），提交人记为"系统"。定时作业和普通作业一样进作业表，走同样的状态和记录。
- **R11 作业记录永久保留**：参数、提交人（内部编号和名字）、状态、进度、计数、诊断样例、结尾摘要都存在数据库里，永久保留，供详情页查看和血缘引用作业编号。重新提交会新建一个作业，并注明"重新提交自 #N"。
- **R12 同库、同步写法**：作业表和平台的业务表（账号、数据集索引等）在同一个 SQLite（WAL）库里，表结构由同步 SQLAlchemy 2 + Alembic 管理。不用 async，不加服务。

下面这些由平台自己负责，**不计入评分**。但如果某个库会妨碍它们（例如库自己会在某一步杀掉任务），请指出：

- 导航层写锁：worker 进程内一把锁，作业只在写导航层那一步持有；
- 写前冲突核对；
- 存储根在线检查；
- 每个作业一个文本日志文件；
- systemd 托管和子进程清理。

## 要评估的库

必须逐个评估：

1. **huey**，重点是 `SqliteHuey`；
2. **APScheduler**，重点是 SQLAlchemy 作业存储。3.x 稳定版和 4.0 预发布版的数据存储模型差别很大，两个都要评估，并注明 4.0 是否仍是预发布；
3. **persist-queue**，重点是 SQLite 系列队列，例如 `SQLiteAckQueue`；
4. **litequeue**。

**其他候选**：如果搜到其他能用 SQLite、不需要额外服务的 Python 任务队列或持久化工作流库，也按同样格式评估。可以先从下面几条线索查起，是否符合条件请自己核实，也不限于这几个：

- DBOS Transact（`dbos`，源码里有 SQLite 系统库的实现）；
- django-q2 的 ORM broker（要依赖 Django）；
- Taskiq 有没有 SQLite broker。

明显不合适的候选（例如必须引入整个 Django，或者必须另起一个服务端），评估可以从简，但要说明原因。

**排除项**：需要 Redis、RabbitMQ 或 PostgreSQL 的（RQ、arq、Celery、dramatiq、procrastinate），每个只用一句话说明排除的理由，附来源网址。

## 每个库要交付的内容

1. **速览**：最近一次发布的版本号和发布日期（以 PyPI 为准）、维护状态（最近的提交或发布、是否有人在处理 issue）、许可证、按我们的用法会带进来的运行时依赖、是否带 `py.typed`。
2. **逐条需求对照表**：R1–R12 每条标注"原生支持 / 要自己补 / 做不到"，并写理由。判定口径：
   - **原生支持**：照文档用就能满足；
   - **要自己补**：在库之上写我们自己的代码可以满足，请说明大概要补什么；
   - **做不到**：库的设计与需求冲突，要绕开或改库才行。
3. **worker 崩溃时，正在执行的任务会怎样**：分清两种情况。
   - 优雅停止，例如 SIGINT、SIGTERM；
   - 硬崩溃，例如 `kill -9`、整机断电。

   结论是"丢失 / 自动重投 / 留下可识别的标记"中的哪一种。要指出决定这一点的代码位置，例如"出队时就删除了这一行"或"状态列标成 locked"。
4. **能不能取消正在运行的任务**：
   - 机制是协作式检查、发信号，还是不支持；
   - 能不能做到 R4 要求的"先请停、约 10 秒后强制结束、关键步骤不打断"。
5. **来源**：每条事实都附来源网址，只用官方文档、源码或 PyPI 页面，不用博客和问答站。
   - 源码引用尽量给对应发布 tag 的固定链接加行号，例如 `https://github.com/<owner>/<repo>/blob/<tag>/<path>#L10-L20`。
   - 确认不了 tag 名时，给 sdist 里的相对路径加行号，并注明是哪个版本。

## 结论部分

1. 有没有哪个库能**明显**减少我们要写的代码？
2. 如果用了它，我们还要自己补哪些部分？
3. 和自己写相比，新增的风险有哪些。至少考虑这几点：
   - 作业状态会不会出现两份事实来源，一份在库的表里，一份在我们的作业记录里；
   - 序列化方式，例如 pickle；
   - 库自己的表能不能纳入 Alembic 管理；
   - 并发写 SQLite 时的锁竞争；
   - 类型检查。
4. 如果结论是自己写，请列出自己写需要的最小部件清单，并指出其中哪些可以直接用标准库，例如 `fcntl.flock`、`subprocess`、`signal`。
