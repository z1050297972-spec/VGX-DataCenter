# 可观测性与报错规范

Type: grilling
Status: resolved
Blocked by: 03

## Question

把原始需求 (10)（像 mcap2lerobot 那样，出问题时给出足够的信息和完整的错误）和 `docs/standards/engineering-control/references/diagnostics.md` 落成平台的规范。作业日志存放在哪里由「[作业模型](10-job-model.md)」定，这张票只管日志的内容和格式。

要定的：

- **日志**：用不用结构化格式；分哪几级；平台自身的日志放在哪里。这张票管的是**运行日志**。操作日志和登录日志已在「[交互形态与前端路线](02-interaction-frontend.md)」定好（存数据库，保留 30 天），作业日志归「作业模型」。三者的定义见 `GLOSSARY.md`，不混用。
- **错误**：
  - 异常怎么分层
  - 上下文在拥有身份信息的那一层补充
  - 用 `raise … from e` 保留原因
  - 每个错误只报告一次
- **诊断消息**：五段式（对象、规则、实际值、期望值、下一步）的固定写法。
- **进度**：后端怎么上报进度，Web 上怎么显示。0003 写的是 rich 进度条，但平台只有 Web，这里需要替换掉。前端约 1 秒轮询一次（「交互形态与前端路线」）。
- **状态一致**：作业最终状态（成功、部分成功、失败）和警告数、失败数一致。

补充（来自「[技术栈与工程规范](03-tech-stack-standards.md)」）：日志用标准库 logging，还是另加一个库（例如 structlog），那张票没有定，归本票。如果要新增依赖，按 `AGENTS.md` 硬性规则 7 走。

**完成标准**：以上各项都有结论，并附一个代表性故障的示例输出。只凭这份输出，就能找到出问题的对象、违反的规则和下一步该查什么。结论写成 ADR 或 `CODING_STANDARDS.md` 诊断章节的要点。

### 结论

- **运行日志**：
  - 用标准库 logging，不加 structlog，不新增依赖。
  - 每条一行：`时间 级别 模块 中文消息 key=value…`。诊断类消息后面跟缩进的明细行。不用 JSON，因为日志主要在终端里用 grep、less 读。
  - 级别四级：
    - ERROR：某个操作、作业或条目失败了。
    - WARNING：结果打了折扣，但作业继续。
    - INFO：生命周期节点，例如启动、阶段切换、作业结束摘要。
    - DEBUG：细节，默认不输出。
  - 时间写本地时间并带时区，例如 `2026-10-21 16:15:02.123+08:00`。数据库照旧存 UTC，网页按本地时间显示。
  - 放在平台状态目录的 `logs/` 下。这个目录和数据库文件放在一起，具体路径由 M0 定，不放进导航层。
    - Web 和 worker 各写一个文件（`web.log`、`worker.log`），因为两个进程按天切分同一个文件会把它写坏。
    - 按天切分，保留 30 天。同时输出到 stderr。
  - uvicorn 的访问日志关掉。几个浏览器每秒各轮询一次，有用的内容会被淹没；写操作已经有操作日志。
- **作业日志的内容**（放在哪里由「[作业模型](10-job-model.md)」定）：
  - 开头：作业编号、类型、提交人、参数、最终生效的配置（配置文件附哈希）、工具及其版本和上报协议版本。
  - 中间：按时间写阶段切换、每条诊断，以及工具的原始 stdout、stderr。原始输出逐行标 `stdout <工具名>│` 或 `stderr <工具名>│`。
  - 结尾：摘要，写最终状态、各项计数、耗时、产物位置、工具退出码，与数据库里的作业记录一致。
  - 目标：只看这一份文件，就能排查和复现。
- **诊断**：
  - 五段：**对象、规则、实际与期望、后果、下一步**，取代票面上的"对象、规则、实际值、期望值、下一步"。
    - 实际值和期望值放在同一行对照。
    - 补上了"后果"：丢了什么、结果还能不能用。
  - 每条诊断还带级别、阶段和来源。来源是"平台"或某个工具名。
  - 代码里只有一种诊断对象。日志里的文本、接口返回的 JSON、网页上的五段卡片，都由它渲染。
  - 同类诊断很多时，只记总数和前几条样例，总数不会因为截断而丢失。
- **报错分类**：按"该由谁来处理"分四类，不按模块分。
  1. **输入或数据问题**：用户自己能改，例如路径不存在、字段缺失、数值超差。网页上显示五段诊断。
  2. **冲突**：锁被占用，或者状态不对，等一会儿或等别人做完即可。
  3. **外部失败**：NAS、机器人或外部工具出错。附上命令、退出码或信号、stderr 的最后几行。
  4. **程序缺陷**：其余所有意外异常。网页显示一句话加错误编号，点开能看完整的异常链和 traceback。
  - 工具报上来的诊断只有 1、3、4 三类。锁和状态由平台管，所以"冲突"只出现在平台一侧。
- **只报告一次**：
  - 由掌握对象身份的那一层补上下文，例如"文件 → 相机 → 编码器 → ffmpeg 退出码"。
  - 重新抛出时一律写 `raise … from e`。
  - 中间层不打印。只在三处边界记录和呈现：接口的统一异常处理、作业执行器的最外层、运维命令的入口。
- **完整报错给谁看**：
  - 所有登录的账号都能点开看完整报错。平台是内部工具，看到报错的人往往就是要去排查的人。
  - 口令、会话令牌、cookie、SSH 私钥一律不写进日志和报错，也不把整份载荷写进日志。
- **作业结果**：共四种，由一个函数根据计数算出，不由代码手动设置。
  - 成功：失败条目为 0，警告为 0。
  - 带警告成功：失败条目为 0，警告多于 0。
  - 部分成功：一部分条目失败，其余成功。
  - 失败：作业整体中止，或者全部条目失败。
  - 失败条目数、警告数、丢弃帧数等分开计数、分开命名，不合并成一个"错误数"。
  - "条目"指文件、episode 或数据集，由每类作业自己定义。
  - 取消和中断归「作业模型」的状态机。
- **进度**：
  - 后端上报：阶段（序号、总数、名称）、已完成数、总数（未知时为空）、单位。只在真正完成的事件之后计数，例如数"已写入"，不数"已提交"。
  - 网页显示：
    - 阶段，例如"阶段 2/4 · 编码视频"。
    - 知道总数时显示进度条，不知道时只显示已处理了多少。
    - 速度和剩余时间按最近约 10 秒计算。网页每秒轮询一次，窗口取 1 秒会抖。
    - 已用时间、实时的警告数和失败数，以及作业日志的最后几十行。
  - 写到哪里、Web 从哪里读，由「作业模型」定。
- **工具的上报**（ADR 0004）：
  - 平台启动工具时，另开一条上报通道（管道），用环境变量告诉工具。工具每行写一个 JSON 事件，协议带版本号。
  - 事件共五种：
    - **进度**：阶段（序号、总数、名称）、已完成数、总数、单位。
    - **诊断**：级别、类别（1、3、4 类之一）、阶段、对象（键值对）、规则、实际、期望、后果、下一步。
    - **条目结果**：条目、成功或失败，以及这个条目的统计，例如保留了多少帧。
    - **致命错误**：一句话，加完整的错误链或 traceback。
    - **结束摘要**：各项计数。
  - 平台把收到的事件当作自己的诊断来计数，用来计算作业结果，并在作业日志和网页上用同样的写法显示，另标来源。
  - 平台自己的计数和工具的结束摘要对不上，或者退出码和上报对不上时（例如退出码为 0 但没有结束摘要），按更坏的情况算，再记一条诊断说明哪里对不上。
  - 工具没上报就退出时（panic、被 OOM 杀掉），平台补一条"外部失败"诊断，内容是退出码或信号、stderr 的最后几行、最后一次进度。
  - 工具库里的工具都必须接入：
    - mcap2lerobot 加一个上报模式，在 M4 接入转换时做。
    - 改不了的第三方脚本，配一个包装脚本来接入。
    - 还没接入的工具可以试跑，但网页上标明"只有原始输出和退出码"。

### `CODING_STANDARDS.md` 第 6 条「错误与诊断」要点（M0 成文）

1. **一种诊断对象**：字段是级别、类别、阶段、来源、对象（键值对）、规则、实际、期望、后果、下一步。日志文本、接口 JSON、工具事件的解析结果都用它，不另起格式。
2. **四类异常**：新异常从四个基类之一派生，不按模块另建平行的异常体系。接口的 HTTP 状态码按类别映射：输入或数据问题 400/404/422，冲突 409，外部失败 502，程序缺陷 500。
3. **补上下文**：在掌握对象身份的那一层补，重新抛出时一律 `raise … from e`（bugbear 的 B904 机械检查）。不允许"先打日志再重新抛出"，只在三处边界报告。
4. **logger**：每个模块写 `logger = logging.getLogger(__name__)`，不用 print（ruff 的 T20 机械检查）。消息写中文。上下文写成 key=value。作业编号和请求编号由日志配置通过 contextvars 自动带上，不在函数之间手工传递。
5. **级别**：按上文四级的含义使用。WARNING 必须写清后果。
6. **聚合**：同一类诊断只保留前 N 条样例，N 用具名常量，并注明含义。总数始终完整。不同口径的计数（失败条目、警告、丢弃帧）分开命名。
7. **进度**：只在真正完成的事件之后更新。写入频率限制在每秒最多一次。总数未知时不要编一个总数。
8. **作业结果**：只能由那一个计算函数得出，不允许在别处直接赋值。
9. **外部进程**：完整捕获 stdout 和 stderr。失败时附上命令、退出码或信号、stderr 的最后几行。工具的上报事件是不受信任的输入，要逐行校验，不合格的行原样保留并记一条警告，不能让作业执行器崩溃。
10. **敏感信息**：口令、令牌、cookie、私钥不进日志和报错，也不把整份载荷写进日志。
11. **测试**：每新增一类诊断，至少写一个代表性故障的测试，断言对象身份、实际值、后果和最终的作业结果。不对整段文本做快照（engineering-control 的 diagnostics 一节）。

### 风险

- **工具上报的量**：帧级诊断可能非常多，平台一侧也要按"总数 + 样例"聚合，否则作业记录和网页会被撑爆。M4 用真实的长 mcap 验证一次。
- **平台状态目录还没定**：运行日志跟着数据库文件放，具体路径在 M0 定，还要和「[备份方案](17-backup.md)」对齐（运行日志要不要备份）。
- **工具接入之前**：M4 之前没有转换作业，所以影响小。M2 的下载用不用工具库里的工具，M2 开图时再定；如果用，同样要接入上报协议。

### 对其他票的影响（已同步到各票正文）

- 「[作业模型](10-job-model.md)」：
  - 进度要存的字段，以及每秒最多写一次的限制。
  - 作业结果有四种，状态机要容纳它们，并定好取消、中断和它们怎么并存。
  - worker 要保留最后一次进度，供工具突然退出时补诊断。
  - 运行日志按进程分文件，并且输出到 stderr。如果用 systemd 托管，要和 journald 配合好。
- 「[工具清单与转换血缘](15-tool-manifest-lineage.md)」：
  - 清单要声明支持的上报协议版本。
  - 定包装脚本放在哪里。
  - 工具必须能不经交互运行，命令模板据此写。
  - 清单草样要包含上报协议这一项。
- 「[备份方案](17-backup.md)」：运行日志要不要备份。
