## Question

平台怎么写导航层？以 0003 4.4 为起点；读取的那一面以「[数据集板块的数据契约](11-dataset-contract.md)」为准，并发和日志以「[作业模型](10-job-model.md)」为准。

要定的：

- **建链**：
  - 0003 4.4 推荐的五条校验规则定稿
  - 写回 `原始路径.json` 的 `links` 和 `sources` 时遵守什么规则
  - 两个视图是否同步建链
- **新增数据集**：是否一次就建好两个视图的目录、链接和三个 JSON 的骨架。
- **改指向**：智元数据迁到 NAS 时的批量换前缀，参考「[NAS 接入事实](04-nas-facts.md)」；两个视图联动修改；先预览、再确认。
- **体检**：只报告、不修复，具体覆盖哪些检查。
- **原子性**：链接和清单两者中有一个写失败时，怎么回滚。
- **操作记录**：「[交互形态与前端路线](02-interaction-frontend.md)」已定，建链、改指向都写进**操作日志**（数据库，保留 30 天）。这里要定的是：操作日志里要记下哪些字段，才能凭它撤回一次改动；超过 30 天的改动还要不要另留一份记录。
- 导航层备份已移到「[备份方案](17-backup.md)」。

补充（来自「[作业模型](10-job-model.md)」，ADR 0005）：
- **写操作都是作业**：建链、新增数据集、改指向，都由 worker 在导航层写锁下执行，Web 不直接写导航层。单条建链正常 1–2 秒出结果。
- **预览时的状态**：写导航层的作业在提交时记下预览时看到的状态，执行前再核对一次，对不上就以"冲突"失败，一行都不写。本票要定这个"状态"具体记什么（例如相关 `原始路径.json` 的内容哈希、链接当前的指向），以及核对哪些范围。
- **中断后的恢复流程**：写导航层的作业被中断（断电、worker 崩溃）后会标成已中断。worker 重启时先跑它的恢复流程，跑完才放行别的写操作。本票的"原子性"一项和"改指向改到一半时断电"场景，要给出这个恢复流程：是回滚还是补完，以及凭什么判断已经做到了哪一步。

补充（来自「[数据集板块的数据契约](11-dataset-contract.md)」，ADR 0006）：
- **改写范围比"改 `原始路径.json`"大得多**：
  - 数据盘的绝对路径在三种 JSON 里都有。两个视图合计，`原始路径.json` 里有 7,634 处，`子任务.json` 里有 16,908 处，`数据集信息.json` 里有 608 处，后者在第 2 项"地址"和第 14 项"信息来源与核验日期"的 Markdown 正文里。
  - 光 agibot_world_2026 一个数据集就约 6,900 处，分散在 6 个文件里。
  - 已定：改指向时按前缀替换，覆盖所有表示"现在的位置"的地方，包括 `direct_path`、链接的 `source_path`、`dataset_roots`、子任务里的路径和 Markdown 里的路径；跳过 `original_path`。Markdown 里的每一处替换都列进预览。
  - 本票要定替换的边界规则，例如前缀后面必须紧跟 `/` 或者是字符串结尾。
- **字段规则已定**：
  - `original_path` 不改，`source_id` 不重算。
  - 能推出来的字段（`entry_path`、`view`/`format`/`version`）在写入时由平台重新生成。
  - 不认识的字段原样保留。
  - 本票要定：写回时，要不要顺手给 `数据集信息.json` 补上缺的 `schema_version`，要不要把省略的 `version` 写成 `null`。
- **副本**：写入时先改按任务入口（规范副本），再由它生成按格式入口的各份。本票要定生成规则：
  - 按格式入口只保留"该格式那一部分"时，数据块和子任务怎么筛选。EgoProDemo 是现成的例子。
  - 链接够不着的数据块怎么处理。例如 alpha 有 3 个这样的数据块，它们的 `entry_path` 是绝对路径。
- **体检就是一致性面板**：检查清单写在「数据集板块的数据契约」的 Answer 里，本票不再定"体检覆盖哪些检查"。
- **写入之后**：在同一个作业里更新受影响数据集的索引，并提交一次统计大小。
- **预览时记下的状态**：重新扫描在第二段提交结果时，也要判断这期间数据集有没有被改过。两处用同一种状态，例如入口里三份 JSON 的内容哈希，加上各链接的指向。
- **数据集编号**：`dataset_id` 不复用。本票要定：
  - 新增数据集时，编号怎么分配。
  - 如果做"移除数据集"（只移除导航层入口，不删数据），之后怎么保证编号不会被重新分配出去。索引可以重建，所以这份记录不能只放在数据库里。
- **存储根**：链接目标可以在只读的存储根下，因为链接只是指向它；但新产物只能写进可写的存储根，也就是平台区。

补充（来自「[核心领域模型与术语](13-domain-model.md)」）：新增数据集时，要写入它的数据来源，例如下载入库的写"开源下载"。写在哪里，由「工具清单与转换血缘」定。

**完成标准**：以上各项都有结论，至少走过三个场景：建链时目的路径已存在；改指向改到一半时断电；改指向 40 天后发现指错了，要撤回（此时操作日志已经清掉）。写入与回滚策略写成 ADR；新出现的术语写进 `GLOSSARY.md`。

补充（来自「[工具清单与转换血缘](15-tool-manifest-lineage.md)」，ADR 0008）：
- **第四个文件 `来源.json`**：按任务入口下新增一份，记数据来源、所属采集任务和血缘。新建入口、改指向、移动的规则都要把它算进去；只放在按任务入口里，按格式入口不放副本。
- **入库也是写导航层**：暂存区的产物检查通过后，入库就是在同一文件系统上改名，然后建入口。建入口的规则，和"新增数据集"用同一套。
- **小的写入作业**：在网页上改数据来源或所属采集任务，会提交一个写导航层的小作业，只改 `来源.json`。


## Answer

### 1A：不依赖 NAS 的部分（2026-10-28 已决）

负责人 2026-10-28 23:31（MDT）："软链接 1A 都按推荐"。1A 的 L1–L19 全部采用《[决策简报](../assets/decision-prep-12-17-04.md)》第 1 节的推荐选项。每条的选项、后果和依据以简报为准，这里只记要点。

**建链**
- **L1（A）建链校验**：保留 0003 4.4 的五条，再补四条：目标 `realpath` 后必须落在已登记的存储根下；目标不能在导航层内部；链接名不含 `/`、不以 `.` 开头、不和入口里的四份 JSON 同名；目标不在 `dataset_roots` 之内时，预览提示"将把 X 加进 `dataset_roots`"。口径和一致性面板第 10 条一致。
- **L2（A）目的路径已存在（场景一）**：拒绝，提示改走改指向。例外：已存在的链接指向同一目标、并且已登记在 `links[]` 里，按"已经是这样了"成功，什么都不写。
- **L3（A）写回 `原始路径.json`**：`links[]` 追加一项（`entry_path` 由平台推导）。目标没被现有数据块覆盖时，`sources[]` 追加一个数据块，`source_id` 照现有规则算一次，之后永不重算；`format`/`version` 取自预览时读到的 `meta/info.json`，`validation_status=path_exists_only`。必要时追加 `dataset_roots`。一个链接目标对应一个数据块。
- **L4（A）两个视图**：建链一律落在按任务入口（规范副本）。按格式入口在预览里勾选（0 到多个），由规范副本按 L8 生成。

**新增数据集与编号**
- **L5（A）新增数据集**：一个作业里建好按任务入口：目录、链接、三份 JSON 的骨架，以及 `来源.json`（数据来源必填）；再加上勾选的按格式入口。14 项写好编号和名称，`value_markdown` 留空；`子任务.json` 写 `tasks: []`、`task_count: 0`。
- **L6（A）`dataset_id` 分配**：在写锁下扫描 `按任务/` 和 `已移除/`，取最大编号加 1，写成 `dataset-36` 这样，至少两位。
- **L7（A）移除数据集**：v1 做"移除"，只移除导航层入口，不删数据。按任务入口和它的各按格式入口整体挪到顶层新增的非数据集目录 `已移除/<dataset_id>_<名称>/` 下，JSON 原样保留，可以挪回恢复。`已移除/` 加进非数据集目录登记表。

**副本与字段**
- **L8（A）按格式入口的生成**：链接以该入口自己的 `links[]` 为准；`sources[]` 取规范副本中 `direct_path` 落在本入口某个链接目标之下的数据块，`entry_path` 重新推导；`子任务.json` 只保留引用到入选数据块的任务，任务内的数据引用同样筛；`数据集信息.json` 整份复制。实现时用 EgoProDemo 做对拍。
- **L9（A）链接够不着的数据块**（alpha 的 3 个）：只留在规范副本里，`entry_path` 保持绝对路径；按格式入口不收录。第一次写 alpha 时预览会列出这 3 条。
- **L10（C）**：推导字段整组重新生成时写出 `version: null`；`数据集信息.json` 不补 `schema_version`。
- **L11（A）JSON 写出格式**：保持原来的键顺序，2 空格缩进，`ensure_ascii=False`，结尾换行；新键追加在末尾，不认识的键原样保留。

**预览、原子性、恢复、撤回**
- **L12（A）预览时记下的状态**：对每个受影响的数据集（按任务入口及其全部按格式入口），记入口里每份 JSON（含 `来源.json`）的 sha256、入口目录的条目名清单、每条链接的 `readlink`。新增数据集另记"目的目录不存在"和当时的最大编号。重新扫描第二段提交时也用这同一种状态。
- **L13（A）原子性**：日志先行。写之前在状态目录 `nav-journal/<作业编号>/` 落一份计划（每一步的路径、前像、后像哈希）并 fsync；然后逐个文件写临时文件、fsync、`rename` 替换，链接先建到临时名再 `rename`。中途失败按前像逆序退回。
- **L14（A）中断后的恢复**：回滚。worker 启动时读 `nav-journal`，逐项比对：等于后像的退回前像，等于前像的不动；两者都不是的停下列出，作业标"恢复失败"，写操作继续被挡住，直到管理员处理完、在页面上确认。回滚完的作业是"已中断"，用户重新预览后再提交。
- **L15（A）操作日志字段**：只记摘要：谁、什么时候、作业编号、操作类型、涉及的数据集、改了几个文件几条链接、结果，加一个变更记录编号。前像和后像全文不进数据库。
- **L16（A）超过 30 天的撤回（场景三）**：每个写导航层的作业，把计划和前像、后像打包成状态目录里的 `nav-changes/<作业编号>.json.gz`，永久保留。撤回是提交"撤回作业 #N"：由变更记录生成反向计划，照常预览、核对；当前状态不等于 #N 的后像就以冲突失败，并列出差异。

**改指向**（规则本身与 NAS 无关，本地盘之间的改指向也用）
- **L17（A）前缀边界**：前缀后面必须紧跟 `/`，或者到了 JSON 字符串的结尾。Markdown 正文里，"结尾"还包括空白、`` ` ``、引号、`)`、`]`、`>` 和中文标点（，。；：）」）。新旧前缀都是不带结尾 `/` 的绝对路径。
- **L18（A）替换范围**：三种 JSON（不含 `来源.json`）里所有字符串值中符合 L17 的都替换，只有 `original_path` 例外。预览按字段分组给出数量，Markdown 和 `notes` 每一处单独列出。`来源.json` 只追加，不改写。
- **L19（A）新位置核对**：旧位置现在存在的路径，新位置必须全部存在，并且落在已登记、在线的存储根下，缺一个就整批拒绝。旧位置本来就不存在的（例如 alpha 那 3 条）照样替换，预览里标"旧位置原本就不存在"。

**三个场景**：按简报 1C 走过一遍，三个场景都由上面的规则覆盖：场景一靠 L2，场景二靠 L13、L14，场景三靠 L16。
