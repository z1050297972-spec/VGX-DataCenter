## Question

工具库按什么约定组织（原始需求 (8)）？数据集的血缘，也就是它"是怎么来的"，记录在哪里（原始需求 (7)）？推荐答案见 0003 第六节的 (7)、(8)；格式版本以「[平台统一的 LeRobot 版本](07-lerobot-version.md)」为准，对象以「[核心领域模型与术语](13-domain-model.md)」为准。

要定的：

- **工具目录与清单**：
  - 目录怎么命名；`tool.toml` 清单有哪些字段
  - 工具放在哪里：`/mnt/datasets/工具/`，还是平台仓库里的 `tools/`
  - 现有的 mcap2lerobot 怎么纳入
- **调用方式**：平台用子进程调用工具；运行环境怎么指定（conda 的 lerobot 环境、Rust 二进制）。
- **血缘**：录制时转换、录制后转换、下载，这三种来源记在哪里，导航层 JSON 还是数据库；记录方式要和"导航层是事实来源"一致。
- **导出 v2.1 算不算平台功能**：openpi、GR00T、Galaxea、智元自家的训练代码只读 v2.1，但官方只有 v2.1 → v3.0 的单向脚本，而且它会丢掉非标准的 `info.json` 字段。导出 v2.1 要不要作为一个登记在册的工具，导出产物是否计入血缘（见「[平台统一的 LeRobot 版本](07-lerobot-version.md)」）。

**负责人初步意见**（走「[技术栈与工程规范](03-tech-stack-standards.md)」时给出，本票确认）：
- 原话是："之后在 nas 上基于现在的结构，再分出一个测试区的目录，有这个必要吗？"
- Claude 的推荐：
  - 有必要，但做成**暂存区**。
  - 转换产物先写进暂存区，回读检查通过后再入库（建导航层目录、链接和三个 JSON）；没通过的不出现在两个视图里。试跑新工具、新映射也放在暂存区，定期清理。
  - 暂存区和正式区放在 NAS 的同一个文件系统上，入库只需改名，不用再拷一遍数据。
  - 暂存区按作业分目录，不照搬导航层的结构。
- 存储根要不要区分只读和可写，归「[数据集板块的数据契约](11-dataset-contract.md)」。

补充（来自「[技术栈与工程规范](03-tech-stack-standards.md)」）：平台运行时不依赖 lerobot（ADR 0003）。需要 lerobot 的工作都做成工具，以子进程方式运行，"调用方式"一项按这个前提展开。

补充（来自「[可观测性与报错规范](09-observability.md)」，ADR 0004）：
- **上报协议**：工具库里的工具都要接入，按平台的诊断格式上报进度、诊断、条目结果、致命错误和结束摘要。事件种类和字段已在那张票定好。本票要定：
  - 清单里怎么声明支持哪个版本的上报协议；
  - 改不了的第三方脚本（例如 lerobot 官方的转换脚本）配的包装脚本放在哪里。
- **不经交互运行**：工具必须能不经交互地运行，例如 mcap2lerobot 需要确认时，非终端下不加 `--yes` 会直接报错。命令模板据此写。
- **分工**：mcap2lerobot 的上报模式、通道的具体实现，都在 M4 落地，本票不做。

补充（来自「[作业模型](10-job-model.md)」，ADR 0005）：
- **GPU**：worker 把 GPU 当作调度资源，一张卡同一时间只给一个作业。清单里要声明工具是否需要 GPU。GPU 用不了时，不自动改用 CPU 配置。
- **规范视频编码**：负责人要求转换放到 GPU 上做，但有几个事实要先考虑：
  - 本机两张 RTX 3090 的 NVENC 只能编码 H.264 和 HEVC，编不了 AV1。
  - lerobot 默认在 CPU 上用 `libsvtav1` 编码 AV1。
  - mcap2lerobot 的 `configs/r1lite.toml` 现在配的是 `hevc_nvenc`。
  - 智元的 v3.0 样本本身是 HEVC。

  所以本票要定：平台规范数据集的视频编码统一用哪一种；GPU 编出来的 HEVC 和下载来的 AV1 能不能并存。
- **血缘引用作业**：作业记录永久保留，所以血缘记录可以引用产生它的作业编号。作业日志 30 天后删除，之后要复现，只能靠血缘里记的工具版本和配置。
- **转换的中断**：转换作业的恢复方式是"标记中断"，由人重新提交，重新提交会新建一个作业。半成品放在哪里、怎么清理，和暂存区方案一起定。mcap2lerobot 在输出目录已存在时，要加 `--force` 才会覆盖。

补充（来自「[数据集板块的数据契约](11-dataset-contract.md)」，ADR 0006）：
- **能写的地方只有平台区**：
  - 存储根分只读和可写，两块数据盘都是只读的。
  - NAS 上单独划出一个平台区，下载、转换、暂存、备份的产物都写在这里，暂存区也放在平台区里。
  - "可写"只表示可以新建，数据一旦入库就不再修改。
- **这两个目录归本票处理**：平台不扫描 `解压样本/` 和 `工具/`。本票要定：
  - `解压样本/`（系统盘上 224 GB 真实数据）要不要挪进暂存区。
  - `工具/`（mcap2lerobot，2.1 GB，主要是构建产物）怎么处理。
- **血缘怎么引用**：引用数据集用 `dataset_id`，引用数据块用 `source_id`，两者都永久不变。
- **实际格式版本**：扫描时会读到每个 LeRobot 数据块 `meta/info.json` 里的 `codebase_version`，血缘可以用它记下数据的实际格式版本。

补充（来自「[核心领域模型与术语](13-domain-model.md)」）：
- **工具挂在机器人型号上**：原始需求 (8) 里说的"工具对应型号的机器人"，指的是平台登记的机器人型号，不是数据里的型号标签。
- **数据来源存在哪里，由本票定**：
  - 数据来源是数据集的一个属性，取值有：真机采集、UMI 采集、ego 采集、仿真生成、开源下载、未知。
  - 平台自己产出的数据集，数据来源自动确定：采集任务产出的，看采集方式对应哪种来源；下载作业入库的，算开源下载。
  - 数据来源和"采集任务 → 数据集"这条关系，回答的都是"这个数据集是怎么来的"，所以和血缘一起定存放的位置：导航层的 JSON，还是数据库。
- **现有数据集要一次性标注**：35 个数据集的数据来源，要由人标注一遍。在哪里标、怎么标，由本票一并定。
- **转换产物的来源**：转换出来的数据集，数据来源是跟着它的原始数据集走，还是另外算，由本票定。

补充（来自「[RobotProfile 是否共用](14-robot-profile.md)」，ADR 0007）：
- **事实和做法分开**：工具配置只写做法，包括同步基准、容差、切 episode 的规则、帧率、编码。话题、关节顺序、单位这些事实，以 RobotProfile 为准。
- **核对，不生成**：工具配置里写的话题和关节顺序，要和 RobotProfile 核对，对不上就报错。v1 不从 RobotProfile 自动生成工具配置。核对放在哪一步、由谁来做，由本票定。
- **血缘**：血缘里要记下这次转换用的是哪个版本的 RobotProfile。

**完成标准**：以上各项都有结论，并用 mcap2lerobot 写一份清单草样来验证，草样要包含上报协议这一项；用 R1_lite_table_withdrawing 的 MCAP 和 LeRobot 两个版本，写一条血缘记录草样。结论写成 ADR；术语写进 `GLOSSARY.md`。本票加调 `algorithm-engineering`。

## Answer

2026-10-22 定稿，ADR 0008。草样在 `../assets/15-tool-manifest-lineage/`：`tool.toml` 是 mcap2lerobot 的清单，`来源.json` 是 dataset-29 的血缘记录。

调研到的事实：
- `R1_lite_table_withdrawing_lerobot`（dataset-29）的特征名和视频参数（hevc、crf 30）与 mcap2lerobot 的 `configs/r1lite.toml` 一致，几乎可以肯定是从 dataset-35 的三天 MCAP 转出来的。但哪里都没有记下版本、配置和输入。
- mcap2lerobot（0.1.0，提交 `4027d15`）的 `configs/r1lite.toml` 有 3 行没提交的改动，`docs/` 也没有纳入版本管理。
- mcap2lerobot 本身能输出 v2.1（`--format v2.1`）；输出目录已存在时，要加 `--force` 才会覆盖；`-y` 跳过确认。

**工具库**
- **位置**：负责人改了推荐，工具就放在导航层的 `工具/` 下，统一管理。`工具/` 是非数据集目录，平台不扫描、不写，现有目录不用动。工具库的位置写在平台配置里，默认是 `/mnt/datasets/工具`。
- **一个工具一个目录**：目录名按 `<输入>2<输出>[-<变体>]` 命名。每个工具目录是一个独立的 git 仓库，根目录放一份 `tool.toml`。
- **版本**：以 git 提交为准，血缘里同时记提交号和清单里的版本号。工作区不干净，平台就拒绝启动作业，并给出诊断。平台不负责构建工具，二进制的位置写在清单里。
- **清单字段**：
  - 身份：名称、版本、一句话说明。
  - 输入输出：输入格式；输出格式和格式版本。
  - 型号：适用的机器人型号，每个型号对应一份 `configs/<型号>.toml`。
  - 运行：运行环境；参数列表形式的命令模板，必须带上不经交互的参数；是否需要 GPU；上报协议的版本（没接入就写"无"）。
  - 清单是工具的事实来源，数据库里只放索引。
- **运行环境**：只支持二进制和 conda 两种。conda 直接调用 `~/miniconda3/envs/<名>/bin/python`。一律用参数列表启动子进程，不经过 shell。改不了的第三方脚本配一个包装脚本，作为单独的工具登记，包装脚本放在这个工具自己的目录里。
- **mcap2lerobot 怎么接入**：先提交现有的改动，再加上 `tool.toml`；上报协议在 M4 接入。

**血缘与数据来源**
- **存放**：按任务入口下新增一份 `来源.json`，现有三个 JSON 的格式不改。里面有三样：数据来源、所属的采集任务、血缘记录。导航层由此成为"数据集怎么来的"的完整事实来源；数据库里只放索引（ADR 0006）。
- **一条血缘记录写什么**：
  - 输入：`dataset_id` 和 `source_id`。
  - 产物：`source_id` 和实际的 `codebase_version`。
  - 工具：名称、版本、提交号。
  - 配置：文件全文和 sha256。
  - 其他：RobotProfile 的型号和版本；命令参数；作业编号；UTC 起止时间；入库检查的结果。
  - 下载产生的记录：来源地址、仓库名、修订号，以及作业编号。
- **怎么写**：由 worker 在入库时写，记录只追加。
- **现有数据集**：现有 35 个数据集写成"来历未知"，可以由人补录成"来历部分未知"，例如 dataset-29。
- **数据来源**：
  - 平台自己产出的数据集，数据来源自动确定（见「核心领域模型与术语」）。
  - 转换产物的数据来源沿用输入数据集的。
  - 现有 35 个由人在网页上逐个标注。
  - 修改数据来源或所属的采集任务，都会提交一个写导航层的小作业，由 worker 写。
- **没有 `来源.json` 的入口**：按"数据来源未知、来历未知"处理，一致性面板只给提示。

**转换产物**
- **暂存区**：工具的输出目录一律设在平台区的 `暂存/<作业编号>/`。
  - 重新提交就新建一个作业，用新的目录，所以不需要 `--force`。
  - 失败和中断的目录保留 7 天，由每晚的作业清理。
- **入库检查**：
  - 转换作业结束时自动跑一遍。暂存区里每个产物都有"检查并入库"按钮，可以手动再跑。
  - 检查按产物的格式定，不按工具定。LeRobot 分四层：
    1. 结构：`info.json` 能读，`codebase_version` 和清单声明的一致，必需的目录都在。
    2. 计数：轨迹数、帧数、parquet 行数三方一致。
    3. 视频：引用到的文件都在；用 ffprobe 读文件头，和 `info.json` 一致；时长约等于帧数除以 fps。
    4. 内容：`state` 和 `action` 的维度、名字和配置以及 RobotProfile 一致；抽查几个 episode，没有 NaN，取值在合理范围内。
  - 工具的退出码不是 0，或者结束摘要是"失败"，直接判为不通过。
  - 结果分三种：通过就自动入库；有警告，由人确认后入库；不通过，留在暂存区。
  - 逐帧解码不在默认检查里，归到"数据质检"那一块。
- **入库**：在同一个文件系统上改名，然后建导航层的入口。
- **转换产物是新数据集**，和现在 `_mcap`、`_lerobot` 分成两个数据集的做法一致。
- **视频编码不统一**：平台转换默认用 GPU 编 HEVC，HEVC 和 AV1 可以并存。编码作为每个数据集的一项事实，从 `info.json` 读出。只认 AV1 的训练框架，要在 M4 用真实的训练代码验证。
- **v2.1 导出**：算平台的转换功能，产物作为新数据集入库，并记录血缘。
  - MCAP 数据用 mcap2lerobot 的 `--format v2.1`。
  - 下载的 v3.0 数据，要另写一个 v3.0 到 v2.1 的工具。负责人说不急，放到 M4，写之前先调研有没有现成的。
- **和 RobotProfile 核对**：作为转换作业的第一步，由 worker 做；提交作业前的预览也跑一遍。具体实现放在 M4。
- **`解压样本/`**：平台不管。等 NAS 到了，由负责人手工挪进平台区，按普通入库流程登记，或者直接删掉。

**负责人原话**："我最开始计划把工具放到导航层的工具目录下，为的是个统一管理"；"能否给一个检查摁纽，通过后自动入库"。
