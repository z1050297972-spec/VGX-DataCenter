# 数据集板块的数据契约

Type: grilling
Status: resolved
Blocked by: 01

## Question

平台怎么理解导航层？以「[盘点导航层的 70 份 JSON](01-nav-json-inventory.md)」的事实为依据，0003 第四节的推荐答案为起点。

要定的：

- **事实来源**：确认导航层是数据集的唯一事实来源，数据库里只存可以重建的索引（0003 4.1）。
- **数据集身份**：用 `dataset_id` 作主键；两个视图里的副本怎么关联；副本内容不一致时以哪份为准。
- **目录深度**：两种目录深度（F6）怎么统一表示；"格式""版本""视图"这几个术语各指什么。
- **三个 JSON 的读取契约**：
  - 哪些字段平台依赖，哪些只做展示
  - `数据集信息.json` 的值是 Markdown 文本，要不要解析出结构化字段。0003 4.2 要按机器人型号、FPS 筛选，而这两个值都在 `value_markdown` 里
- **存储根**：两块盘加 NAS 怎么登记；存储根离线（`nofail` 挂载没挂上）时，数据集处于什么状态。
  - 另外要定：存储根要不要区分只读和可写。0003 写的是"数据盘对系统只读"，但下载和转换的产物都要写进 NAS。负责人还提出转换要有试跑区，见「[工具清单与转换血缘](15-tool-manifest-lineage.md)」。
  - 这一点要和「[备份方案](17-backup.md)」里的 NAS 写入例外一起对齐。
- **数据集大小**：大小从哪里来，用"数据大小"这一项，还是现算？13 TB 的 tar 现算 `du` 很慢，0003 4.3 写的"实时显示目标多大"是否可行。
- **索引重建时机**：手动"重新扫描"、平台启动时、定时，还是监听文件系统。
- **一致性面板**：要检出哪些问题（0003 4.3）。
- **非数据集目录**：`索引/`、`解压样本/`、`文档/`、`工具/` 这些目录怎么对待。（`日志/` 原来也在这里，「作业模型」定了日志不放导航层，所以已经删掉。）

盘点之后新增的待定点（事实见 `docs/brief/0005-环境事实更新-导航层盘点.md`）：

- **`按格式` 是副本还是切片**：EgoProStandard、EgoProDemo 在 `按格式` 里的链接指向格式子目录，EgoProDemo 还少了 1 条 source 和 1 个子任务。所以上面"副本内容不一致时以哪份为准"的前提要先改。同时要定：一个包含多种格式的数据集，在 `按格式` 里出现几次。
- **导航 JSON 与磁盘漂移**：已经实际发生过（智元的 3 个目录被删除，JSON 没有同步）。一致性面板要不要检出"JSON 引用了不存在的路径"，以及 `.aria2` 残留这类未下载完的文件。
- **读取契约里的不一致**：`数据集信息.json` 没有 `schema_version`；"没有版本"在 `子任务.json` 里是省略这个键，在 `原始路径.json` 里是 `null`；`format=archives` 和目录名不一样；`validation_status` 的含义没有任何文档说明。
- **`解压样本/`**：在系统盘上放了 224 GB 真实数据，平台把它当作数据集、样本，还是忽略。

补充（来自「[技术栈与工程规范](03-tech-stack-standards.md)」）：假导航层和代码测试用的样本，都从真实数据里只读截取，放在 `tests/fixtures/`，不用 lerobot 现场生成（ADR 0003）。

补充（来自「[作业模型](10-job-model.md)」，ADR 0005）：
- **`日志/` 不在导航层**：作业日志放在平台状态目录，导航层里不会出现 `日志/`。上面"非数据集目录"一项已经把它删掉。
- **存储根在线检查**：作业开跑前，要确认它要写的存储根确实挂载着，不在线就以"外部失败"结束，什么都不写。这样做是因为 NAS 没挂上时，挂载点只是系统盘上的空目录。本票定"存储根离线"时，一并定"在线"怎么判断，供作业调用。
- **重新扫描是作业**：由 worker 执行，执行时持有导航层写锁。"索引重建时机"里的手动、平台启动时、定时，最后都是提交一个重新扫描作业。

**完成标准**：以上各项都有结论，至少走过四个场景：NAS 掉线时打开智元数据集；两个视图的 `数据集信息.json` 不一致；有人在终端里手工删了一条链接；有人在数据盘上删了一个目录，但没有更新 JSON。"导航层是事实来源"写成 ADR；导航层相关术语写进 `GLOSSARY.md`；M0 测试用假导航层的形态要求写在本票 Answer 里。

### 结论

#### 事实来源与身份（Q1、Q9）

- 导航层是数据集的唯一事实来源。数据库里只放数据集索引，可以整个删掉，重新扫描就能恢复。平台自己的对象引用数据集时，只用 `dataset_id`。
- `dataset_id` 一经分配就不改、不复用，数据集改名也不变。新 id 怎么分配，归「软链接接口规则」。
- 数据块的三个身份字段：
  - `source_id`：不重算。
  - `original_path`：首次登记时的位置，永远不改，一致性面板不检查它。
  - `direct_path`：现在的位置，随改指向更新，一致性面板检查它是否存在。

#### 两个视图与格式目录（Q2、Q3）

- **按任务**：每个数据集恰好有一个入口，代表完整的数据集，它的三份 JSON 是规范副本。`dataset_roots` 和 `sources` 以这里为准。
- **按格式**：入口代表数据集在该格式下可以直接用的那一部分，一个数据集可以有 0 到多个入口，不要求每种格式都有。
- **不一致时**：两份 `数据集信息.json` 不一致的，按规范副本显示，面板报出。只有按格式入口、没有按任务入口的，照常列出，面板报出。
- **格式目录登记表**：
  - `lerobot` → `lerobot`，有版本层
  - `mcap` → `mcap`
  - `tar、tar.gz（含分卷）` → `archives`

  入口的位置统一记成（视图，格式，格式版本，数据集名）。不改目录名。出现没登记的目录，面板报出。

#### 读取契约（Q6、Q8）

- **平台依赖的字段**：
  - `原始路径.json`：`schema_version`、`dataset_id`、`dataset_name`、`dataset_roots`；`links[]` 的 `name`、`source_path`、`source_type`；`sources[]` 的 `source_id`、`original_path`、`direct_path`。
  - `数据集信息.json`：`dataset_id`，以及 `fields[]` 的结构。
  - `子任务.json`：`schema_version`、`dataset_id`。
- **推导字段**：`view`/`format`/`version`、`links[].entry_path`、`sources[].entry_path`。平台按位置自己算，文件里存的值只用来核对。
- **其余字段**：原样展示；不认识的字段原样保留。
- **宽松读取**：
  - 缺 `schema_version` 当作 1；省略 `version` 等同于 `null`。
  - 遇到不认识的 `schema_version`、解析失败、缺少依赖的字段，这份文件不解析。数据集照常列出，带一条诊断。
- **14 项**：`value_markdown` 只按 Markdown 渲染，不解析。
- **`validation_status`**：原样显示，配中文标签，见导航层手册第 5 节。
- **不改现有 JSON 的格式**，冗余这样消化：
  1. 绝对路径保留。改指向时按前缀替换，三种 JSON 全部覆盖，Markdown 里的每处替换都列进预览（「软链接接口规则」）。
  2. `source_id` 不重算。
  3. `original_path`、`direct_path` 按上面的含义处理。
  4. 推导字段由平台算，写入时重新生成。
  5. 写入时先改规范副本，再由它生成按格式入口的各份。生成的仍是真实文件。
  6. 快照值标明记录日期，平台算出的值并排显示。
- **停用旧程序**：当初生成这些 JSON 的程序以后不再运行。

#### 存储根（Q4、Q5，以及走场景时补的一条）

- **登记**：记下路径和挂载源。ext4 记文件系统 UUID，NAS 记"服务器:导出路径"。现在登记的是 `/mnt/dataset1`、`/mnt/dataset2`。
- **在线**：此刻是挂载点，并且挂载源和登记的一致。只读挂载表来判断（例如 `findmnt --mountpoint`），不往数据盘上放标记文件。
- **超时**：作业访问存储根时带超时，超时就按离线处理，作业记一条警告。超时设多长、卡住的读取能不能中止，等「NAS 接入事实」测出来再定。
- **离线时**：
  - 数据集照常列出，三份 JSON 照常能看。
  - 链接标"存储根离线"，不算断链。
  - 大小显示上次的统计值。
  - 面板顶部报一条，并跳过这个存储根下的磁盘检查。
- **只读和可写**：存储根默认只读，两块数据盘都是只读。NAS 登记成两个存储根：
  - 智元数据迁过去的那部分：只读。
  - 平台区：可写。下载、转换、暂存、备份的产物都写在这里。

  "可写"只表示可以新建，入库后的数据不再修改。v1 不提供删除数据的功能。
- 链接目标不在任何已登记的存储根下的，面板报出。

#### 非数据集目录（Q7）

- 平台只扫 `按任务/` 和 `按格式/`。顶层的 `索引/`、`文档/`、`工具/`、`解压样本/` 登记为非数据集目录，不扫描。顶层出现登记表以外的目录或文件，面板报出。
- `解压样本/` 要不要挪进暂存区、`工具/` 怎么处理，都归「工具清单与转换血缘」。`索引/` 保留不动。

#### 大小（Q10）

- **"统计大小"作业**：只读数据盘，结果写进索引，不拿导航层写锁，用最低的 IO 优先级。三种情况提交：
  - 每晚定时一次，提交人记为"系统"。
  - 写入作业完成后，对相关的数据集补算一次。
  - 页面上手动提交。
- **按链接目标统计**：
  - 入口的大小 = 它所有链接目标的大小之和。
  - 数据集的大小 = 它按任务入口的大小。
  - 树上一个节点的大小 = 节点下各入口之和。

  没被链接的内容不计入。
- **口径**：表观字节数，和"数据大小"一项里记录的字节数口径相同。
- **显示**：详情页同时显示统计值（带统计时间）和"10-12 记录"的值。列表和树上用统计值，没统计过的用记录值，并标出来。
- **顺带统计**：同一次遍历数出 `.aria2` 和 `.incomplete` 文件，交给面板。

#### 筛选（Q11）

- 扫描时读每个 LeRobot 数据块的 `meta/info.json`，取出 `robot_type`、`fps`、`codebase_version`。一个数据集可以有多个值。
- 值为 `unknown`、`null`，读不到，或者不是 LeRobot 格式的，都归为"未知"。现在 25 个数据集能按型号筛到，10 个归为"未知"。
- FPS 按四舍五入后的整数匹配。
- 这里的 `robot_type` 只是数据里写的字符串。它和平台登记的机器人型号是什么关系，归「核心领域模型与术语」。

#### 网页与详情页（Q12）

- **读索引的**：两棵树、数据集列表、筛选、一致性面板、链接状态、大小。
- **直接读导航层的**：详情页的三份 JSON，其中 `子任务.json` 点开才加载。读到的文件比索引新时，顶部给出提示和"重新扫描"按钮。
- **链接状态**：显示扫描时查到的结果和检查时间。详情页的"重新检查"按钮，会提交一个只扫这一个数据集的扫描作业。0003 4.3 里的"实时显示"改为这样。
- **边界**：Web 可以只读导航层本身，但不访问存储根。这是 ADR 0006 对 ADR 0005 的补充。

#### 重新扫描（Q13）

- **范围**：全量，或者只扫一个数据集。
- **时机**：
  - 手动提交。
  - worker 启动时。
  - 每 10 分钟定时一次，全量。
  - 平台的写入作业，在同一个作业里更新受影响数据集的索引。
- 不监听文件系统。
- **分两段执行**：
  1. 持导航层写锁，读导航层（实测 0.2 秒），然后放锁。
  2. 再检查数据盘（约 8 秒）。

  提交结果时，跳过这期间被写入作业改过的数据集。

#### 一致性面板（Q14）

- 每个问题是一条五段诊断，分"需要处理"和"提示"两级。面板只报告，不修复。「软链接接口规则」里说的"体检"就是这个面板。
- 同一类问题合并显示，并列出前几个样例。
- 面板上的问题是扫描的"发现"，不算扫描作业失败。只有两种情况会影响扫描作业的结果：
  - 某个入口因为第 1 条的问题建不了索引，算失败条目。
  - 存储根离线、跳过了检查，算警告。
- **完整的检查清单**：
  - ① JSON 本身（都是需要处理）：
    1. JSON 解析失败、缺少依赖的字段，或者 `schema_version` 不认识。
    2. 一个入口里三份 JSON 的 `dataset_id` 不一致；目录名和 `dataset_name` 不一致；同一个 `dataset_id` 出现在两个按任务入口里。
    3. 只有按格式入口，没有按任务入口。
    4. `按格式/` 下有没登记的格式目录；顶层有没登记的目录或文件。
    5. 存下来的推导字段，和按位置算出来的不一致。
  - ② 两个视图之间（都是需要处理）：
    6. 按格式入口的 `数据集信息.json` 和规范副本不同。
    7. 按格式入口的数据块，不是规范副本数据块的子集（按 `source_id` 对）；或者同一个数据块，除位置字段以外内容不同；或者顶层的 `dataset_name`、`dataset_roots` 和规范副本不同。子任务按 `task_key` 同样核对。
  - ③ JSON 和磁盘之间（只在存储根在线时查）：
    8. 磁盘上的链接和 `links[]` 不一致：多了、少了，或者指向不同。需要处理。
    9. 断链。需要处理。
    10. 链接目标不在任何已登记的存储根下，或者不在 `dataset_roots` 之内。需要处理。
    11. 失效引用，不查 `original_path`：
        - `dataset_roots`、数据块的 `direct_path` 失效：需要处理。
        - `excluded_from_navigation`、子任务里的路径、14 项 Markdown 里的本地链接、`summary_path` 失效：提示。
    12. 数据块登记的格式版本和 `info.json` 的 `codebase_version` 不一致。需要处理。
    13. 按子目录链接的数据集，根目录下有既没被链接、也没登记为排除的内容。提示。
  - ④ 存储状况：
    14. 存储根离线，或者挂错了盘：在面板顶部报一条，并跳过它下面的磁盘检查。需要处理。
    15. 有没下载完的文件，由统计大小作业数出来。提示。
- **第一次扫描的预期**（按 2026-10-22 的数据）：
  - 需要处理 1 类：agibot_world_alpha 那 3 个已删除转换副本的数据块路径不存在，每个视图 3 条。
  - 提示 5 类：
    - `summary_path` 失效，涉及 35 个数据集。
    - 排除目录已不存在，涉及 2 个数据集。
    - 子任务和 Markdown 里的失效引用，涉及 2 个数据集。
    - 有没下载完的文件，涉及 2 个数据集。
    - 根目录下有没被链接的内容，涉及 1 个数据集。

#### 假导航层（Q15，M0 的形态要求）

- **路径从配置读**：平台代码里不写死 `/mnt/...`。导航层的位置和各个存储根都从配置读，测试时指向临时目录。
- **挂载表可替换**：存储根在线检查里"读挂载表"这一步可以替换。测试用它模拟离线、挂错盘和超时，不需要真的去挂载。
- **样本**：`tests/fixtures/` 里放从真实数据只读截取的样本。
  - 5 个必选数据集的三份 JSON：libero_10、R1_lite_table_withdrawing_mcap、EgoProStandard、EgoProDemo、agibot_world_alpha。
  - 大的截短，例如 EgoProStandard 的 734 条数据块只留几条。
  - 保留中文标点、空格、括号、撇号这些难处理的字符。
  - JSON 里的绝对路径换成存储根占位符，例如 `{dataset1}/libero_v3/libero_10`。
- **清单**：另附一份清单，写明每个入口有哪些链接，以及假存储根上要造哪些目录和小文件。其中包括带真实 `robot_type`、`fps`、`codebase_version` 的 `meta/info.json`。
- **展开**：测试开始时，由一个 fixture 在临时目录里把样本展开：
  - 建假存储根。
  - 建两个视图的目录和真实的软链接。
  - 替换占位符。
  - 带上空的 `lerobot/2.0`、`lerobot/2.1`，以及非数据集目录的骨架。
- **每条检查都有测试**：面板的每一条检查至少有一个测试。做法是在展开后的假导航层上改一处，再断言报出的诊断（对象、规则、级别），不为每种异常各存一份样本。
- **大规模不进 `make check`**：753 万个文件这种规模不放进检查链。M1 验收时，在真实数据上只读实测一次扫描和统计大小的耗时。
- **可选样本先不放**：agibot_world_2026（14 MB 的 `子任务.json`）和 libero_90（跨数据集的子任务）暂时不放，需要时再加。

### 四个场景

**场景一：NAS 掉线时打开智元数据集**（假设智元数据已经迁到 NAS）
1. 下一次扫描发现 NAS 存储根离线（没挂上，或者访问超时）。面板顶部显示"存储根 NAS 离线"，跳过它下面的检查，这次扫描作业记为"带警告成功"。
2. 数据集列表里，智元数据集照常显示，大小显示上一次的统计值和统计时间。
3. 打开详情页，三份 JSON 照常能看。链接标"存储根离线"，不标断链。网页不碰 NAS，所以不会卡住。
4. 这段时间里要写 NAS 的作业，开跑前发现存储根离线，以"外部失败"结束，什么都不写。NAS 恢复后，下一次扫描自动恢复正常。

**场景二：两个视图的 `数据集信息.json` 不一致**
1. 有人在终端里改了 `按格式/lerobot/3.0/libero_10/数据集信息.json`。
2. 最多 10 分钟后，扫描在面板第②组报出"按格式那份和规范副本不同"，级别是需要处理，并列出哪几项不同。
3. 页面一律按规范副本显示。
4. 修复办法：在终端里改回来；或者由平台的写入操作，从规范副本重新生成。

**场景三：有人在终端里删了一条链接**
1. 删掉的是 `按任务/libero_10/原始数据`。
2. 下一次扫描在面板第③组报出"`links[]` 里登记的链接 `原始数据` 在磁盘上不存在"，级别是需要处理。
3. 详情页仍然按 JSON 列出这条链接，标"磁盘上没有"。
4. 修复办法：用平台的建链功能按清单重建，或者在终端里恢复。平台不会自动修。

**场景四：有人在数据盘上删了一个目录，但没有更新 JSON**
1. alpha 现在就是这种情况：10-17 删了 `lerobot_v2_output`，JSON 没有跟着改。
2. 扫描在面板第③组报出两类问题：3 个数据块的 `direct_path` 不存在，需要处理；排除目录、子任务、说明里的引用失效，提示。
3. 如果删掉的正好是某条链接指向的目录，那就是断链，需要处理。
4. 下一次统计大小时，算出来的大小会相应变小，和 10-12 的记录值并排显示。

### 风险

- **NAS 卡死**：NAS 挂着但不响应时，挂载表里仍然显示已挂载，只能靠访问超时发现。「NAS 接入事实」测出挂载方式之前，超时的具体做法还定不下来。
- **手工修改要过一会儿才看得到**：终端里的修改，最多 10 分钟后才会出现在面板上。如果这期间有人基于旧状态预览了一次写入，执行前的核对会以"冲突"拦下（ADR 0005）。具体核对哪些内容，由「软链接接口规则」定。
- **每晚统计 alpha 很慢**：冷缓存下要遍历 753 万个文件和目录，约 8 分钟。虽然用了最低的 IO 优先级，和同一块盘上的转换作业仍可能互相拖慢，M1 验收时实测。
- **旧程序再次运行**：如果有人再跑一次当初生成 JSON 的程序，会覆盖平台写入的内容，还会重算 `source_id`。这一点已经写进导航层手册和 ADR 0006。
- **快照继续过期**：14 项不会更新，只能靠并排显示统计值来缓解。
