### 每张实现票的流水线（修订 0003 第八节的 ①–⑦）

1. **开票**：Claude 选票，把 Status 改成 `in-progress`。从 main 建分支 `t/<里程碑>-<NN>-<slug>`，用 `git worktree` 放进单独的工作目录 `~/桌面/robot-data-platform.wt/<里程碑>-<NN>-<slug>`。Claude 在里面装好依赖（`uv sync`、`pnpm install`），因为沙箱不能联网。
2. **派工 A**：在后台运行 `codex exec -C <工作目录> -s workspace-write --json -o <输出>`，记下会话编号。Codex 交付契约骨架和测试清单。
3. **骨架关卡**：Claude 审骨架，给负责人一页摘要（格式见下）。负责人说"通过"后，Claude 做契约提交。
4. **派工 B**：先进入工作目录，再执行 `codex exec resume <会话编号> -c 'sandbox_mode="workspace-write"'`。Codex 按测试清单逐个函数用 TDD 实现。
5. **评审**：不采信 Codex 自述，依次做：
   1. 在工作目录里重跑 `make check`。
   2. 核对文件归属：工作目录里 `git status --porcelain` 只能出现 `src/`、`tests/` 下的改动，本票明确允许的受保护文件除外；主仓库目录的 `git status --porcelain` 必须为空。越界直接打回。
   3. 拿契约提交对比工作区，确认已获批的签名和 docstring 没有被改。改了就按下文"契约变更"处理。
   4. 跑 `/code-review`。涉及同步、录制、转换的模块，再跑 `algorithm-code-review`。
6. **打回**：修复清单写进工单的 Comments，再续接会话发给 Codex，状态在 `changes-requested` 和 `in-progress` 之间切换。
7. **合并**：评审通过后，Claude 做实现提交，再给负责人汇报：改了什么、测试情况、风险。负责人说"合并"后，Claude 用 `--no-ff` 合并到 main，把 Status 改成 `done`，删掉工作目录和分支。

- **一次只做一张实现票。** 走图、写规划可以同时在主仓库目录里进行；工作目录分开，就是为了让两者互不干扰。

### 骨架关卡的一页摘要

按这五块写：
1. 这张票做什么，一句话。
2. 函数清单表：模块、函数、职责（一句话）、会改动什么、什么情况下报错。
3. 测试清单：每个契约行为对应的测试名。测试在骨架阶段就交，测试体先跳过（`pytest.skip`），所以骨架阶段的 `make check` 也能全绿。
4. 需要负责人拍板的问题，最多 3 条，每条附 Claude 的建议。
5. Claude 的结论：建议通过，或建议改。

### 契约变更

- Codex 不能自己改已获批的契约。实现时发现要改，就停下来，在最终回复里写"契约变更申请"：哪个函数、改什么、为什么。
- 改变含义的，回到负责人那里重新过骨架关卡。"改变含义"指参数、返回值、报错条件、副作用、时间语义有变化。
- 只是措辞、笔误、补充说明的，由 Claude 批准，记进 Comments，汇报时告诉负责人。

### 打回与升级

- 每次把修复清单发回给 Codex 算一轮，包括 Claude 重跑 `make check` 没过的情况；运行超时也算一轮。
- 第 3 轮仍不通过，就停下来，把问题清单和判断带给负责人，三种处理里选一种：
  - (a) 再给两轮；
  - (b) Claude 改写契约或把票拆小，开一个新的 Codex 会话重做（默认建议）；
  - (c) 这张票退回规划。

### 状态流转

- 实现票派工前，Status 用五个 triage 角色（`triage-labels.md`）。其中只有 `ready-for-agent` 能进入派工。
- 派工后的主线是 `in-progress → in-review → done`；打回时走 `in-review → changes-requested → in-progress`。
- 等负责人过骨架或者说"合并"时，Status 停在 `in-review`。
- 走图的决策票照旧用 `open / claimed / resolved`，和实现票的状态不混用。

### 提交

所有提交都由 Claude 做，都经过钩子跑 `make check`，不加 `--no-verify`。

| 时间点 | 提交说明开头 | 内容 |
|---|---|---|
| 骨架获批 | `契约：<票名>` | 签名、类型、docstring、跳过的测试清单 |
| 新增依赖获批 | `依赖：<包名>（<票名>）` | `pyproject.toml`、锁文件等。Claude 在工作目录里安装，单独提交 |
| 评审通过 | `实现：<票名>` | 实现和测试 |
| 负责人说"合并" | `合并：<票名>` | `--no-ff` 合并提交 |

- 打回期间不提交：钩子要求 `make check` 全绿，中间状态提交不了。每轮派工前，Claude 用临时索引给工作目录拍一个快照（`git write-tree` 加 `git commit-tree`，挂在 `refs/rdp/<票>/r<轮>` 上；这样不产生分支提交，也不触发钩子）。评审时比较前后两个快照，就能看出这一轮改了什么。
- 每次派工前，工作目录的 `git status --porcelain` 必须为空。这样派工之后出现的改动全是 Codex 的。
- 工单、Comments、派工记录这些规划文件，只在主仓库目录里改。实现分支上只有代码和依赖文件，合并时不会冲突。
- 如果整轮方向都错了，要丢弃工作区改动，先问负责人，不自行回退。

### 派工提示的内容

- **A、B 共有的部分**：
  - 先读 `AGENTS.md`、工单，以及工单引用的 spec、ADR 和 `GLOSSARY.md` 术语；
  - 写明本票允许改的受保护文件，没有就写"无"；
  - 改动留在工作区，不提交；
  - 需要新依赖就停下写依赖申请（`AGENTS.md` 硬性规则 7）；
  - 交付时在最终回复里列出改动清单、`make check` 的结果，以及有没有契约变更申请或依赖申请。
- **A**：只写契约骨架。签名、类型、六项 docstring 写全，函数体写 `raise NotImplementedError`；测试清单写成跳过的测试，每个测试的注释写明它验证哪条契约行为。
- **B**：按测试清单逐个函数做 TDD：先去掉一个测试的跳过、看到它失败，再写实现让它通过。已获批的契约不改。最后 `make check` 全绿。
- **修复轮**：只发修复清单，每条写明问题、位置和期望的结果。

### 非代码任务（走图时的 AFK 执行：盘点、采集、调研）

| 任务 | 沙箱 | 工作目录 |
|---|---|---|
| 只读取证 | `-s read-only` | 临时目录 |
| 要写脚本或中间文件 | `-s workspace-write` | 临时目录下单独一个子目录。写不到仓库，也写不到 `/mnt` |
| 联网调研 | `-s read-only -c 'web_search="live"'` | 临时目录 |

- **派工提示**写这几项：目标、只读范围、要交付什么（事实清单，每条附命令或来源网址）、禁止碰的路径（两个旧项目）。
- **证据**以运行日志（`--json`）里记录的命令和输出为准，不以 Codex 自己的总结为准。Claude 把用到的命令和输出整理进 assets。
- **联网调研**：每条事实都要附来源网址。要下载的东西（例如克隆一个仓库来读代码）Codex 做不了，由 Claude 先下到临时目录，再让 Codex 读。
- **复核**：
  - 写进 `docs/` 的每条事实，都要能追到 assets 里的原始输出。
  - 结论性的事实（计数、大小、有没有、版本号），由 Claude 重跑，或者亲自打开来源核对；其余抽查。
  - 抽查发现一处对不上，整份打回重做。
  - 另外查一遍运行日志里的命令，确认没有碰两个旧项目的路径。沙箱挡不住这一条（0009）。

### 执行细节

- **续接**：先进入那张票的工作目录，再执行 `codex exec resume`，并且用 `-c 'sandbox_mode="…"'` 显式写明沙箱模式。续接的会话会在执行命令时所在的目录里工作，不在当初 `-C` 指定的目录里（0009）。
- **会话**：一张实现票一个 Codex 会话，A、B 和各修复轮都续接这个会话。只有升级处理选了 (b)，才开新会话。
- **超时**：每次运行都设超时，暂定 60 分钟，M0 跑通时再调。
- **记录**：
  - 每次派工都在工单的 Comments 里记一条：会话编号、第几步或第几轮、结论。
  - 派工提示和 Codex 的最终回复（`-o`）存进 `.scratch/<里程碑>/assets/<NN>-<slug>/`。
  - 运行日志（JSONL）太大，留在临时目录。

### 文件归属、沙箱与依赖（已在「技术栈与工程规范」定好，这里只归位）

- Codex 只改 `src/`、`tests/`。React 前端放在 `src/web/`，也由 Codex 写（ADR 0001）。受保护文件只有工单明确允许时才能改。
- 在工作目录里，Codex 连 `git add` 都做不了，改动只能留在工作区（0009）。
- 新增依赖的流程按 `AGENTS.md` 硬性规则 7，安装和提交见上文"提交"一节。

### 风险

- **basedpyright 能否在沙箱里运行**：仍然留给 M0 第一张工单实测（「技术栈与工程规范」）。
- **读权限挡不住旧项目**：任何沙箱模式都能读整个文件系统，"不读旧项目"只能靠派工提示加事后查运行日志。
- **超时和快照的做法**还没在真实工单上跑过，M0 那张小票跑通后，通过 `/retro` 调整。
