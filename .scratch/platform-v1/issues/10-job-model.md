# 作业模型

Type: grilling
Status: resolved
Blocked by: 02, 03

## Question

长任务（下载、转换、重新扫描、批量改指向）在哪里跑、怎么看进度、出了事怎么恢复？

**负责人初步意见**（开图时给出，本票确认）：

- 作业由独立于 Web 的后台 worker 跑。Web 重启不影响正在跑的作业；整台电脑重启后，没跑完的作业能接着跑。
- 两个作业不能同时改导航层。
- 作业日志按时间记录在导航层根目录下的 `日志/下载/` 和 `日志/转换/`。

**先确认一处矛盾**：开图时负责人同时提到"Web 进程里的后台线程"和"单独的 worker"，这是两种方案，先确认选哪一种。

要定的：

- **worker 形态**：worker 是什么进程、怎么托管（systemd 用户服务？开机自启？）；Web 和 worker 之间怎么通信（例如共享 SQLite 里的作业表）。
- **作业状态机**：排队 / 运行 / 成功 / 失败 / 取消 / 中断。"整机重启后继续"具体指什么：哪些作业能断点续跑（例如 aria2 续传），哪些只能从头重跑，或者只标成中断。
- **导航层写锁**：锁的粒度（整个导航层，还是单个数据集）、怎么实现、持锁的进程崩溃后怎么办。
- **日志放在导航层的取舍**：导航层在系统盘上（F1，剩约 334G），又是数据集的唯一事实来源。日志写进去会不会影响扫描、备份和终端里的 `ls` 浏览？扫描器要不要忽略 `日志/`？
- **进度查看**：「[交互形态与前端路线](02-interaction-frontend.md)」已定为前端约 1 秒轮询一次，这里只定 worker 把进度写到哪里、Web 从哪里读。
- **提交人与权限**（来自「交互形态与前端路线」）：作业要记录提交它的账号。成员能不能取消别人提交的作业。
- **提交人的存法**（负责人初步意见，走「交互形态与前端路线」时给出，本票确认）：作业记录同时存提交人的内部编号和名字。账号删除以后，记录显示为"张三（已删除）"。作业记录不会挡着账号删除，作业记录保留多久可以单独定。

补充（来自「[可观测性与报错规范](09-observability.md)」，详见那张票的 Answer）：
- **作业日志**：内容和格式已经定了，包括开头、中间、结尾三段，结尾的摘要要和作业记录一致。本票只定放在哪里。
- **作业结果**：成功、带警告成功、部分成功、失败，共四种，由计数算出（见 `GLOSSARY.md`）。状态机的终态要容纳这四种结果，还要定取消、中断和它们怎么并存。
- **进度要存的字段**：
  - 阶段的序号、总数和名称；
  - 已完成数、总数（可以为空）、单位；
  - 警告数、失败数；
  - 更新时间。

  每秒最多写一次。本票定写到哪里、Web 从哪里读。
- **作业执行器的最外层**：这里是"每个错误只报告一次"的三处边界之一。worker 要保留最后一次进度，因为工具突然退出时，平台要靠它补诊断，写明"死在哪一步"。
- **运行日志**：Web 和 worker 各写一个文件（`web.log`、`worker.log`），保留 30 天，同时输出到 stderr。如果用 systemd 托管，要和 journald 配合好，不要存两份、两套保留期。

**完成标准**：以上各项都有结论，至少走过两个场景且结果明确：worker 跑到一半整机断电；两个用户同时提交改同一个数据集的作业。结论写成 ADR；作业、worker、写锁等术语写进 `GLOSSARY.md`。

各项结论落在这些地方：
- **决策和取舍**：[ADR 0005 作业由独立的 worker 执行，worker 是导航层唯一的写者](../../../docs/adr/0005-作业由独立worker执行且是导航层唯一写者.md)。
- **术语**：作业、作业状态、作业记录、Worker、导航层写锁、取消、中断、恢复方式，已写进 `GLOSSARY.md`。
- **环境事实**：
  - 本机 `loginctl show-user shawn` 显示 `Linger=yes`。
  - GPU 是两张 RTX 3090，各 24 GB，驱动 595.91（`nvidia-smi`），ffmpeg 带 `h264_nvenc`、`hevc_nvenc`。3090 的 NVENC 编不了 AV1。
  - mcap2lerobot 不能续跑，输出目录已存在时拒绝运行，加 `--force` 才会删掉重新生成（`src/convert.rs`）。它的 `configs/r1lite.toml` 现在配的是 `vcodec = "hevc_nvenc"`。

### 结论

- **开图时的矛盾**：选单独的 worker，不在 Web 进程里开后台线程。
- **Web 和 worker 分工**：
  - 几秒内做完、只读写数据库的事，Web 当场做，例如浏览、登记、账号管理、看日志。
  - 耗时的、要调外部工具的、要写导航层的事，做成作业交给 worker。Web 只提交作业、请求取消、读进度。
  - worker 执行所有作业，是唯一写导航层的进程。它还负责中断恢复、写心跳，以及到点提交定时作业（提交人记为"系统"）。
- **worker 形态**：
  - Web 和 worker 各是一个 systemd 用户服务，开机自启，崩溃自动重启。
  - 两者只通过 SQLite 里的作业表联系。
  - worker 用状态目录里的排他文件锁保证只有一个实例在跑。运维命令里要碰导航层的，在 worker 运行时拒绝执行。
  - 在 systemd 下运行时，日志只写文件，不往 stderr 输出，journald 只收程序启动阶段的崩溃输出。
- **作业状态**：排队中、运行中、正在取消、已完成、已取消、已中断。
  - 只有已完成的作业有作业结果，共四种，由计数算出。网页上显示的结局因此是六种：成功、带警告成功、部分成功、失败、已取消、已中断。
  - 已取消和已中断也显示做到了哪一阶段、多少条目。
- **中断后怎么恢复**：每类作业声明一种恢复方式。
  - 下载：续跑。
  - 重新扫描：重跑。
  - 转换：标记中断，等人重新提交。
  - 写导航层的作业：标记中断，先跑完恢复流程再放行别的写操作。
  - 排队中的作业重启后照常排队。升级时重启 worker 也按中断处理，"等作业跑完再停"的功能 v1 不做。
- **取消**：
  - 任何登录账号都能取消任何作业，取消人记进操作日志。
  - 排队中的作业，取消后立刻变成已取消。运行中的作业，先请工具停下，约 10 秒后还没停就强制结束。正在写导航层的那一步不打断。
  - 取消不清理产物，所以不另做暂停功能。
  - 重新提交会新建一个作业，注明"重新提交自 #N"，提交人记成点按钮的人。
- **导航层写锁**：
  - 整个导航层一把锁，放在 worker 进程里。作业只在写导航层的那一步持有它，重新扫描也要拿。
  - 写导航层的作业提交时记下预览时看到的状态，执行前核对，对不上就以"冲突"失败，一行都不写。
  - 提交时如果已有排队的作业要改同一个数据集，网页先给提醒。
  - worker 崩溃时锁随进程释放。在终端里手工改导航层不受这把锁约束，只能靠一致性面板事后发现。
- **并发与 GPU**：
  - 每类作业有各自的并发上限，默认 1，可以在配置里改。不同类型的作业之间可以并行。
  - GPU 由 worker 分配：两张卡算两个名额，一张卡同一时间只给一个作业。转换默认同时只跑 1 个，M4 实测后再调。
  - GPU 用不了时直接以"外部失败"报错，不自动改用 CPU。
- **存储根在线检查**：作业开跑前，先检查要写的存储根确实挂载着，不在线就以"外部失败"结束，什么都不写。怎么判断"在线"，由「[数据集板块的数据契约](11-dataset-contract.md)」定。
- **进度**：worker 把进度写进数据库里的作业记录，每秒最多一次，并保留最后一次进度，供工具突然退出时补诊断。Web 从数据库读进度；作业日志的最后几十行直接从日志文件里读。
- **作业日志与作业记录**：
  - 作业日志是平台状态目录里的文本文件，路径形如 `logs/<作业类型>/2026-10-22_143015_123.log`，和 `web.log`、`worker.log` 放在同一个 `logs/` 下。导航层里不放日志。
  - 作业日志保留 30 天，管理员可调。
  - 作业记录存在数据库里，永久保留。日志删除后，详情页仍能看到结果、计数、耗时、产物位置和工具版本。
  - 作业日志要不要备份，由「[备份方案](17-backup.md)」定。
- **提交人**：负责人的初步意见确认。作业记录同时存提交人的内部编号和名字，账号删除后显示为"张三（已删除）"，作业记录不会挡着账号删除。
- **里程碑**：worker 进程、作业表、心跳、中断恢复、导航层写锁，加一个示例作业，都在 M0 交付。M1 的建链、改指向和重新扫描从第一天起就是作业。

### 场景一：worker 跑到一半时整机断电

1. 断电前，数据库里有最后一次进度，最多晚 1 秒；作业日志也写到了最后一行。
2. 来电开机后，systemd 启动 Web 和 worker，不用有人登录。
3. worker 拿到单实例锁，发现上一个实例留下了"运行中"的作业，于是判为中断：在作业日志里追加一段，写明中断在哪个阶段、最后进度是多少。
4. 然后按恢复方式处理：
   - **下载**：重新排队，用 aria2 `-c` 接着已下载的部分继续。
   - **重新扫描**：从头重跑。
   - **转换**：变成"已中断"，半成品留在原处。有人点"重新提交"后，由新作业重新生成。半成品怎么清理，和「工具清单与转换血缘」的暂存区方案一起定。
   - **改指向**：变成"已中断"，先跑「[软链接接口规则](12-link-rules.md)」定的恢复流程，跑完才放行别的写操作。
5. 如果开机后 NAS 没挂上，续跑的下载在存储根在线检查这一步就会失败，以"外部失败"结束，不会写进系统盘上的空挂载点。

### 场景二：两个用户同时提交改同一个数据集的作业

1. 张三和李四都在 10:00 预览了数据集 X，看到的状态是 S0。两人先后提交了作业 A 和 B。李四提交时，网页提醒"已有排队中的作业 #A 要改数据集 X"。
2. worker 先执行 A：拿锁，核对 X 仍是 S0，写入，X 变为 S1，释放锁。
3. 再执行 B：拿锁，核对时发现 X 已经是 S1，不是 S0。B 一行都不写，以"冲突"失败，提示"数据集 X 在你预览之后被作业 #A（张三）改过，请重新预览"。
4. 如果两人改的是不同的数据集，两个作业先后都会成功。

### 风险

- **升级时会打断转换**：升级要重启 worker，正在跑的转换会变成已中断，要重新跑。在加上"等作业跑完再停"的功能之前，升级前要先看一眼。
- **建链要多等一会儿**：建一条链接要经过排队，正常 1–2 秒。批量改指向持锁时间较长时，单条建链要等它写完。M1 用真实规模（智元迁移的批量换前缀）实测一次。
- **GPU 显存被占满**：有人在同一张卡上训练、把显存占满时，NVENC 编码会失败。
