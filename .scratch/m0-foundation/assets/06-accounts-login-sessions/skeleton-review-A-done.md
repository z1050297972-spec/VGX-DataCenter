## A 阻塞问题（必须在骨架阶段改）

**A1 路由的 Raises 和 Time Semantics 是同一份模板，有好几条不适用，违反 3.2，也推不出 7.1 要的测试**
- `src/rdp/api/accounts.py:57、90、121、161、200、234、274、315、356、394`：十个路由的 Raises 基本逐字相同。
  - `who_am_i`（:121）写了 `PasswordChangeRequiredError`，但 `/api/auth/me` 本来就在强制改密允许集合里；还写了 Origin 403，可 GET 不查 Origin；还写了"字段、目标编号、口令不合格 422"，这个接口没有任何输入。
  - `logout`（:90）也写了 `PasswordChangeRequiredError`，登出同样在允许集合里。
  - `login`（:57）写了"管理员操作角色不足 403"，还写了"重复登录名 409"。
  - `list_accounts`（:200）写了"重复登录名 409"和"口令不合格"。
- 改法：每个路由只列这个路由真会抛的异常和触发条件。Time Semantics 里"提交完成后才发送响应"对只读的 GET 不成立，也要分开写。
- `src/rdp/accounts/service.py`：13 个方法的 Time Semantics 是同一段 6 行文字（:91–95、:124–128、:222–227 等）。只读的 `list_accounts` 也写了"限流窗口起点""写锁单次等待""Argon2"。`list_accounts` 的 Raises（:211）写"写事务内重新检查"，Side Effects（:220）却写"只读事务"，两处矛盾。每个方法都要按实际行为重写。

**A2 时钟回拨的语义自相矛盾，而且会让登录出现长时间 409**
- `service.py` 每段 Time Semantics（如 :93–94）同时写了两句："now 早于所用行的创建时刻或限流窗口起点时 ConflictError" 和 "活动和修改时间取 max(已存时刻, now)，不把负时长当过期"。
- 按前一句实现：系统时钟被 NTP 往回拨几秒，0 号全局桶的 `window_started_at` 就会让所有登录返回 409，最长接近一分钟；在回拨区间里新建的会话也会 409。
- 测试 `tests/test_accounts.py:227`、`:536` 把这个 409 写成了期望。
- 建议：统一成"负时长按 0 处理（clamp），不抛 ConflictError"，只保留 max 规则；Raises 里删掉"时钟回拨"（`account_auth.py:95、179` 和各路由 Raises 里都有）。

**A3 Origin 检查、401、405 的先后没写清，和验收 5、S1 冲突**
- `account_auth.py:100` 写"非 GET/HEAD/OPTIONS 先校验 Origin"，`:61` 又写"健康路径的错误方法直接按 S1 返回 405"。`tests/test_account_api.py:146–147` 期望"匿名 POST /api/health 返回 405"。
- 测试客户端默认不带 Origin。按"先查 Origin"实现会得到 403，按"先 405"则 Origin 规则对这条路径就开了口子。
- 同样的问题：验收 5"没登录调任何业务接口返回 401"，对不带 Origin 的匿名写请求，按现在的设计会得到 403。
- 改法：在 `enforce_api_access` 的契约里写一张决策顺序表，推荐顺序：
  1. 不安全方法查 Origin → 403
  2. 白名单（按方法和已匹配的路由，不按原始字符串）
  3. 认证 → 401
  4. 强制改密 → 403
  5. 兜底 404/405
- 然后把 S1 测试和验收 5 的写请求测试改成带正确 Origin，另加一条"不带 Origin 时 403 优先"的测试。

**A4 Argon2 没有并发上限，有内存耗尽的风险；"每分钟 60 次全局预算"挡不住这个**
- argon2-cffi 的默认参数是每次 64 MiB 内存、并行度 4。同步路由在 FastAPI 线程池里跑（默认约 40 个线程）。同一秒涌进来的 40 次登录（未知名字也会做 dummy verify）可以同时占用约 2.5 GiB。
- 全局预算按分钟计数，不限同一时刻的并发，所以限不住这个峰值。
- 工单的风险一节按"几十 MB"估算，没考虑并发。
- 改法：在 `policy.py` 加一个具名常量，例如 `ARGON2_MAX_CONCURRENCY = 2`，限制进程内同时做 `PasswordCodec.verify/hash` 的数量（入口层用 semaphore 实现，或者由 PasswordCodec 自带）。还要定好排队等多久、超时返回什么（建议 429 加 Retry-After，或者沿用 ConflictError），并补测试。这一条也是 C 里建议取消全局预算的前提。

**A5 有工单之外、当前没有调用方的公开函数（3.3.2、2.9）**
- `service.py:472` 的 `clear_expired_sessions`，契约自己写着"供第 9 张调用，本票不启动调度器"。
- 现在已经有"访问时删过期会话"和"每账号最多 32 个会话"两道上界，存储不会无限增长。
- 建议删掉这个函数，连同 `tests/test_accounts.py:482–497` 的 4 条测试，留到第 9 张再加。如果要保留，需要负责人点头。

**A6 测试清单的缺口（7.1）**
1. 401 清 cookie 只测了 `handle_error` 一条路径。`test_error_contract_both_paths`（`test_account_api.py:216`）只断言了 429，ErrorBoundary 那条出口的 401 清 cookie 没测。
2. 认证守卫在所有业务路由上都会跑，但 `sanitize_account_error` 的契约只说"账号请求"（`errors.py` 新增的两个函数，`handle_error` 的 06 提案）。要写明"账号请求"包括任何路由在认证阶段抛出的异常，并补一条测试：非账号路由在认证时抛出含秘密的未知异常，报错表里没有原文。
3. 管理员停用、删除、降级自己（前提是还有别的管理员），当前会话下一次请求 401，没有测试。
4. 验收 11"成员那边立刻被踢回"：前端契约写的是"不轮询"，空闲页面不会发请求。需要在契约里写明靠 TanStack Query 的 `refetchOnWindowFocus`（切回窗口时重新查 /me）触发，并加一条 Vitest。否则演示时成员窗口不会自己跳回登录页。
5. `tests/test_api_errors.py:168` 原来用 `dict(status=403)` 验证"INPUT 不接受的状态"。现在 403 合法了，这个用例只是因为标题对不上才失败，原来要测的东西已经测不到。应换成 `status=418`（标题也配对），恢复"状态码表外的状态被拒绝"这条断言。

## B 建议（非阻塞）

- **B1 多余的常量时间比较，可以删**
  - `session_digest` 和 `authenticate` 要求查库后再用 `hmac.compare_digest` 复核（`security.py:289`、`service.py:118`）。这是按主键查一个高熵令牌的摘要，复核没有安全收益。
  - 运维两次口令的常量时间比较（`ops/accounts.py:45`）也一样：是操作者自己在本地比自己的两次输入。
  - 删掉这两处，连同对应测试 `test_accounts.py:102`、`test_account_ops.py:12、47`。
- **B2 改角色撤销会话是多余的**（`service.py:291`）：`authenticate` 每次请求都重读角色，权限本来就立即生效。撤销会话只会让被提升为管理员的成员也被踢出去。建议去掉，或者只在降级时撤销。
- **B3 会话触摸应当尽力而为**：`authenticate` 在 60 秒触摸时拿不到写锁（worker 正在写库），按现在的契约整个请求 409，GET 也会失败。建议改成：会话未过期时，触摸因 BUSY 失败就跳过、照常放行；只有"删除过期会话"这一步失败时才不放行（失败时关闭）。
- **B4 cookie 续期频率**：现在每个认证成功的响应都带 Set-Cookie 重发令牌（`account_auth.py:22`、`:101`）。可以改成只在真正触摸的那次（每 60 秒）续 Max-Age，减少令牌在响应头里出现的次数，语义不变。
- **B5 关文档页放到 create_app 里**：`/docs`、`/redoc`、`/openapi.json` 不在 `/api` 下，全局守卫管不到。契约把关闭它们放在 `install_account_security` 里（`account_auth.py:70`），而这个函数只在有数据库时安装。建议在 `create_app` 里无条件 `docs_url=None, redoc_url=None, openapi_url=None`，离线导出用 `app.openapi()`。
- **B6 白名单按已匹配的路由判断**：建议用 `scope["route"]` 的路径模板加方法，不用原始路径字符串。现在的写法失败时是关闭的（多出来的路径一律要认证），但按路由判断能和 S1 的 Allow 计算共用同一个匹配结果。
- **B7 登录时撤销旧会话**：请求已经带着另一个有效会话来登录时，可以顺手撤销旧会话，免得留下 7 天的孤儿会话。非必须。
- **B8 运维函数的时刻**：`now` 由调用方在交互输入前传入，操作者输得慢，记录的时刻就早于实际写入。建议改成传时钟回调，读完口令后再取时刻。
- **B9 编号用十进制文本是过度设计**：SQLite 自增编号在本项目不可能超过 2^53。这个做法让前端和测试都多一层字符串编号。可以考虑改回整数，加上限 2^53−1。非必须，改动面较大，可以交负责人定。
- **B10 规范表同步**：`diagnostics.py:58` 的注释写"规范表由 Claude 在骨架关卡后同步"。按 6.2"先改表再改代码"，契约提交前，Claude 要先把 401/403/429（429 带 Retry-After）写进 CODING_STANDARDS 6.2 的表和运维手册速查，并按 S1 改 404/405 两行。
- **B11 超出工单字面的扩展**（都不算违规，但要让负责人知道）：
  - 新建账号也强制首次改密（G3 只说了重置后）
  - 新旧口令不得相同
  - 每账号最多 32 个会话
  - 账号列表分页
  - Argon2 存量编码的成本上限
  - 运维重置后强制改密

  第一条见 D2，其余我认为可以保留。

## D 建议交负责人拍板的问题（最多 3 个）

1. **登录防护保留哪几层？**
   - 方案甲（推荐）：G2 按账号计数 + 未知名字只做 dummy verify 并返回 401（不计数）+ 进程内 Argon2 并发上限 2。取消"全平台每分钟 60 次"和 1024 个未知桶。代价是：攻击者能通过"输错 5 次后是否返回 429"判断某个登录名是否存在，内部工具可以接受。
   - 方案乙：在甲的基础上，再加按客户端 IP 的登录速率上限。
   - 方案丙：照 Codex 的方案。风险是任何一台机器都能让全员无法登录。
   - 推荐：甲。
2. **管理员新建的账号，首次登录是否也必须先改口令？**（G3 原文只说了重置之后）推荐：是。初始口令是管理员设的，和重置后的处境一样。演示时成员登录后会先进改密页，演示脚本要相应调整。
3. **写请求不带 Origin 一律 403（包括以后的命令行或脚本调用 API）是否接受？** 推荐：接受。命令行脚本要自己带正确的 Origin 头，这条写进使用手册。M5 上 HTTPS 时再评估要不要改成按 Host 白名单判断。
