评审第 2 轮（一键脚本这一段，本段第 2/3 轮）。验收 9 演练（`assets/11-ops-entry-systemd/drill9-run.log`，提交 `9d90249`，临时 HOME、真实联网）失败：Node 下载、校验、安装都成功了，uv 和 pnpm 没装上。执行线逐项查实了原因，全是真实环境才暴露的问题。

**1. GitHub API 的 TLS 握手偶发失败，脚本没有重试**
第一次运行时，uv 的元数据请求失败，报"官方文件下载失败"。执行线连续 3 次请求同一个地址，第 1 次是 `curl: (35) TLS connect error: ... unexpected eof while reading`，后 2 次是 200。`curl --retry` 不会重试连接或 TLS 错误。
- 修法：
  - 对连接和 TLS 类失败要重试，例如在有限次数内加 `--retry-all-errors`，或者在 `_fetch_official` 里自己循环。
  - 重试的总时间仍受顶部的预算限制。
  - 4xx 不能被当成可以重试的错误一直重试下去。如果用 `--retry-all-errors`，要说明它对 4xx 的影响，或者先判断状态码再决定。

**2. GitHub API 未认证限流（403）**
同一个出口 IP 每小时只有 60 次，本机经代理出口和别人共用这个 IP。实测返回：
`{"message":"API rate limit exceeded for 89.116.88.34. ..."}`
- 修法：
  - 403 或 429 并且响应带有 rate limit 字样时，给出明确提示：已被 GitHub 限流，几点可以重试（读响应头 `X-RateLimit-Reset`），或者手动安装。不能笼统地报"下载失败"。
  - 不新增认证参数。
  - 不能因为限流就跳过校验。

**3. pnpm 11 的发布包不是独立的二进制文件**
v11.22.0 的 asset 实际名字是 `pnpm-linux-x64.tar.gz`、`pnpm-linux-arm64.tar.gz`，还有 `-musl` 变体，不是 `pnpm-linux-x64`。按旧名字去下载，会得到 404。
- 修法：
  - asset 名改成 `pnpm-linux-<架构>.tar.gz`，只选 glibc 版，不选 musl。
  - 走和 uv 一样的归档检查，然后解包。
  - 解包后，在解包根目录或者往下一层里定位名为 `pnpm` 的可执行文件，用 `--version` 自检。
  - 执行线没有下载这个包，不知道包里的确切结构。所以定位逻辑不要写死成一种结构；如果结构不符合预期，就明确报错。
  - 用测试构造两种结构：根目录直接放 `pnpm`，和 `<目录>/pnpm`。
  - 帮助文本里 pnpm 那一行要同步改：从"独立可执行文件"改成"官方 tar.gz"。这是事实更正，在第 3 块列出。

**4. uv 版本自检的字符串不对**
真实输出是 `uv 0.13.5 (x86_64-unknown-linux-gnu)`。脚本要求整行等于 `uv 0.13.5`，所以第二次运行（下载成功以后）报"工具版本自检失败"。`ensure_user_toolchain` 里判断"已有固定版本"用的是同一种比较，结果 PATH 上已经有正确版本的 uv，也会被当成没有。
- 修法：
  - 解析出版本号再比较：输出以 `uv 0.13.5` 开头，后面是行尾或空格。
  - node、pnpm 的判断也按同样的规则检查一遍。
  - 测试里假 uv 的输出要改成真实格式。

**5. 没有终端、也没有配置时，先下载工具，最后才报错退出**
演练第 7 步：`--yes --no-systemd < /dev/null`，没有配置文件。脚本先下载了 Node、uv，最后才因为缺配置退出，而且退出码不是 2。
- 修法：
  - "没有终端、配置又缺失"这个条件很便宜就能判断，要放到下载工具之前，直接以 2 退出。帮助里写的"非交互必须已有有效配置"就是这个意思。
  - 管理员条件的检查依赖校验环境，可以照旧放在后面。
