# 工具和平台用同一套诊断，工具经单独的通道上报

Status: accepted（2026-10-22，决策票「可观测性与报错规范」）

平台调用的外部工具（mcap2lerobot，以及调用 lerobot 的 Python 工具）在开发上是另一层。负责人的要求是"使用者看到的还是一个系统"。所以工具内部的报错和进度，按平台的诊断格式上报给平台。诊断格式分五段：对象、规则、实际与期望、后果、下一步。

平台收到工具的诊断后，和自己产生的诊断同样对待：同样计数，同样参与作业结果的计算，在作业日志和网页上的写法也一样，只多标一个来源，说明问题该去哪一层修。

具体做法：
- **上报通道**：平台启动工具时，另开一条上报通道（管道），用环境变量告诉工具。工具每行写一个 JSON 事件，共五种：进度、诊断、条目结果、致命错误、结束摘要。协议带版本号。
- **原始输出**：stdout、stderr 仍然原样完整地记进作业日志，供开发者查看。
- **工具没上报就退出**（panic、被 OOM 杀掉）：平台根据退出码或信号、stderr 的最后几行、最后一次进度，补一条"外部失败"诊断。
- **上报和退出码对不上**：按更坏的情况算，再记一条诊断说明哪里对不上。
- **接入范围**：工具库里的工具都要接入。自己的工具加一个上报模式；改不了的第三方脚本配一个包装脚本。还没接入的工具可以试跑，但网页上标明"只有原始输出和退出码"。

## Considered Options

- **只记录工具的原始输出，按退出码定成败**：这是走票时的原推荐，被负责人否决。这样做有三个问题：
  - 使用者会看到两套报错。
  - 网页拿不到工具的进度：mcap2lerobot 不在终端里运行时，会把进度条隐藏。
  - 作业结果分不出"带警告成功"和"部分成功"。
- **解析工具的 stdout**：放弃。这样做有两个问题：
  - 工具平时打印的文字可能被误认成事件。
  - 平台要跟着每个工具的输出格式改。

  单独开一条通道，工具在终端里直接运行时的行为保持不变，进度条照常显示。

## Consequences

- mcap2lerobot 要加一个上报模式，在 M4 接入转换时做。
- 工具上报的内容对平台来说是不受信任的输入，因此：
  - 逐行校验，不合格的行原样保留并记一条警告，不能让作业执行器崩溃。
  - 同一类诊断很多时，平台同样按"总数 + 前几条样例"聚合。
- 工具清单要声明支持的上报协议版本，包装脚本放在哪里，由「工具清单与转换血缘」定。环境变量名、管道编号等通道细节在 M4 落地。
- 工具必须能不经交互运行，例如 mcap2lerobot 要加 `--yes`。
- 工具突然退出时，平台只能给出比正常上报粗的信息。
