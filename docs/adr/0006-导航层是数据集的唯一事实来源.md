# 导航层是数据集的唯一事实来源，平台不改它的格式

Status: accepted（2026-10-22，决策票「数据集板块的数据契约」）

平台关于数据集的一切，都以 `/mnt/datasets` 导航层为准：两个视图的目录、链接，以及每个入口里的三个 JSON。数据库里只放数据集索引，可以整个删掉，重新扫描就能恢复。这样定的原因有三条：负责人要求保留现有的结构和在终端里的使用习惯；平台出了问题，导航层照样能用；不会出现"数据库和磁盘两套真相"。

现有的 JSON 有不少冗余，见 Consequences。平台不改它的格式，而是在读写规则里把冗余消化掉。导航层现在没有备份，平台也还没经过验证，这时一次性改写 210 份事实来源，是风险最大的做法。

## 具体做法

- **身份**：
  - `dataset_id` 一经分配就不改、不复用，数据集改名也不变。平台自己的对象（作业记录、血缘、采集任务）只用它来引用数据集。
  - 数据块的 `source_id` 现在等于 `sha256(original_path)` 的前 12 位，但平台把它当作已分配的编号：不重算，改指向时也不变。
- **两个视图**：
  - 按任务视图里，每个数据集恰好有一个入口，代表完整的数据集。这个入口里的三个 JSON 是规范副本。
  - 按格式视图里的入口，代表数据集在某种格式下可以直接使用的那一部分。一个数据集在这里可以有零到多个入口。
  - 各入口的内容不一致时，以规范副本为准。平台写入时，由规范副本生成按格式入口里的各份。
- **格式目录**：`按格式/` 下的第一层目录，靠一张登记表对应到格式，并记下有没有版本层。`tar、tar.gz（含分卷）` 这个目录名不改，它对应的格式是 `archives`。
- **读取契约**：
  - 平台只依赖少数字段，字段清单见决策票的 Answer。其余字段原样展示，不认识的字段原样保留。
  - 缺少 `schema_version` 当作 1；省略 `version` 等同于 `null`。
  - 能推出来的字段（`entry_path`、`view`/`format`/`version`）由平台按入口的位置自己算，文件里存的值只用来核对。
  - `original_path` 记的是首次登记时的位置，永远不改；`direct_path` 是现在的位置，随改指向更新。
  - 14 项的 Markdown 不解析。筛选用的 `robot_type`、`fps`，从数据自带的 `meta/info.json` 里读。
- **存储根**：
  - 平台登记每个存放真实数据的挂载点，记下路径和挂载源：ext4 记文件系统 UUID，NAS 记"服务器:导出路径"。
  - **在线**的意思是：这个路径此刻是挂载点，并且挂载源和登记的一致。判断只读挂载表，不往数据盘上放标记文件。作业访问存储根时带超时，超时就按离线处理。
  - 存储根离线时，数据集照常显示，链接标为"存储根离线"，不算断链。
  - 存储根分只读和可写两种，默认只读。两块数据盘只读；NAS 上单独划一个平台区，是可写的。下载、转换、暂存、备份的产物都写在平台区，而且只新建，已经入库的数据不再修改。`AGENTS.md` 的硬性规则 1 据此改成一条例外。
- **索引与扫描**：
  - 重新扫描是一种作业，在这些时候提交：手动、worker 启动时、每 10 分钟一次。平台自己的写入作业，在同一个作业里顺带更新受影响数据集的索引。不监听文件系统。
  - 扫描分两段。第一段持有导航层写锁，只读导航层，实测约 0.2 秒；放锁之后，第二段再检查数据盘，约 8 秒。
  - 大小由单独的"统计大小"作业来算（每晚、手动、写入后），不拿写锁，页面上显示统计时间。
  - 一致性面板展示的就是扫描时的发现，分四组、两级，只报告，不修复。
- **Web 的边界**（补充 ADR 0005）：Web 可以只读导航层本身，例如详情页的三个 JSON 直接读文件；但不访问存储根。凡是要碰数据盘或 NAS 的检查，都放在 worker 的作业里做，这样 NAS 卡死时网页不会跟着卡住。

## Considered Options

- **以数据库为事实来源，导航层由平台生成**：放弃。这要放弃现在的结构和终端里的习惯；平台一出问题，导航层就不可信了；还会出现两套真相。
- **一次性把 210 份 JSON 改成没有冗余的新格式**（例如路径改成相对于存储根、不再存能推出来的字段、两个视图只存一份）：这次不做。导航层没有备份，平台也还没经过验证，这是对事实来源风险最大的一种改动。现有的冗余由唯一的写者在规则里消化就够了。等平台当了一段时间唯一写者之后，另开一次再评估。
- **从 14 项的 Markdown 里解析机器人型号和 FPS**：放弃。35 份里只有 29 份是固定写法，另外 6 份是自由文字。`meta/info.json` 是结构化的，491 份全部读完不到 1 秒。
- **实时计算大小**：做不到。agibot_world_alpha 有 753 万个文件和目录，冷缓存下 `du` 要约 8 分钟。
- **监听文件系统（inotify）**：放弃。它只能发现导航层里的改动，发现不了数据盘上删目录这类变化。全量扫描一次只要 8.5 秒，定时扫就够了。
- **在数据盘上放标记文件来判断在线**：放弃。数据盘只读。
- **把 `tar、tar.gz（含分卷）` 改名为 `archives`**：放弃，保留现有习惯，靠登记表对应。

## Consequences

- **改指向的改写范围很大**。数据盘的绝对路径在三种 JSON 里都有：两个视图合计，`原始路径.json` 里有 7,634 处，`子任务.json` 里有 16,908 处，`数据集信息.json` 里有 608 处，后者在 Markdown 正文里。改指向按前缀替换，三种 JSON 全部覆盖，具体规则由「软链接接口规则」定。
- **当初生成这些 JSON 的程序以后不再运行**。它要是再跑一次，会覆盖平台写入的内容，还会按新路径重算 `source_id`。
- **手工修改只能事后发现**。在终端里改导航层仍然允许，但只能靠一致性面板事后发现，最多晚 10 分钟。
- **`original_path` 会指向不存在的位置**。迁移之后它指向的位置就没了，这是有意为之，一致性面板不检查它。
- **NAS 挂着但不响应时，挂载表仍显示已挂载**，只能靠作业访问时的超时发现。超时设多长、卡住的读取能不能中止，要等「NAS 接入事实」测出挂载方式后再定。
- **14 项会继续过期**。它们是 10-12 的快照。页面上要标明记录日期，并把平台算出来的值并排显示。

## 修订（2026-10-29，依据「软链接接口规则」12 的 1A）

12 的 1A（2026-10-28 已决）定了写导航层的规则，写在 ADR 0009「导航层的写入与回滚」。本节补充本 ADR，原文不改；和原文不一致的地方以本节为准。

- **改指向的规则**：Consequences 第一条里"具体规则由「软链接接口规则」定"，改为引用 12 的 L17、L18（ADR 0009）：
  - **边界**（L17）：新旧前缀都是不带结尾 `/` 的绝对路径。前缀后面必须紧跟 `/`，或者到了 JSON 字符串的结尾；Markdown 正文里，"结尾"还包括空白、`` ` ``、引号、`)`、`]`、`>` 和中文标点（，。；：）」）。
  - **范围**（L18）：三种 JSON（不含 `来源.json`）里所有字符串值中符合边界的都替换，只有 `original_path` 例外。预览按字段分组给出数量，Markdown 和 `notes` 每一处单独列出。`来源.json` 只追加，不改写。
- **alpha 的按格式入口会少 3 个数据块**（简报 C7）：agibot_world_alpha 的规范副本里有 3 个链接够不着的数据块（10-17 被删掉的转换副本），`entry_path` 是绝对路径；它的按格式那份现在也收着这 3 个。按 L9，它们只留在规范副本里，按格式入口不收录。所以平台第一次写 alpha 时，按格式那份会少这 3 个数据块，预览里会列出。这不违背本 ADR：按格式入口本来就是由规范副本生成的（"两个视图"一条），少掉的是"该格式下不能直接使用"的部分。
- **`version` 和 `schema_version` 的读和写**（L10）：

  | | 读 | 写 |
  |---|---|---|
  | 省略的 `version` | 等同于 `null`（原文） | 推导字段（`view`/`format`/`version`）整组重新生成，显式写出 `version: null` |
  | `数据集信息.json` 缺少的 `schema_version` | 当作 1（原文） | 不补。这份文件从来没有 `schema_version`，补上等于改格式 |

  读的规则不变；写出 `version: null` 是整组重新生成推导字段的自然结果，不算改格式。

## 修订（2026-10-30，M1.5 第 01 张：原文件只读查看器）

负责人："用户通过接口看不到具体的视频、info.json等原文件"；问答选定"写导航层，不动数据盘"，查看器只读。

- **例外**：Web 进程里**只有原文件查看器这一个模块**可以读存储根，而且只读。它用 M0 第 10 张的超时访问（有访问槽上限）；文件和目录都带 O_NOATIME 打开，EPERM 时退回普通读取；路径 realpath 之后必须落在该数据集已登记链接的目标之内，不接受 `..`、绝对路径，也不接受跳出存储根的软链接；超过 32 MiB 的文本不读，视频按 HTTP Range 分段返回。
- 第 03 张"数据集接口不访问存储根"的 import-linter 契约对其余浏览模块照旧有效，查看器模块是唯一的豁免。
- 数据盘只读的硬规则不变：查看器没有任何写、删、改名的接口。
- 演练实测（2026-10-30）：在真实数据盘上浏览目录、读 meta/info.json、用 Range 播放 71 分钟的 AV1 视频并拖动进度，两块数据盘的写入扇区数不变。

## 修订（2026-11-06，M1.5 第 15 张：筛选统一以数据集信息为准）

负责人："五个筛选条件全部按照数据集信息.json为准，我们再额外做一个比对的功能……提醒使用者在正式使用该数据集前，哪些参数要更改"；"型号标签这个字段无所谓"。本节补充本 ADR，原文不改；和原文不一致的地方以本节为准。

- **筛选的依据**："具体做法"里"筛选用的 `robot_type`、`fps`，从数据自带的 `meta/info.json` 里读"作废。型号、FPS、数据来源、场景、任务五个筛选，全部取规范副本 `数据集信息.json` 的顶层字段：`robot_model`、`fps`、`data_origin`、`scene`、`tasks`。14 项 Markdown 仍然不解析；唯一例外是上线回填时，第 8 项（FPS）是一个正整数（后面可以跟一个括号说明）就拿来做顶层 `fps` 的初始值，只用这一次。
- **info.json 的用途**：扫描照旧读 `meta/info.json` 的 `robot_type`、`fps`，只用于两件事：一次性回填顶层 `fps` 时作为第 8 项取不到数字时的后备（只新增，不改已有内容），以及和顶层字段比对、在一致性面板里给提示级发现。它不再出现在任何筛选里。
- **型号只有一个概念**：`robot_model`。"型号标签"不再作为筛选；M3 不建平台型号表。
- **理由**：人工标注和平台筛选用同一份数据，所有格式都能标注（info.json 只有 LeRobot 有）；数据盘照旧只读。代价是筛选值可能和原数据不一致，所以要有比对，页面上也要说明筛选以导航层为准。
