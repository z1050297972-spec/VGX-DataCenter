# 导航层的写入与回滚：日志先行，中断一律回滚

Status: accepted（2026-10-28，决策票「软链接接口规则」的 1A；NAS 部分待它的 1B）

平台写导航层（建链、新增数据集、改指向、改 `来源.json`、撤回），改的是数据集唯一的事实来源（ADR 0006），而导航层现在没有备份。一次改指向要在 6 个文件里改约 6,900 处，写到一半断电，导航层就会一半新、一半旧，而且没人知道做到了哪一步。所以我们规定：每次写之前，先在平台状态目录里落一份写入日志，记下每一步要改什么、改之前是什么；写的时候逐个文件原子替换；写失败或中断，一律按日志退回改之前的样子，不往下补完。每次改动另存一份永久的变更记录，操作日志清掉以后照样能撤回。

本 ADR 是 ADR 0005（worker 是导航层唯一的写者）在"怎么写"这一面的展开。每条规则的选项、后果和依据，见 12 的 Answer 和《决策简报：12、17、04》第 1 节（L1–L19）。规则的细节和例子写在 `docs/manual/导航层手册.md` 第 9 节。

## 具体做法

### 入口和阶段

- **Web 提交，worker 执行**：0003 4.4 写的"同一组核心函数，套上 CLI 命令和 Web 表单两个入口"，已经被取代。「交互形态与前端路线」取消了 CLI，ADR 0005 规定写导航层一律是作业。4.4 的流程"校验 → 预览 → 确认 → 写链接 → 写回清单 → 重新索引 → 记操作日志"，变成一个写导航层作业内部的几个阶段（简报 C9）。
- **一个作业的阶段**：
  1. 校验并生成预览，同时记下预览状态（L12）。用户在网页上看过预览、确认后提交执行。
  2. 拿到导航层写锁，重新算一次预览状态，和记下的比对。对不上就以"冲突"失败，一行都不写（ADR 0005）。
  3. 在写锁下落写入日志，逐个文件写入（L13）。
  4. 在同一个作业里更新受影响数据集的索引，再提交一次统计大小（ADR 0006）。
  5. 写变更记录（L16），记操作日志（L15）。
- **预览由谁算，待定**：L1、L3、L19 的校验要访问存储根，而 Web 不访问存储根（ADR 0006）。预览放在哪里算，1A 没有定，待 M1 第 07 张骨架关卡定。
- **只写两处**：写导航层的作业只写导航层和平台状态目录，不改链接目标里的任何东西（0003 4.4 第五条）。链接目标可以在只读存储根下，链接只是指向它。

### 写入规则

- **建链**（L1–L4）：
  - 校验保留 0003 4.4 的五条，再加四条：目标 `realpath` 后落在已登记的存储根下；目标不在导航层内部；链接名不含 `/`、不以 `.` 开头、不和入口里的四份 JSON 同名；目标不在 `dataset_roots` 之内时，预览里提示"将把 X 加进 `dataset_roots`"。
  - 目的路径已存在时拒绝，提示改走改指向。只有一个例外：已存在的链接指向同一目标、并且已登记在 `links[]` 里，按"已经是这样了"成功，什么都不写（场景一）。
  - `links[]` 追加一项。目标没被现有数据块覆盖时，`sources[]` 追加一个数据块，`source_id` 照现有规则算一次，之后永不重算。必要时追加 `dataset_roots`。一个链接目标对应一个数据块。
  - 链接只建在按任务入口（规范副本）。按格式入口在预览里勾选，0 到多个，由规范副本生成。
- **新增数据集**（L5、L6）：一个作业里建好按任务入口的目录、链接、三份 JSON 的骨架和 `来源.json`（数据来源必填），再加上勾选的按格式入口。`dataset_id` 在写锁下扫描 `按任务/` 和 `已移除/`，取最大编号加 1，至少两位。
- **移除数据集**（L7）：只移除导航层入口，不删数据。按任务入口和它的各按格式入口整体挪到顶层的非数据集目录 `已移除/<dataset_id>_<名称>/` 下，JSON 原样保留，可以挪回恢复。编号因此不会被重新分配。放进哪个里程碑，待负责人定（12"待落实"第 8 条）。
- **由规范副本生成按格式入口**（L8、L9）：链接以该入口自己的 `links[]` 为准；`sources[]` 取规范副本中 `direct_path` 落在本入口某个链接目标之下的数据块，`entry_path` 重新推导；`子任务.json` 只保留引用到入选数据块的任务，任务内的数据引用同样筛；`数据集信息.json` 整份复制。链接够不着的数据块只留在规范副本里，`entry_path` 保持绝对路径。
- **字段与写出格式**（L10、L11）：推导字段整组重新生成，写出 `version: null`；`数据集信息.json` 不补 `schema_version`。保持原来的键顺序，2 空格缩进，`ensure_ascii=False`，结尾换行；新键追加在末尾，不认识的键原样保留。
- **改指向**（L17–L19，本地盘之间也用）：
  - 新旧前缀都是不带结尾 `/` 的绝对路径。前缀后面必须紧跟 `/`，或者到了 JSON 字符串的结尾；Markdown 正文里，"结尾"还包括空白、`` ` ``、引号、`)`、`]`、`>` 和中文标点（，。；：）」）。
  - 三种 JSON（不含 `来源.json`）里所有字符串值中符合边界的都替换，只有 `original_path` 例外。预览按字段分组给出数量，Markdown 和 `notes` 每一处单独列出。`来源.json` 只追加，不改写。
  - 旧位置现在存在的路径，新位置必须全部存在，并且落在已登记、在线的存储根下，缺一个就整批拒绝。旧位置本来就不存在的照样替换，预览里标"旧位置原本就不存在"。

### 预览状态（L12）

- 对每个受影响的数据集（按任务入口及其全部按格式入口），记三样：入口里每份 JSON（含 `来源.json`）的 sha256、入口目录的条目名清单、每条链接的 `readlink`。新增数据集另记"目的目录不存在"和当时的最大编号。
- 重新扫描第二段提交结果时，也用这同一种状态判断数据集有没有被改过。M1 第 01 张的"数据集状态指纹"就是它。

### 写入日志与原子写（L13）

- **日志先行**：拿到写锁、核对通过以后，真正写之前，先在平台状态目录 `nav-journal/<作业编号>/` 落一份写入日志，并 fsync。日志里是这次的计划：每一步的路径、前像（旧内容或旧链接目标，原来不存在也记下）、后像的哈希。
- **逐个原子替换**：每个文件先写到同目录的临时文件，fsync，再 `rename` 替换；链接先建到临时名，再 `rename` 盖过去。
- **中途失败**：按前像逆序退回。
- 写入日志没落完整就断电时，导航层一处都还没动。

### 中断后的恢复：一律回滚（L14）

- worker 启动时，在放行任何写导航层的作业之前，读每一份还在的写入日志，逐项比对磁盘现状：
  - 等于后像的，退回前像；
  - 等于前像的，不动；
  - 两者都不是的（中间有人在终端里改过），停下，列出这些项。
- 全部退回以后，作业是"已中断"。用户重新预览后再提交；不自动补完。
- 有两者都不是的项时，作业为**恢复失败**：写导航层的作业继续被挡住，直到管理员处理完、在页面上确认。"恢复失败"在作业状态里怎么表达，见 ADR 0005 的修订。

### 操作日志、变更记录与撤回（L15、L16）

- **操作日志**只记摘要：谁、什么时候、作业编号、操作类型、涉及的数据集、改了几个文件几条链接、结果，加一个变更记录编号。前像和后像全文不进数据库。
- **变更记录**：每个写导航层的作业，把计划和前像、后像打包成状态目录里的 `nav-changes/<作业编号>.json.gz`，永久保留。
- **撤回**：提交"撤回作业 #N"。平台由 #N 的变更记录生成反向计划，照常预览、核对。当前状态不等于 #N 的后像，就以冲突失败，并列出差异。撤回本身也是一个写导航层的作业，同样有写入日志和变更记录。

### 和 ADR 0005 的衔接

- 只有 worker 写导航层；写入日志、原子写、回滚、恢复都只在 worker 里发生。
- 导航层写锁只在第 2、3 阶段持有：核对、落日志、写入、中途失败时的逆序退回，都在同一次持锁里完成。
- 恢复流程在 worker 启动、把中断的作业判为已中断之后、放行任何写导航层的作业之前运行。ADR 0005 中断恢复表里"写导航层的作业"一行，恢复流程就是本 ADR 的"一律回滚"。

### 三个场景

1. **建链时目的路径已存在**：预览阶段就报出。已经指向同一目标、并且登记在 `links[]` 里的，作业成功、什么都不写；否则拒绝，提示改走改指向（L2）。
2. **改指向改到一半时断电**：来电后 worker 读 `nav-journal`，已经写好的文件退回前像，没写的不动，作业变成"已中断"；完事后才放行别的写操作。用户重新预览，再提交（L13、L14）。
3. **改指向 40 天后发现指错了**：操作日志已经清掉，`nav-changes/<作业编号>.json.gz` 还在。提交"撤回 #N"，预览显示反向替换；当前状态等于 #N 的后像就照做，中间又被改过的以冲突失败并列出差异（L16）。

## Considered Options

- **不留日志，写失败时尽力撤销**（L13 B）：放弃。断电以后不知道做到了哪一步。
- **在旁边重建整个入口目录，再互换**（L13 C）：放弃。Linux 原子互换目录要 `renameat2(RENAME_EXCHANGE)`，标准库没有；一次写入还常常跨多个入口，互换也保证不了它们之间的一致。标准库的 `os.replace`、`os.symlink`、`os.fsync` 就够用（`AGENTS.md` 规则 7）。
- **中断后补完**（L14 B）：放弃。补完执行的是断电前确认的计划，确认时看到的状态可能已经过时；补到一半再断一次，处理起来更复杂。
- **中断后不自动处理，只标出来让人修**（L14 C）：放弃。每次断电都要人工介入。
- **预览状态只记 `原始路径.json` 的哈希**（L12 B）：放弃。有人在终端里改了 `子任务.json` 或删了链接，核对发现不了。整个导航层算一个哈希（L12 C）也放弃：任何无关的改动都会让写入以冲突失败。
- **完整的差异存进操作日志或数据库**（L15 B、L16 C）：放弃。一次 agibot 改指向就是几十 MB，会撑大数据库和每天的数据库备份，理由同 ADR 0005 不把作业日志存进数据库。
- **不留变更记录，靠备份退回**（L16 B）：放弃。备份最多留 4 周，40 天的场景回不去。
- **编号账本**（L7 B、C）：放弃。单独一份 `已分配编号.json` 和入口内容是两份真相；放进 `索引/` 又和「数据集板块的数据契约」的"`索引/` 保留不动"冲突。改为把移除的入口整体挪进 `已移除/`，编号从目录里就能推出来。

## Consequences

- **恢复失败会挡住所有写导航层的作业**，直到管理员处理。这是有意的：两者都不是的项说明有人在终端里同时改过，自动处理可能覆盖别人的修改。运维手册写明怎么处理。
- **`nav-changes/` 只在系统盘上**，永久保留，体积约为每次改动文件压缩后的大小。还没有备份，系统盘一坏，撤回能力就跟着丢了；跟着备份走，等「备份方案」（17）。
- **第一次写 alpha 时，它的按格式入口会少 3 个数据块**：这 3 个是链接够不着的数据块（10-17 被删掉的转换副本），按 L8、L9 由规范副本生成时自然不收录，预览里会列出（简报 C7）。
- **第一次写某个数据集时，入口里的 JSON 可能多出 `version: null`** 这一类推导字段的差异（L10），这是整组重新生成推导字段的结果，不是改格式。
- **在终端里手工改导航层仍然不受写锁约束**。写入前的核对能拦下"预览之后有人改过"；恢复时比对出的"两者都不是"会变成恢复失败。
- 写入日志、变更记录的文件格式，以及作业状态里"恢复失败"的表达，在 M1 第 07 张的骨架关卡定。
