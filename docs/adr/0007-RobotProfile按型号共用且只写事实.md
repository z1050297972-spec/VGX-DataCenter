# RobotProfile 按型号写，预览、录制、转换共用，只写事实

Status: accepted（2026-10-22，决策票「RobotProfile 是否共用」）

同一台机器人的事实，包括关节的名字、顺序和单位，目标和观测各从哪个话题取，相机的编码，以及怎么加入它的 ROS 图，原来要在 mcap2lerobot 的配置、`viz_relay`、录制三处各写一份。比如 R1 Lite 的反馈消息里 `name` 只有一项，却带着 6 个位置值，关节顺序只能靠外部给出；哪一处给错了，曲线就画错，转换出来的数据也会错。所以我们为每个机器人型号写一份 RobotProfile，作为这些事实唯一的来源，三处都从它读。

## 具体做法

- **只写事实**：内容是关节组（关节名、顺序、单位），每组的观测来源和目标来源，相机的话题、编码、分辨率和标称帧率，每路数据的时间戳从哪里来、是否可信，以及怎么加入 ROS 图（DDS 实现、发现方式、QoS）和就绪条件。
- **目标和观测成对写**：每个关节组写两个来源，共用同一份关节名、顺序和单位。来源 = 话题 + 取法，例如"`JointState.position`"，或者 JSON 路径。没有目标的组，明确写"无目标"。
- **就绪条件**：平台节点启动前逐条检查，不满足就报错并说明原因。例如 R1 Lite 要求机器人持有 `10.42.0.238`，也就是 `eth1` 已经接通。
- **存放**：放在平台仓库里，每个型号一份 TOML（例如 `profiles/r1lite.toml`），带版本号，修改走工单和评审。数据库里的机器人型号只记用哪一份。录制和转换时，记下用的是哪个版本。
- **一个型号一份**：v1 不支持单台机器人覆盖型号的配置。单台机器人特有的值，例如相机序列号、地址，放在机器人登记里。

## Considered Options

- **三处各自维护映射**：放弃。同一个事实写三遍，迟早会不一致。
- **从 RobotProfile 自动生成 mcap2lerobot 的配置**：v1 不做。同步基准、容差、切 episode 的规则、编码，这些都是转换算法的参数，归工具配置；自动生成会让平台绑死在某个工具的配置格式上。改为核对：工具配置里写的话题和关节顺序必须和 RobotProfile 一致，对不上就报错。这个核对在 M4 实现。
- **存在数据库里，在网页上编辑**：放弃。它是技术配置，改错一处会同时影响三个地方，应当走评审，留下版本历史。

## Consequences

- 两份草样在 `.scratch/platform-v1/assets/14-robot-profile/`。写草样时发现不少事实还不知道：R1 Lite 的关节名和夹爪单位，AutoLife 的关节名、单位、目标话题的字段，以及头部相机的分辨率和帧率。这些在 M5 开工前要补齐（「机器人现场补测」）。
- AutoLife 的状态消息是 `std_msgs/String`，没有 header，时间戳只能用接收时刻，并且标为不可信。预览和对齐时都要考虑这一点。
- R1 Lite 的目标话题来自主臂的电脑，时间戳不可信。转换按目标值对齐时，要用接收时刻或者别的办法，具体由工具配置决定。
