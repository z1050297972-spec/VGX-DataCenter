# 作业由独立的 worker 执行，worker 是导航层唯一的写者

Status: accepted（2026-10-22，决策票「作业模型」）

平台的长任务（下载、转换、重新扫描、写导航层、定时备份）都做成作业，由一个独立于 Web 的 worker 进程执行。worker 也是唯一写导航层的进程，即使只建一条链接也走作业。这样定，是因为负责人要求"Web 重启不影响正在跑的作业，整机重启后作业能接着跑，两个作业不能同时改导航层"。把执行、写导航层和崩溃恢复都收进一个进程，并发和恢复只需在一处处理。

## 具体做法

- **分工**：几秒内做完、只读写数据库的事，Web 当场做，例如浏览、登记机器人和采集任务、管理账号。耗时的、要调外部工具的、要写导航层的事，Web 只往作业表里插一行，交给 worker。Web 进程不写导航层。
- **通信**：Web 和 worker 只通过 SQLite 里的作业表联系，不另开通道。
  - Web 提交作业是插一行，取消作业是在那一行上写一个取消请求。
  - worker 每秒查一次有没有新作业和取消请求，每秒最多写一次进度，并且一直保留最后一次进度。
  - worker 定时写心跳。心跳过期时，网页顶部提示"worker 不在线，作业不会开始"。
- **托管**：Web 和 worker 各是一个 systemd 用户服务，开机自启，崩溃后自动重启。本机已开 `Linger=yes`，开机后不用登录服务就会启动。
  - worker 退出时，systemd 会把它启动的工具子进程一起结束，不会留下孤儿进程继续写盘。
  - 在 systemd 下运行时，日志只写 `web.log` / `worker.log`，不往 stderr 输出，免得 journald 再存一份、多出一套保留期。程序启动阶段的崩溃输出仍然会进 journald。
- **单实例**：worker 启动时先拿平台状态目录里的一把排他文件锁，拿不到就直接退出，所以不会有两个 worker 同时跑。运维命令里要碰导航层的（例如重建索引）也要拿这把锁，worker 在运行时拒绝执行，提示改到网页上提交。
- **导航层写锁**：worker 进程里有一把锁，管整个导航层。
  - 作业只在写导航层的那一步持有它。下载要跑三天，也只在最后入库的几秒占锁。
  - 重新扫描也要拿这把锁，免得扫到写了一半的状态。
  - 写导航层的作业在提交时记下预览时看到的状态，拿到锁后、真正写之前再核对一次。对不上就以"冲突"失败，一行都不写。
  - 提交时如果已有排队的作业要改同一个数据集，网页先给一句提醒。
- **中断与恢复**：worker 启动时，把上一个 worker 实例留下的"运行中"作业判为中断，在作业日志里写明中断在哪一步、最后进度是多少。然后按每类作业声明的恢复方式处理：

  | 作业 | 恢复方式 |
  |---|---|
  | 下载 | 续跑（aria2 `-c`、curl `-C -`） |
  | 重新扫描 | 重跑 |
  | 转换 | 标记中断，等人重新提交。mcap2lerobot 不能续跑，要加 `--force` 删掉半成品才能重跑，自动删不安全 |
  | 写导航层的作业 | 标记中断，先跑完它的恢复流程，再放行别的写操作。恢复流程由「软链接接口规则」定 |

  升级时重启 worker 也按中断处理。
- **并发**：每类作业有各自的并发上限，默认 1，可以在配置里改。不同类型的作业之间可以并行。
  - GPU 由 worker 分配：两张卡算两个名额，一张卡同一时间只给一个作业。worker 告诉工具用哪张卡，作业跑完收回；没有空卡就排队。
  - 转换默认同时只跑 1 个，M4 实测后再调。
- **存储根在线检查**：作业开跑前，先检查要写的存储根确实挂载着，不在线就以"外部失败"结束，什么都不写。这样做是因为 NAS 没挂上时，挂载点只是系统盘上的空目录，往里写会把系统盘写满。
- **作业的结局**：作业状态有六种：排队中、运行中、正在取消、已完成、已取消、已中断。
  - 只有已完成的作业有作业结果，四种结果由计数算出（ADR 0004）。
  - 已取消和已中断也显示做到了哪一阶段、多少条目。
  - 取消运行中的作业时，worker 先请工具停下，约 10 秒后还没停就强制结束。正在写导航层的那一步不打断。
  - 取消不清理产物，怎么清理由每类作业自己定。
  - 重新提交会新建一个作业，并注明"重新提交自 #N"。
- **日志与记录**：
  - **作业日志**是平台状态目录里的文本文件，路径形如 `logs/<作业类型>/2026-10-22_143015_123.log`，`<作业类型>` 例如 `下载`、`转换`。保留 30 天，管理员可调。
  - **作业记录**存在数据库里，永久保留，包括参数、提交人、状态、进度、计数、诊断样例和结尾摘要。
  - 提交人同时存内部编号和名字。账号删除后显示为"张三（已删除）"，作业记录不会挡着账号删除。定时作业的提交人记为"系统"。

## Considered Options

- **在 Web 进程里开后台线程跑作业**（开图时负责人提过）：放弃。升级或改配置要重启 Web，正在跑的下载会跟着停掉；长任务还会和请求处理抢同一个进程。
- **Celery、RQ 这类任务队列加 Redis**：放弃。要多运维一个服务。ADR 0002 选 SQLite，就是为了不加服务。几个人用的平台，每秒查一次作业表就够了。
- **能用 SQLite 的现成任务队列（huey、APScheduler、persist-queue、litequeue、DBOS）**：放弃（2026-10-22 补充，依据 `AGENTS.md` 规则 7"先用现成的"做的调研）。
  - 崩溃语义、运行中取消、按类型恢复都不符合要求。例如 huey 领取任务时就删掉那一行，断电时任务直接丢失；APScheduler 3 不能多进程共用作业存储；litequeue 不接受和其他表共用一个库。
  - 用了它们，作业表、恢复、取消、名额、进度这些代码照样要写，还要多协调一套库自己的状态。
  - 理由和出处见 `docs/research/作业队列选型.md`。
- **按数据集加锁**：放弃。批量改指向、新增数据集都会同时动多个数据集目录和两个视图。写操作都只要几秒，锁分得再细也换不来什么，反而多了死锁和漏加锁的可能。
- **锁放在数据库里（带租约的锁行），让 Web 也能直接写导航层**：放弃。这样要处理持锁进程崩溃后租约什么时候过期，Web 里也要再写一套写导航层的代码。只让 worker 写，锁随进程存亡，崩溃了自然释放，恢复流程也只在 worker 启动时跑一次。
- **作业日志放在导航层的 `日志/下载/`、`日志/转换/`**（负责人初步意见）：放弃。
  - 导航层是数据集的唯一事实来源，日志放进去以后，扫描、一致性面板、备份都得专门排除它。
  - 日志是持续写入的，等于在单写者之外又开了一个写入口。
  - 运行日志已经放在状态目录（ADR 0004、「可观测性与报错规范」）。

  "按类型分目录、按时间命名"这一点保留。
- **作业日志存进数据库**：放弃。工具原样的输出一份可能有几百 MB，会把数据库和每天的数据库备份撑大；放在文件里还能在终端直接 grep。
- **GPU 用不了时自动改用 CPU 编码**：放弃。换成 CPU 就是换了编码器，产物不同，血缘对不上。改为直接报错，提示用 CPU 配置重新提交。
- **单独的"暂停"功能**：不做。取消不清理产物，下载取消后重新提交就能接着下。

## Consequences

- 建一条链接也要排队，正常 1–2 秒出结果。正在执行一个较长的写导航层步骤时（例如几百条链接的批量改指向），要等它写完。
- worker 不在线时，作业只会一直排队。网页靠心跳提示，不会静默。
- 升级时重启 worker 按中断处理：下载会续跑，转换会变成已中断。升级前要先看一眼有没有正在跑的转换。"等作业跑完再停"的功能 v1 不做。
- 在终端里手工改导航层不受这把锁约束，只能靠一致性面板事后发现（「数据集板块的数据契约」）。
- 作业日志过了保留期就删除，之后只剩作业记录里的摘要。要复现，靠血缘里记下的工具版本和配置。
- 作业记录永久保留，所以提交人的名字也会一直留在作业记录里。
- 本机的两张 RTX 3090 的 NVENC 只能编码 H.264 和 HEVC，编不了 AV1，所以用 GPU 转换时，产物不是 lerobot 默认的 AV1。平台统一用哪种编码，由「工具清单与转换血缘」定。
- 有人在同一张卡上训练、把显存占满时，NVENC 编码会因为显存不够而失败，以"外部失败"报出。
- worker 进程、作业表、心跳、中断恢复、导航层写锁，加一个示例作业，都在 M0 交付。这一项原来不在 0003 的 M0 清单里。M1 的建链、改指向和重新扫描从第一天起就是作业。
