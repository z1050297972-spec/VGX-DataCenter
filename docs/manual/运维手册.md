# 运维手册

> 给维护平台的人看：装在哪、怎么配、出了问题去哪看。各节随 M0 的工单逐步补齐；第 11 张「运维入口与 systemd 服务」合并后整理成完整的安装和升级流程。

## 配置文件

**位置**
- 默认读 `~/.config/rdp/config.toml`。
- 环境变量 `RDP_CONFIG` 可以指向别的文件，必须是绝对路径或 `~/` 开头。它指向的文件不存在时拒绝启动，不会退回默认值。
- 只有这一个环境变量；不能用环境变量改单个配置项，所有配置都写在文件里。

**没有配置文件**：全部用默认值，日志里记一行"使用默认配置"。

**写错了**：类型不对、超出范围、写了不认识的项（多半是拼错了），都拒绝启动。报错写明文件路径、项名、实际值和期望。不认识的项，实际值显示为 `<已隐藏>`，以免把口令一类的值打进日志；"期望"部分有时是 pydantic 的英文原文。

**现有的项**（后面的工单会各自加）：

```toml
# 平台状态目录：绝对路径或 ~/ 开头；不接受相对路径。
state_dir = "~/.local/share/rdp"

[web]
host = "0.0.0.0"   # 监听地址
port = 8600        # 1–65535

[log]
level = "INFO"         # DEBUG、INFO、WARNING、ERROR，区分大小写
retention_days = 30    # 运行日志保留天数，1–3650；只能在这里改，网页上不能改
```

改完配置要重启服务才生效。

## 状态目录

默认 `~/.local/share/rdp/`，由配置里的 `state_dir` 决定。平台第一次启动时建好。

| 路径 | 是什么 |
|---|---|
| `rdp.sqlite3` | 平台数据库（M0 第 5 张起使用） |
| `logs/web.log`、`logs/worker.log` | 运行日志，见下一节 |
| `logs/<作业显示名>/` | 作业日志，一件作业一个文件，按开始时间（UTC）命名，例如 `logs/示例：数数/2026-10-26_120000_000.log` |
| `worker.lock` | worker 的单实例锁 |

- 新建的目录权限是 `0700`，因为数据库里会有口令哈希。
- 目录已经存在、但权限比 `0700` 宽（例如 `0755`）时，平台照常启动，但在日志里记一条警告，写明路径和现在的权限。平台不自动改权限，确认无误后自己执行 `chmod 700 <路径>`。
- 路径被一个普通文件占着，或者不可写，拒绝启动并说明是哪个路径。

## 运行日志

**两个文件**：Web 写 `logs/web.log`，worker 写 `logs/worker.log`，互不混写。

**格式**：一条一行，

```
2026-10-23 09:29:25.123-06:00 INFO rdp.api 消息 request_id=… job_id=…
```

- 时间是本机时区的本地时间，精确到毫秒，带偏移。本机现在是 `America/Cambridge_Bay`（−06:00），见 `docs/brief/0013`。看时间时以行里的偏移为准。
- 请求编号（`request_id`）、作业编号（`job_id`）由平台自动带上。Web 的每个响应头 `X-Request-ID` 就是这次请求的编号：用户报问题时拿到这个编号，就能在 `web.log` 里找到对应的行。
- 多行的诊断明细缩进跟在后面。
- 没有访问日志（每个请求一行的那种）。uvicorn 自己的启动、关闭和报错日志也是这个格式。

**切分和保留**
- 每天零点后的第一条日志触发切分，旧内容归档成 `web.log.2026-10-23` 这样的文件。夜里没有日志时，切分会晚一些。
- 只保留 `retention_days` 天的归档，更早的在切分时删掉。删不掉的（例如权限问题）留着，下次切分或启动时再试，不影响写日志。
- 已知问题：服务停了几天再启动，停机前那几天的内容会归档成重启当天的日期。M0 第 11 张修正。

**怎么看**

```bash
tail -f ~/.local/share/rdp/logs/web.log
grep 'request_id=<编号>' ~/.local/share/rdp/logs/web.log*
grep ' ERROR ' ~/.local/share/rdp/logs/worker.log
```

**日志本身写不进去时**（磁盘满、权限不对）：平台不会往屏幕上报错（ADR 0005：systemd 下只写文件），只会少几条日志。日志突然没有新内容时，先查磁盘空间和 `logs/` 的权限。

## 按错误编号查日志

用户看到报错时，网页上会显示一个**错误编号**（32 位十六进制，例如 `18a6568a905c46cb83435f4fc9cadfdc`）。它就是这次请求的请求编号，也在响应头 `X-Request-ID` 和返回内容的 `error_id` 里。

```bash
grep -A 40 'request_id=<错误编号>' ~/.local/share/rdp/logs/web.log*
```

找到的是一条 ERROR 行，后面缩进跟着诊断的几行，程序缺陷还会跟着完整的 traceback：

```
2026-10-24 00:00:17.123-06:00 ERROR rdp.api.errors 平台内部错误，请把错误编号交给维护者。 method=GET path=/api/… request_id=18a6…
    平台在<阶段>发现程序缺陷（错误）：<规则>
    对象：…
    规则：…
    实际：…
    后果：…
    检查：…
    Traceback (most recent call last):
      …
```

- 每个出错的请求只有一条 ERROR，traceback 只记一次。traceback 保留原始的报错文字和出错的那行代码，不打印变量的值。
- 日志里只记请求方法和路由，不记请求的内容；参数不合格（422）时只记哪个字段错了，不记填的值。
- 以后（M0 第 5 张）完整报错也会存进数据库，保留 30 天，到时候网页上能直接点开看。

**状态码速查**（完整的表和规则在 `docs/standards/CODING_STANDARDS.md` 6.2）：

| 状态码 | 意思 | 先查什么 |
|---|---|---|
| 400 | 数据或内容有问题（含改口令时"当前口令不正确"） | 诊断里的"对象""实际""检查" |
| 401 | 没登录、会话过期或已被撤销；登录时账号或口令错误 | 重新登录；登不上看账号是否被停用 |
| 403 | 登录了但不允许：角色不够、必须先改口令；或写请求没带本站 `Origin` | 诊断里写的是哪一条；脚本调写接口要自己带 `Origin` |
| 404 | 要找的东西不存在；或者 `/api` 下的路径不存在（已登录时） | 编号、路径有没有写错 |
| 405 | `/api` 下路径存在但方法不对，响应带 `Allow` 头 | 请求方法 |
| 422 | 请求参数不合格 | 日志里列出的字段位置 |
| 429 | 同一账号连续输错口令 5 次，要等 1 分钟；`Retry-After` 头写还要等几秒 | 等够再试；确认是不是有人在猜口令 |
| 409 | 和当前状态冲突（例如被别的作业改过） | 诊断里写的是哪个作业 |
| 502 | 外部的东西出错（存储根离线、工具失败）；同时登录的人太多、口令哈希排队超过 1 秒 | 存储根、外部工具，诊断里的"错误链" |
| 500 | 平台自己的 bug | 按错误编号找 traceback，报给维护的人 |

## 创建首个管理员

平台刚装好时没有任何账号，第一个管理员由运维在服务器上创建：

1. 先做数据库迁移（升级到 `0002_accounts_sessions` 以后才有账号表）。
2. 运行"创建首个管理员"，给出登录名和显示名，然后**输两遍口令**。输入不回显；终端不支持不回显输入时直接拒绝，不会把口令显示出来。
3. 只有平台里**还没有任何管理员**（包括已停用的）时才能建。已经有了就拒绝，避免被拿来再造一个管理员。

首个管理员的口令是本人输入的，第一次登录**不要求**再改。其他人的账号由这个管理员在网页"账号管理"里建，新账号第一次登录必须先改口令。

> 命令入口在 M0 第 11 张接上；现在是 `rdp.ops.accounts.create_first_admin` 函数。

## 忘记了唯一管理员的口令怎么办

在服务器上运行"重置账号口令"（`rdp.ops.accounts.reset_account_password`，命令入口同样在第 11 张），给出登录名，输两遍新口令。效果：

- 换成新口令，清掉连错计数，并要求下次登录先改口令；
- 这个账号所有已登录的浏览器立刻失效；
- 不改变角色，也**不会启用已停用的账号**；记录里修改人写"运维"。

账号不存在会直接说明，这个提示只在服务器上能看到。

## worker 没在运行时怎么办

worker 是执行作业的后台进程，和 Web 分开跑，同一台机器上只能有一个。它每 5 秒写一次心跳；Web 发现超过 15 秒没有心跳，所有页面顶部显示"worker 没在运行"。这时提交的作业只会排队，不会执行。

> 启动 worker 的命令和 systemd 服务由第 11 张工单「运维入口与 systemd 服务」提供；在那之前没有可直接运行的命令。

**先看 `logs/worker.log`**

- **"worker启动检查失败"**：多半是数据库版本不对，按日志里的提示先运行迁移，再启动 worker。worker 不自动迁移。
- **"另一个 worker 正在运行，锁文件：…"**（退出码 2）：已经有一个 worker 拿着 `worker.lock`。先确认那个进程是否还在（例如 `fuser <锁文件路径>`）。锁会随进程退出自动释放，**不要删锁文件**。
- **"worker失败退出，需要重启"**（退出码 1）：上面几行有 ERROR 和异常报告，说明出了什么故障，例如数据库写不进去。排除原因后重新启动。systemd 下会自动重启。
- 正常停止退出码是 0。停止时不等作业做完，最多 30 秒退出；没做完的作业下次启动时按下面的规则处理。

**重启后作业怎么样**

- 排队中的作业照常按编号顺序执行。
- 上次停掉时正在运行的作业，先在它的作业日志里写一段"中断"，再按作业类型的规定处理：接着做、从头重做，或者标"已中断"（"示例：数数"是标"已中断"）。同一件作业自动恢复超过 3 次也标"已中断"。
- 上次停掉时"正在取消"的作业，直接变成"已取消"。
- worker 写出第一次心跳后，页面上的提示几秒内自动消失。

**worker 被强制杀掉（`kill -9`）以后**

作业调用的外部程序在自己的进程组里运行，worker 被 `kill -9` 时它们不会跟着结束。用 systemd 运行时（第 11 张），服务停止会把整个服务的进程一起结束；手动运行时，重启前先查一下有没有残留的外部程序还在跑，有就结束掉，以免和重做的作业同时写同一份产物。
