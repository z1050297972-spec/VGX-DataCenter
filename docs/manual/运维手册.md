# 运维手册

> 给维护平台的人看：怎么装、怎么配、怎么升级、出了问题去哪看。内容对应 M0（底座），以 `a67be16` 上的脚本和代码为准。
>
> 下文的路径都是默认值。改过 `--deploy-dir`、配置里的 `state_dir` 或用了别的配置文件时，命令里的路径要换成你自己的。

## 0. 装好以后都在哪

| 东西 | 默认位置 | 说明 |
|---|---|---|
| 仓库副本 | 你 `git clone` 到的目录，下文写作 `~/robot-data-platform` | 安装和升级都从这里取代码。部署目录是它的一个 `git worktree`，**不要删除或挪动这个副本** |
| 部署目录 | `~/.local/opt/rdp` | 服务实际运行的那份代码：仓库在某个提交上的检出，加上 `.venv`、前端构建产物和 `rdp-build.json`（记录提交号） |
| 运维命令 | `~/.local/opt/rdp/.venv/bin/rdp` | 见第 6 节 |
| 配置文件 | `~/.config/rdp/config.toml` | 见第 3 节 |
| 状态目录 | `~/.local/share/rdp` | 数据库、运行日志、作业日志、迁移备份，见第 4 节 |
| systemd 用户服务 | `~/.config/systemd/user/rdp-web.service`、`rdp-worker.service` | 见第 5 节 |
| 一键安装装的工具 | `~/.local/opt/rdp-tools/<工具>/<版本>-<平台>/`，入口在 `~/.local/bin` | 只有一键安装会装，见 1.6 |

## 1. 一键安装（推荐）

`scripts/setup.sh` 在一台新机器上从零装好并启动平台：检查环境 → 缺工具时问过再装 → 问答生成配置 → 调用 `install.sh` → 建第一个管理员 → 健康检查 → 打印访问地址。

### 1.1 机器要求

- Linux，CPU 是 x86_64 或 aarch64，glibc 发行版。其他平台脚本会直接退出，提示手动准备工具。
- 已有这些基础工具：`git`、`curl`、`tar`、`sha256sum`、`findmnt`、`ip`、`flock` 和常用 coreutils。缺了脚本只提示，不替你装。
- 默认以 systemd 用户服务运行，需要 `systemctl --user` 和 `loginctl` 可用。没有时用 `--no-systemd`（见 1.4）。
- 不需要 sudo。脚本自己不运行 sudo，不装 git 和 systemd，不改系统服务。
- 能联网（下载内容见 1.6）。

### 1.2 取代码

从负责人提供的仓库地址克隆：

```bash
git clone <仓库地址> ~/robot-data-platform
```

> **占位**：仓库还没配远程，`<仓库地址>` 等负责人提供后填上。

一键安装默认装本地 `main` 分支的最新提交，脚本自己**不 clone、不 fetch、不 pull**。

### 1.3 运行

```bash
bash ~/robot-data-platform/scripts/setup.sh
```

脚本按下面的顺序提问，方括号里是直接回车时用的默认值；`[y/N]` 的问题直接回车算"否"。

1. **装工具**（PATH 上没有固定版本时才问）：Node、uv、pnpm 逐个说明版本、官方来源和安装目录，问"是否继续？[y/N]"。答否就停下，并打印手动安装办法。
2. **linger**（默认模式、linger 关着时才问）：说明"退出登录后用户服务可能停止，无法保证开机运行"，问"为当前用户启用linger？[y/N]"。答否就停下。启用失败时打印要管理员执行的 `sudo loginctl enable-linger <用户名>`。
3. **生成配置**（配置文件不存在时才问；已有配置只读取和校验，**绝不覆盖**）：
   - `监听地址 [0.0.0.0]`：直接回车是局域网明文 HTTP，见第 9 节；只给本机用填 `127.0.0.1`。
   - `端口 [8600]`
   - `导航层绝对目录（必填）`：没有默认值。
   - `状态目录 [~/.local/share/rdp]`
   - 列出本机所有挂载点，每行是编号、挂载点、文件系统、UUID 或 NFS 来源、内核只读还是可写、能不能选。只有 ext4 和 NFS 能选，其他标原因（例如 `unsupported_filesystem`、"叠加挂载，无法确认哪一层可见"）。在 `选择存储根编号（逗号分隔，空为不选）` 填编号，例如 `8,9`；什么都不选要再确认一次。
   - 每个选中的存储根问`名字`。平台默认只读：本地盘直接提示"本地盘或内核只读挂载保持平台只读"；只有内核可写的 NFS 才问"确认这是NFS专属平台区并允许平台写入？[y/N]"。
   - 有 `nvidia-smi` 时列出 `可用GPU编号`，在 `选择GPU编号（逗号分隔，默认空）` 填，例如 `0,1`。没有 `nvidia-smi` 就写 `gpus = []`。
   - 生成的配置先用目标提交里平台自己的校验检查一遍，通过后才以 `0600` 权限写出。
4. **开始安装**：问"开始安装平台到~/.local/opt/rdp？[y/N]"，答 `y` 后调用 `install.sh`（见第 2 节）。
5. **第一个管理员**（还没有任何管理员时才问；有了就打印"已有管理员，跳过创建。"）：`管理员登录名 [admin]`、`管理员显示名 [管理员]`，然后"请输入口令：""请再次输入口令："，输入不回显。口令不能写在命令行或环境变量里。
6. **健康检查**：请求本机的 `/api/health`，最多等约 70 秒。

成功时最后打印：

```
http://127.0.0.1:8600/
http://<本机网卡地址>:8600/
部署健康；以上是候选地址，未检测防火墙或外部连通性。
升级命令：bash ~/robot-data-platform/scripts/upgrade.sh --deploy-dir ~/.local/opt/rdp --commit <本地提交>
本次PATH已加入用户工具目录；可自行把 export PATH="$HOME/.local/bin:$PATH" 写入shell配置。
```

地址列表只是候选，脚本没有检查防火墙和外部能不能连上。用浏览器打开其中一个，用刚建的管理员登录。

脚本装了工具时，PATH 的改动只在这次运行里有效。以后要在终端里直接用 `uv`、`pnpm`（例如手动跑 `install.sh`、`upgrade.sh`），把这一行加进 `~/.bashrc`：

```bash
export PATH="$HOME/.local/bin:$PATH"
```

### 1.4 选项什么时候用

| 选项 | 什么时候用 | 效果 |
|---|---|---|
| `--yes` | 确定要装、不想逐个回答 y | 自动同意装工具、启用 linger 和最后的"开始安装"。**不代答**配置问答、存储根写许可和管理员口令；不覆盖已有配置和工具；不会把已有部署自动升级 |
| `--no-systemd` | 机器上没有可用的 systemd 用户服务（例如 SSH 会话里报"用户服务总线不可用"），或者只是试装 | 不调用 `systemctl`、`loginctl`，不装单元，不改 linger。装好后脚本**留在前台**同时运行 Web 和 worker，按 Ctrl+C 两个一起正常停下（退出码 0）。关掉终端服务就没了，也不会开机自启 |
| `--skip-admin` | 没有终端（脚本里调用），或者想以后再建管理员 | 不建管理员，打印建管理员的完整命令，之后在终端里执行。没有终端又还没有管理员时，必须带这个选项，否则退出码 2 |
| `--config FILE` | 配置不放在默认位置，或者事先写好了配置（例如从别的机器拷来） | 用这个文件。优先级：`--config` > 环境变量 `RDP_CONFIG` > `~/.config/rdp/config.toml`。文件已存在就只校验不改；不存在且有终端时，问答生成到这个位置 |
| `--deploy-dir DIR` | 部署目录不想用 `~/.local/opt/rdp` | 透传给 `install.sh`，必须是不存在的绝对路径 |
| `--commit REF` | 不装本地 `main`，装某个指定提交 | 校验和安装都用这个提交 |

没有终端时脚本不会等待输入，缺什么就报错退出。无人值守的完整写法：

```bash
bash ~/robot-data-platform/scripts/setup.sh --config /绝对路径/config.toml --yes --skip-admin
```

用了 `--config` 时，服务单元会记下这个配置路径；以后在终端里运行 `rdp` 运维命令，前面要加上同一个 `RDP_CONFIG=/绝对路径/config.toml`。

### 1.5 退出码

| 退出码 | 意思 |
|---|---|
| 0 | 成功；`--no-systemd` 下按 Ctrl+C 正常停下也是 0 |
| 1 | 环境、下载、配置、安装、启动或健康检查失败 |
| 2 | 参数错误，或没有终端又缺输入（缺配置、缺 `--yes`、缺 `--skip-admin`） |
| 3 | 另一个 setup 正在运行（锁文件 `~/.local/state/rdp/setup.lock`） |
| 130 | 某个确认问题答了否，或按 Ctrl+C 取消 |

### 1.6 会联网下载什么、装到哪里

| 下载 | 来源 | 装到 |
|---|---|---|
| Node 22.23.2 | `https://nodejs.org` 官方 `node-v<版本>-linux-<架构>.tar.gz`，用同源 `SHASUMS256.txt` 校验 | `~/.local/opt/rdp-tools/node/`，入口 `~/.local/bin/node` |
| uv 0.13.5 | `https://github.com/astral-sh/uv/releases/download/0.13.5/uv-<target>.tar.gz`，用脚本里固定的 SHA256 校验 | `~/.local/opt/rdp-tools/uv/`，入口 `~/.local/bin/uv` |
| pnpm 11.22.0 | `https://github.com/pnpm/pnpm/releases/download/v11.22.0/pnpm-linux-<架构>.tar.gz`，用脚本里固定的 SHA256 校验 | `~/.local/opt/rdp-tools/pnpm/`，入口 `~/.local/bin/pnpm` |
| Python 和 Python 依赖 | uv 按 `uv.lock` 下载，依赖来自 `https://pypi.org/simple` | uv 缓存、部署目录的 `.venv` |
| 前端依赖 | pnpm 按 `pnpm-lock.yaml` 下载，来自 `https://registry.npmjs.org` | pnpm 存储 `~/.local/share/pnpm/store`、部署目录的 `src/web/node_modules` |

- 三个工具只在 PATH 上没有这个确切版本时才装；已有就直接用。
- 下载完先校验，校验通过前不解包、不执行。缺少有效摘要就拒绝，不会跳过校验。
- 只接受官方 HTTPS 地址；GitHub 的重定向只允许去 `release-assets.githubusercontent.com` 和 `objects.githubusercontent.com`。
- 不调用 GitHub API（避开未认证限流）。
- 只发布自己管理的入口，不覆盖 `~/.local/bin` 里你已有的其他程序，不改 shell 配置。

### 1.7 网络注意事项

- **代理**：脚本的下载遵守 `HTTPS_PROXY`、`HTTP_PROXY`、`ALL_PROXY`、`NO_PROXY`，报错时不打印代理凭据。uv、pnpm 是脚本的子进程，会继承同样的环境变量。例如：

  ```bash
  HTTPS_PROXY=http://<代理地址>:<端口> bash ~/robot-data-platform/scripts/setup.sh
  ```

- **GitHub**：uv 和 pnpm 从 `github.com` 下载。网络到不了 GitHub 时，先配好代理，或者照 10.7 手动装工具。
- **超时和重试**：每次连接最多等 10 秒，每个文件最多下载 300 秒，暂时失败自动重试 2 次，屏幕上显示"官方请求暂时失败，重试 1/2"。
- **npm 源不稳定**：演练时 pnpm 多次遇到 `ECONNRESET`，pnpm 自己重试后装好了，看到 `[WARN] ... Will retry` 不用管。
- 健康检查只访问本机，不走代理。

### 1.8 失败了怎么办

失败时最后一行是：

```
部署停止：<阶段>（退出码<N>）；保留已完成工具、配置和部署，请修正原因后重试。
```

- 前面几行写了原因。已经校验通过的工具、已经写出的配置、部署目录和迁移备份都会保留；这次下载的临时文件会清掉。
- 修好原因后**重新运行同一条命令**，装好的工具不会重下，已有的配置不会再问。
- 如果失败发生在 `install.sh` 里（例如前端依赖下载失败），部署目录已经建了一半，重跑时会报"未完成部署；保留现场，请按install.sh帮助人工处理"。确认这个目录不用保留后，删掉这个 worktree 再重跑：

  ```bash
  git -C ~/robot-data-platform worktree remove --force ~/.local/opt/rdp
  bash ~/robot-data-platform/scripts/setup.sh
  ```

  或者用 `--deploy-dir` 换一个新目录重试。
- 健康检查失败时，报错里写了 `web.log` 和 `worker.log` 的实际位置，先看这两个文件（第 4 节）。这时脚本只停掉这次自己启动的服务。
- 下载类失败看 10.7。

### 1.9 重复运行

部署目录里已经是完整安装时，再运行 `setup.sh` 只报告状态，然后退出，退出码 0：

```
0.1.0 (b556311)
worker 已停止（锁未被持有）
无活跃作业
已有完整部署；升级命令：bash ~/robot-data-platform/scripts/upgrade.sh --deploy-dir ~/.local/opt/rdp --commit <本地提交>
```

（默认模式下还会显示两个服务是否 `active`。）它不重装、不重启、不改配置、不自动升级。要升级用第 7 节。状态读不出来时退出码非 0。

## 2. 手动安装（install.sh）

一键安装内部调用的就是它。已经自己准备好 `git`、`uv`、`pnpm` 和配置文件时，可以直接用。

```bash
bash ~/robot-data-platform/scripts/install.sh
```

| 选项 | 意思 |
|---|---|
| `--deploy-dir DIR` | 默认 `~/.local/opt/rdp`；必须是**不存在**的绝对路径，可以有中文和空格 |
| `--commit REF` | 默认本地 `main`；不 fetch、不 pull |
| `--no-systemd` | 只构建、迁移、查端口，不装单元、不调用 `systemctl` |

做的事情，按顺序：

1. 检查 `git`、`uv`、`pnpm`（默认模式还要 `systemctl`）；
2. `git worktree add --detach` 在部署目录检出目标提交；
3. `uv sync --frozen`；在 `src/web` 里 `pnpm install --frozen-lockfile`、`pnpm exec vite build`；写 `rdp-build.json`；
4. `rdp migrate`，然后 `rdp status --check-port` 检查端口；
5. 默认模式：生成两个单元文件写到 `~/.config/systemd/user/`，`daemon-reload` 后 `enable --now` 两个服务。不改 linger，不碰别的单元。

`install.sh` **不建管理员**，装完要自己建：

```bash
~/.local/opt/rdp/.venv/bin/rdp create-admin admin 管理员
```

用 `--no-systemd` 时，装完会打印三条前台命令（建管理员、`rdp web`、`rdp worker`），Web 和 worker 要在两个终端里分别运行，并保持 `HOME`、`RDP_CONFIG` 和安装时一致。

失败时打印"失败阶段：…；部署：…；旧提交：…；目标：…。保留现场与备份，修正原因后重试，不自动回滚。"。已有部署目录不能直接重装：先看失败现场，改用新目录重试，或者确认不用保留后用 1.8 的 `git worktree remove` 清掉。启动阶段失败时，它会停掉本项目的两个服务。

## 3. 配置文件

**位置**

- 默认读 `~/.config/rdp/config.toml`。
- 环境变量 `RDP_CONFIG` 可以指向别的文件，必须是绝对路径或 `~/` 开头。它指向的文件不存在时拒绝启动，不会退回默认值。
- 只有这一个环境变量；不能用环境变量改单个配置项。
- 安装时设了 `RDP_CONFIG`（一键安装总是会设），两个单元文件里会写上 `Environment="RDP_CONFIG=…"`，升级时沿用。

**没有配置文件**：全部用默认值，日志里记一行"使用默认配置"。

**写错了**：类型不对、超出范围、写了不认识的项（多半是拼错了），都拒绝启动。报错写明文件路径、项名、实际值和期望。不认识的项，实际值显示为 `<已隐藏>`，以免把口令一类的值打进日志；"期望"部分有时是 pydantic 的英文原文。

**改完要重启服务才生效**（第 5 节）。

**全部配置项和默认值**

```toml
# ↓ 顶层项必须写在所有 [表] 的前面
state_dir = "~/.local/share/rdp"   # 平台状态目录：绝对路径或 ~/ 开头，不接受相对路径
nav_root = "/mnt/datasets"         # 导航层位置：绝对路径或 ~/ 开头

[web]
host = "0.0.0.0"   # 监听地址；默认对局域网开放明文 HTTP，见第 9 节
port = 8600        # 1–65535

[log]
level = "INFO"         # DEBUG、INFO、WARNING、ERROR，区分大小写
retention_days = 30    # 运行日志保留天数，1–3650；只能在这里改

[errors]
retention_days = 30    # 完整报错保留天数，1–3650；由定时作业"清除过期报错"删除

[jobs]
gpus = [0, 1]          # 平台可用的卡，按 nvidia-smi 编号；[] 表示不用 GPU；见 8.1

[jobs.concurrency]     # 每类作业同时最多跑几个，不写就是 1；见 8.1
# example_gpu = 3

[storage]
access_timeout_s = 10  # 作业开跑前访问存储根的超时，0.1–60 秒

# 存储根：默认没有，一条一个 [[storage_roots]]；见 8.2
[[storage_roots]]
name = "dataset1"
path = "/mnt/dataset1"
uuid = "2d3a48d6-3785-47fe-8c8f-a20857fdc41a"
writable = false
```

> **坑：顶层项要写在表前面。** `state_dir`、`nav_root` 是顶层项，必须写在第一个 `[表]` 之前。写在某个表下面，TOML 会把它当成那个表里的项，平台按"不认识的项"拒绝启动。

> **没有 GPU 的机器**要写 `gpus = []`。不写时默认是 `[0, 1]`，worker 启动时核对不过，会在日志里各记一条 ERROR。

一键安装生成的配置形如：

```toml
state_dir = "/home/<用户>/.local/share/rdp"
nav_root = "/mnt/datasets"
[web]
host = "0.0.0.0"
port = 8600
[jobs]
gpus = [0,1]
[[storage_roots]]
name = "dataset1"
path = "/mnt/dataset1"
uuid = "2d3a48d6-3785-47fe-8c8f-a20857fdc41a"
writable = false
```

## 4. 状态目录和日志

### 4.1 状态目录

默认 `~/.local/share/rdp/`，由配置里的 `state_dir` 决定。`rdp migrate` 或服务第一次启动时建好。

| 路径 | 是什么 |
|---|---|
| `rdp.sqlite3` | 平台数据库 |
| `backups/` | `rdp migrate` 升级数据库前自动做的备份，文件名形如 `rdp-before-<UTC 时间>-<版本>-<编号>.sqlite3`，只留最新 5 份 |
| `logs/web.log`、`logs/worker.log` | 运行日志 |
| `logs/<作业显示名>/` | 作业日志，一件作业一个文件，按开始时间（UTC）命名，例如 `logs/示例：数数/2026-10-26_120000_000.log` |
| `worker.lock` | worker 的单实例锁，**不要删** |

- 新建的目录权限是 `0700`，因为数据库里有口令哈希。
- 目录已经存在、但权限比 `0700` 宽时，平台照常启动，在日志里记一条警告。平台不自动改权限，确认后自己执行 `chmod 700 ~/.local/share/rdp`。
- 路径被普通文件占着或不可写时拒绝启动，并说明是哪个路径。

### 4.2 运行日志

Web 写 `logs/web.log`，worker 写 `logs/worker.log`。systemd 下服务带 `--no-stderr` 运行，**日志只进这两个文件**；`journalctl --user -u rdp-web` 里只有 systemd 自己的启停记录。

格式一条一行：

```
2026-10-29 00:35:47.345-06:00 INFO rdp.api.production Web开始运行 platform_version="0.1.0 (b556311)"
```

- 时间是本机时区的本地时间，精确到毫秒，带偏移。本机现在是 `America/Cambridge_Bay`（−06:00），见 `docs/brief/0013`。看时间以行里的偏移为准。
- 请求编号（`request_id`）、作业编号（`job_id`）由平台自动带上。Web 每个响应头 `X-Request-ID` 就是这次请求的编号。
- 多行的诊断明细缩进跟在后面。
- 没有访问日志（每个请求一行的那种）。uvicorn 自己的启动、关闭日志也是这个格式。
- 每次启停都有一行：`Web开始运行`、`Web结束运行：正常停止 exit_code=0`、`worker开始运行`、`worker结束运行：worker已停止 exit_code=0`。

**切分和保留**

- 每天零点后的第一条日志触发切分，旧内容归档成 `web.log.2026-10-23` 这样的文件。
- 服务启动时，如果活动日志文件的修改日期早于今天，先按那个日期归档，再开新文件。所以停机几天再启动，旧内容仍归到它原来的日期。
- 只保留 `[log] retention_days` 天的归档，更早的在切分时删掉。删不掉的留着下次再试，不影响写日志。

**怎么看**

```bash
tail -f ~/.local/share/rdp/logs/web.log
tail -n 50 ~/.local/share/rdp/logs/worker.log
grep ' ERROR ' ~/.local/share/rdp/logs/worker.log
```

**日志写不进去时**（磁盘满、权限不对）：平台不会往屏幕上报错，只会少几条日志。日志突然没有新内容时，先查磁盘空间（`df -h ~/.local/share/rdp`）和 `logs/` 的权限。

### 4.3 按错误编号查日志

用户看到报错时，页面上有一个**错误编号**（32 位十六进制，例如 `18a6568a905c46cb83435f4fc9cadfdc`）。它就是这次请求的请求编号：

```bash
grep -A 40 'request_id=<错误编号>' ~/.local/share/rdp/logs/web.log*
```

找到的是一条 ERROR 行，后面缩进跟着诊断，程序缺陷还跟着完整的 traceback：

```
2026-10-24 00:00:17.123-06:00 ERROR rdp.api.errors 平台内部错误，请把错误编号交给维护者。 method=GET path=/api/… request_id=18a6…
    平台在<阶段>发现程序缺陷（错误）：<规则>
    对象：…
    规则：…
    实际：…
    后果：…
    检查：…
    Traceback (most recent call last):
      …
```

- 每个出错的请求只有一条 ERROR，traceback 只记一次，不打印变量的值。
- 日志只记请求方法和路由，不记请求内容；参数不合格（422）时只记哪个字段错了，不记填的值。
- 完整报错也存进数据库，保留 `[errors] retention_days` 天。

**状态码速查**（完整规则在 `docs/standards/CODING_STANDARDS.md` 6.2）：

| 状态码 | 意思 | 先查什么 |
|---|---|---|
| 400 | 数据或内容有问题（含改口令时"当前口令不正确"） | 诊断里的"对象""实际""检查" |
| 401 | 没登录、会话过期或已被撤销；登录时账号或口令错误 | 重新登录；登不上看账号是否被停用 |
| 403 | 登录了但不允许：角色不够、必须先改口令；或写请求没带本站 `Origin` | 诊断里写的是哪一条；脚本调写接口要自己带 `Origin` |
| 404 | 要找的东西不存在；或者 `/api` 下的路径不存在（已登录时） | 编号、路径有没有写错 |
| 405 | `/api` 下路径存在但方法不对，响应带 `Allow` 头 | 请求方法 |
| 409 | 和当前状态冲突（例如被别的作业改过） | 诊断里写的是哪个作业 |
| 422 | 请求参数不合格 | 日志里列出的字段位置 |
| 429 | 同一账号连续输错口令 5 次，要等 1 分钟；`Retry-After` 头写还要等几秒 | 确认是不是有人在猜口令 |
| 502 | 外部的东西出错（存储根离线、工具失败）；或口令哈希排队超过 1 秒 | 存储根、外部工具、诊断里的"错误链" |
| 500 | 平台自己的 bug | 按错误编号找 traceback |

## 5. 两个 systemd 用户服务

| 服务 | 运行 | 停止时 |
|---|---|---|
| `rdp-web.service` | `~/.local/opt/rdp/.venv/bin/rdp web --no-stderr` | 最多等 360 秒（`TimeoutStopSec`） |
| `rdp-worker.service` | `~/.local/opt/rdp/.venv/bin/rdp worker --no-stderr` | 最多等 45 秒；整个服务的进程（包括作业调用的外部程序）一起结束（`KillMode=control-group`） |

两个都是 `Restart=on-failure`、`RestartSec=5`（异常退出 5 秒后自动重启），`WantedBy=default.target`（开机自启）。单元文件由安装和升级脚本从仓库的 `scripts/systemd/*.service` 生成，不要手改；要改就改模板再升级。

**常用命令**

```bash
systemctl --user status rdp-web rdp-worker        # 看状态
systemctl --user is-active rdp-web rdp-worker     # 只看是否在运行
systemctl --user restart rdp-web                  # 重启 Web（改了配置后）
systemctl --user restart rdp-worker               # 重启 worker：运行中的作业会被中断
systemctl --user stop rdp-web rdp-worker          # 停止
systemctl --user start rdp-worker rdp-web         # 启动
systemctl --user is-enabled rdp-web rdp-worker    # 是否开机自启
curl http://127.0.0.1:8600/api/health             # 正常返回 {"status":"ok"}
```

- 重启或停止 worker 时，它不等作业做完；上次正在运行的作业，下次启动时按作业类型处理："示例：数数"标"已中断"，同一件作业自动恢复超过 3 次也标"已中断"；"正在取消"的直接变成"已取消"。
- worker 启动后几秒内写出第一次心跳，页面上的"worker 没在运行"提示自动消失。

**开机自启要求 linger**

用户服务默认只在你登录时运行。要开机自启、退出登录后继续运行，必须为这个用户打开 linger：

```bash
loginctl show-user "$USER" --property=Linger --value   # 显示 yes 才行
loginctl enable-linger "$USER"                          # 打开；不允许时请管理员执行：
sudo loginctl enable-linger <用户名>
```

一键安装会检查并问你要不要打开；`install.sh` 不改 linger。

## 6. 运维命令 rdp

都在部署目录里：`~/.local/opt/rdp/.venv/bin/rdp`。每个子命令都有 `--help`。用了非默认配置时，前面加 `RDP_CONFIG=<配置文件>`。

| 命令 | 做什么 |
|---|---|
| `rdp --version` | 显示版本和提交号，例如 `0.1.0 (b556311)` |
| `rdp web [--no-stderr]` | 前台启动 Web |
| `rdp worker [--no-stderr]` | 前台启动 worker |
| `rdp migrate` | 把数据库升级到当前版本，打印"数据库版本：…；备份：…"。**先停两个服务** |
| `rdp create-admin <登录名> <显示名>` | 创建首个管理员，终端里输两遍口令 |
| `rdp reset-password <登录名>` | 在终端里重置一个账号的口令 |
| `rdp status --active-jobs` | 退出码 0：没有运行中或正在取消的作业；3：有 |
| `rdp status --worker-stopped` | 退出码 0：worker 锁没人拿；3：worker 在运行 |
| `rdp status --check-port` | 退出码 0：配置里的地址和端口可用；1：被占用（包括被自己的 Web 占着）或检查失败 |

参数错误退出码 2；`status` 退出码 1 表示检查失败，不能当作"可以安全维护"。

**创建首个管理员**：只有平台里**还没有任何管理员**（包括已停用的）时才能建，有了就拒绝。口令输入不回显，终端不支持不回显时直接拒绝。首个管理员第一次登录不要求改口令；其他人由他在网页"账号管理"里建。操作日志里操作人记为"运维"。

```bash
~/.local/opt/rdp/.venv/bin/rdp create-admin admin 管理员
```

## 7. 升级

部署目录和仓库副本是分开的：仓库更新了，跑着的服务不会变，要跑升级脚本。

```bash
git -C ~/robot-data-platform pull          # 先更新本地 main（脚本自己不联网）
bash ~/robot-data-platform/scripts/upgrade.sh
```

| 选项 | 意思 |
|---|---|
| `--deploy-dir DIR` | 默认 `~/.local/opt/rdp`；必须是安装脚本建的、没有本地改动的 worktree |
| `--commit REF` | 默认本地 `main` |
| `--yes` | 跳过"确认升级"；**不跳过**运行中作业检查和服务停止检查 |
| `--no-systemd` | 前台运行的部署用：先自己在前台终端停掉 Web 和 worker，脚本用 worker 锁和端口确认它们真停了；完成后打印前台命令 |

**过程**（默认模式）：

1. 用旧版本检查有没有运行中或正在取消的作业。**有就停下**，服务保持原样：

   ```
   仍有运行中或正在取消的作业；保持当前服务状态，用旧版本恢复并处理至空闲后重试
   ```

   等作业做完，或在网页上取消，再重新运行升级。
2. 显示部署目录、旧提交、新提交，提示"将停止 Web 和 worker；失败不自动回滚。"，问"确认升级？输入 y 继续"。
3. 停 Web、停 worker，确认两者都停了，再查一次作业。
4. 检出新提交，`uv sync`、`pnpm install`、`vite build`，写 `rdp-build.json`，`rdp migrate`（迁移前自动备份数据库）。
5. 重新生成两个单元文件，`daemon-reload`，先启动 worker 再启动 Web，确认都在运行。
6. 打印新版本和"升级完成：…"。

核对：

```bash
~/.local/opt/rdp/.venv/bin/rdp --version
systemctl --user is-active rdp-web rdp-worker
curl http://127.0.0.1:8600/api/health
```

账号、作业记录都保留；旧作业仍记着当时的平台版本。

**升级失败**：保留备份和当前部署，打印失败阶段和旧、新提交。**已停的服务不会自动重启**。构建或迁移失败后保持停机，先按日志处理原因；数据库备份在 `~/.local/share/rdp/backups/`，脚本不自动恢复。

- 原单元里有 `RDP_CONFIG` 时沿用；终端里设的 `RDP_CONFIG` 和它不一致会拒绝升级。
- 部署目录里有人改过文件会拒绝升级，不会丢掉修改。
- 预检发现遗留的"运行中"作业（例如 worker 被直接停掉过）时，先用旧版本启动 worker，让它把这些作业处理掉（标"已中断"），空闲后再升级。

## 8. 调度和存储根的配置

### 8.1 调度

worker 按作业类型分别排队：同一类型按编号先后执行，不同类型互不等待。网页"调度"页只读，要改都在配置文件里改，改完重启 worker。

**并发上限**：每类默认 1 个，按作业类型的内部名写，1–32：

```toml
[jobs.concurrency]
example_gpu = 3          # "示例：占用 GPU" 同时最多 3 个
example_navigation = 2   # "示例：写锁" 同时最多 2 个
```

内部名在作业日志开头的 `type_name=` 里。写了不存在的类型或超出范围，拒绝启动。要卡的作业还受卡数限制，卡不够时排队显示"等待 GPU"。

**给平台留卡**：平台只用 `[jobs] gpus` 里列的卡，按 `nvidia-smi` 编号。想留一张给别人就写 `gpus = [0]`。

- 作业领到卡后，子进程拿到 `CUDA_VISIBLE_DEVICES=<卡号>` 和 `CUDA_DEVICE_ORDER=PCI_BUS_ID`，只看得到自己那张卡。
- worker 启动时用 `nvidia-smi` 逐张核对（每张最多 5 秒）。核对不过的卡移出名额池，调度页显示"已移出名额池"和原因，`worker.log` 里有 ERROR（`gpu_index=<卡号>`）。修好后重启 worker 才会重新核对。
- `gpus = []` 或所有卡都核对不过时，要卡的作业以"外部失败"结束，诊断写"平台没有可用的卡"；不要卡的作业不受影响。

**定时作业**：本机时区每天 03:00 由 worker 提交，提交人记为"系统"。

| 名称 | 做什么 |
|---|---|
| 清除过期报错 | 删掉超过 `[errors] retention_days` 的完整报错 |
| 清除过期日志 | 按"操作日志"页上的保留期，一起删过期的操作日志和登录日志 |

- 每天最多提交一次，重启不会重复提交。worker 启动时，从没跑过、上次提交已过 24 小时以上、或当天 03:00 已过还没交的，马上补交。
- 夏令时切换那天：03:00 不存在时顺延到切换后的第一个时刻；出现两次时按第一次。
- 失败只影响这一次，第二天照常跑。

**导航层写锁**：会改导航层的作业同一时刻只能有一个在写。等锁最多 300 秒，超时以"冲突"结束。

### 8.2 存储根

存储根写在配置文件里，网页上不能登记或修改；改完重启 Web 和 worker。

```toml
[[storage_roots]]
name = "dataset2"                                  # 小写字母开头，只含小写字母、数字、下划线
path = "/mnt/dataset2"                             # 真实挂载点的绝对路径，不要写软链接
uuid = "35445b14-9e83-4f74-ac73-1551e3db6d63"      # ext4：文件系统 UUID，小写
writable = false                                   # 平台能不能往上写，默认 false
```

- 挂载源二选一：ext4 写 `uuid`；NAS 写 `nfs_export = "服务器:/导出路径"`，和 `findmnt` 显示的来源逐字一致。两个都写或都不写，拒绝启动。
- 查 UUID：

  ```bash
  findmnt -no SOURCE,UUID /mnt/dataset2
  ls -l /dev/disk/by-uuid/
  ```

- 名字重复、路径不是绝对路径、两个存储根路径相同或一个在另一个里面，拒绝启动。
- "只读"是平台自己守的规则，和系统挂载的 `ro`/`rw` 无关。声明要写的作业遇到只读存储根，直接以"外部失败"结束，什么都不写。

## 9. 监听地址的安全风险

默认 `host = "0.0.0.0"`：**同一局域网里的任何人都能打开平台的登录页，而且是明文 HTTP**，登录口令和会话在网络上不加密（HTTPS 在 M5 再做）。只在可信的内网这样用。

只给本机用，改成 `127.0.0.1`：

1. 编辑 `~/.config/rdp/config.toml`，在 `[web]` 下改：

   ```toml
   [web]
   host = "127.0.0.1"
   ```

2. 重启 Web：

   ```bash
   systemctl --user restart rdp-web
   curl http://127.0.0.1:8600/api/health
   ```

改成 `127.0.0.1` 后，别的机器打不开平台。需要从别的机器访问时，可以用 SSH 端口转发：在自己电脑上执行 `ssh -L 8600:127.0.0.1:8600 <用户>@<服务器>`，然后打开 `http://127.0.0.1:8600/`。

## 11. 排查

### 11.1 页面提示"worker 没在运行"

worker 每 5 秒写一次心跳，Web 超过 15 秒没收到心跳就在所有页面顶部提示。这时提交的作业只排队，不执行。

```bash
systemctl --user status rdp-worker
tail -n 50 ~/.local/share/rdp/logs/worker.log
```

| 日志里看到 | 原因和处理 |
|---|---|
| "worker启动检查失败"，提示 `rdp migrate` | 数据库版本不对，见 11.3。worker 不自动迁移 |
| "另一个 worker 正在运行，锁文件：…"（退出码 2） | 已经有一个 worker 拿着 `worker.lock`。用 `fuser ~/.local/share/rdp/worker.lock` 看是哪个进程。锁随进程退出自动释放，**不要删锁文件** |
| "worker失败退出，需要重启"（退出码 1） | 上面几行有 ERROR 说明原因（例如数据库写不进去）。排除后 `systemctl --user restart rdp-worker`；systemd 下会每 5 秒自动重试 |
| 服务显示 inactive，日志最后是"worker结束运行" | 被人停掉了：`systemctl --user start rdp-worker` |

**手动运行的 worker 被 `kill -9` 以后**：作业调用的外部程序在自己的进程组里，不会跟着结束。用 systemd 运行时停服务会一起清掉；手动运行时，重启前先查一下有没有残留的外部程序在跑，有就结束掉，以免和重做的作业同时写同一份产物。

### 11.2 存储根离线

网页"存储根"页显示每个存储根的状态；它只读系统挂载表，不碰存储根里的文件。

| 页面显示 | 意思 | 怎么查 |
|---|---|---|
| 没挂载 | 这个路径此刻不是挂载点 | `findmnt /mnt/dataset1` 没有输出；看 `/etc/fstab`、`dmesg`，挂上后点"重新检查" |
| 挂错了盘 | 是挂载点，但不是登记的那块盘，或者只挂了那块盘的子目录 | `findmnt -no SOURCE,FSTYPE,FSROOT,UUID /mnt/dataset1` 对照登记：UUID 要一致，FSROOT 要是 `/` |
| 超时 | 只在作业开跑前检查里出现：访问超过 `[storage] access_timeout_s` 没返回，多半是 NAS 卡住 | `grep 'storage_root=' ~/.local/share/rdp/logs/worker.log`，检查网络和 NAS |

- 整页报错"外部失败 · 存储检查"表示连挂载表都读不了，按诊断提示检查权限。
- 作业开跑前发现存储根离线，作业以"外部失败"结束，一步都没做；修好后让用户重新提交。
- 访问卡住的 NAS 时，检查线程可能一直挂着，反复超时会让 worker 的线程慢慢变多，`systemctl --user restart rdp-worker` 可以清掉。

### 11.3 数据库版本不对

现象：服务起不来（systemd 每 5 秒重试一次），`web.log` 或 `worker.log` 里提示运行 `rdp migrate`。多半是代码换了版本但没迁移。正常用 `upgrade.sh` 升级时它会自动迁移。

```bash
systemctl --user stop rdp-web rdp-worker
~/.local/opt/rdp/.venv/bin/rdp migrate
systemctl --user start rdp-worker rdp-web
```

`migrate` 打印"数据库版本：<版本>；备份：<备份文件或'无'>"。数据库已经是最新时什么都不改，备份显示"无"。

如果数据库版本**比代码新**（例如部署目录被退回了旧提交），不能降级：把代码换回和数据库匹配的版本；必要时人工从 `~/.local/share/rdp/backups/` 恢复备份。

### 11.4 忘了管理员口令

在服务器的终端里：

```bash
~/.local/opt/rdp/.venv/bin/rdp reset-password admin
```

输两遍新口令（不回显），看到"账号操作成功：admin"即可。效果：

- 换成新口令，清掉连错计数，并要求下次登录先改口令；
- 这个账号所有已登录的浏览器立刻失效；
- 不改变角色，**不会启用已停用的账号**；操作日志里操作人记为"运维"。

账号不存在会直接说明。

### 11.5 端口被占

安装时报"端口检查失败；检查配置 … 的 web.port，再重试"，或 Web 起不来。

```bash
systemctl --user stop rdp-web
~/.local/opt/rdp/.venv/bin/rdp status --check-port; echo $?
ss -ltnp | grep ':8600'
```

- 自己的 Web 还在跑时 `--check-port` 也返回 1，所以先停 Web 再查。
- 停了以后仍是 1，说明别的程序占着。换端口：在 `~/.config/rdp/config.toml` 的 `[web]` 下改 `port`，然后 `systemctl --user start rdp-web`。

### 11.6 单元文件报 bad-setting

现象：

```
Failed to start rdp-worker.service: Unit rdp-worker.service has a bad unit file setting.
```

用 systemd 自己的检查找出是哪一行：

```bash
systemd-analyze --user verify ~/.config/systemd/user/rdp-web.service ~/.config/systemd/user/rdp-worker.service
```

已知原因：`9d90249` 之前的安装脚本给 `WorkingDirectory` 加了引号，`verify` 报 `WorkingDirectory= path is not absolute: "…"`。现在的脚本已修好。按下面步骤修：

```bash
sed -i 's/^WorkingDirectory="\(.*\)"$/WorkingDirectory=\1/' ~/.config/systemd/user/rdp-web.service ~/.config/systemd/user/rdp-worker.service
systemd-analyze --user verify ~/.config/systemd/user/rdp-web.service ~/.config/systemd/user/rdp-worker.service
systemctl --user daemon-reload
systemctl --user start rdp-worker rdp-web
```

之后用 `upgrade.sh` 升到当前 `main`，单元文件会按修好的模板重新生成。

### 11.7 一键安装下载失败或被限流

| 看到 | 意思 | 怎么办 |
|---|---|---|
| "官方请求暂时失败，重试 1/2" | 暂时性错误，脚本在自动重试 | 等它 |
| "官方文件下载失败（curl退出码N）；重试预算已用尽或错误不可重试，请检查网络、代理或手动安装" | 连不上或一直失败 | 检查网络和代理（1.7），重跑 |
| "官方下载被拒绝或限流（HTTP 403）"或"（HTTP 429）" | 被 GitHub 拒绝或限流，常见于出口 IP 是共用的 | 过一会儿重跑，或换个代理出口，或手动装工具 |
| "下载总时间超过预算" | 单个文件 300 秒没下完 | 网络太慢，配代理或手动装 |
| "拒绝非官方下载域" | 下载被重定向到白名单之外的地址 | 检查代理是否篡改了重定向 |

已经校验通过的工具会保留，重跑不会重下。

**手动装工具**：从 1.6 表里的地址下载同一个文件，用 `sha256sum <文件>` 对照 `scripts/setup.sh` 开头 `SETUP_TOOL_SHA256` 里的值（Node 对照 nodejs.org 同目录的 `SHASUMS256.txt`），解包后让 `node`、`uv`、`pnpm` 出现在 PATH 上（例如放进 `~/.local/bin`），确认：

```bash
node --version   # v22.23.2
uv --version     # uv 0.13.5 (…)
pnpm --version   # 11.22.0
```

然后重跑 `setup.sh`。PATH 上已经是这几个确切版本时，脚本直接用，不再下载。

**npm 源报 `ECONNRESET`**：pnpm 会自己重试。最终还是失败时，`install.sh` 停在"前端依赖"，部署目录只建了一半，按 1.8 删掉 worktree 后重跑。

### 11.8 已知现象：打开登录页时 web.log 有 ERROR

没登录时打开登录页，`web.log` 会记 2–3 条 `ERROR rdp.api.errors 输入或数据不符合要求，请查看诊断。`。这是未登录请求被当成错误记录，不影响使用，以后的工单会调低级别。
