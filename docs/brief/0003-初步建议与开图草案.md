## 四、数据集板块（系统核心，回答你的补充 1–4）

### 4.1 事实来源：导航层就是真相

- **`/mnt/datasets` 导航层（目录 + 软链接 + 三个 JSON）是数据集的唯一事实来源。** 系统读它、展示它、通过受控接口改它。
- 数据库只保存一份**可以随时从导航层重建的索引**，用来加速搜索。索引删了也不丢任何信息，点"重新扫描"即可恢复。
- 好处：
  - 你现在的结构和习惯完全保留。
  - 系统挂了，导航层照样能在终端里 `ls`、`cat`。
  - 不存在"数据库和磁盘两套真相"的问题。
- 数据盘（`/mnt/dataset1`、`/mnt/dataset2`、NAS）对系统**只读**，和 JSON 里的 `source_files_modified: false` 一致。系统只写导航层。

### 4.2 按"格式"和"任务"浏览（补充 3）

扫描器把导航层读成两棵树，按 `dataset_id` 把两个视图里的同一数据集关联起来：
- **按任务**：`按任务/<数据集>`，一层。
- **按格式**：`按格式/<格式>/<版本>/<数据集>` 或 `按格式/<格式>/<数据集>`，两层或三层，取决于该格式有没有版本层（F6）。

Web 页面：
- 左侧是两个页签"按格式 / 按任务"，各显示一棵树，带数据集数量和总大小。
- 右侧是数据集列表，可以按名称、机器人型号、FPS 筛选。
- 点开某个数据集，能跳到它在另一个视图里的位置。

### 4.3 数据集详情页展示三个 JSON（补充 3）

| JSON | 展示方式 |
|---|---|
| `数据集信息.json` | 14 项渲染成一张表，`value_markdown` 按 Markdown 渲染，文中的本地路径可以点击 |
| `原始路径.json` | 列出每条链接：名称 → 目标；**实时显示目标是否存在、在哪个存储根、多大**，并显示 `validation_status` |
| `子任务.json` | 只读的 JSON 查看器，默认折叠、按需加载（最大 14MB）。暂不做任何子任务功能（补充 5） |

还有一个**一致性面板**，标出以下问题：
- 两个视图里的 JSON 副本内容不一致
- 断链
- 磁盘上的链接和 `原始路径.json` 记录的不一致
- 失效引用（例如 `summary_path`）

### 4.4 软链接接口（补充 4）

同一组核心函数，套上 CLI 命令和 Web 表单两个入口：

- **创建链接**：
  - 输入"目标路径"（真实数据，例如 `/mnt/dataset1/libero_v3/libero_10`）和"目的路径"（链接放在哪，例如 `/mnt/datasets/按任务/libero_10/原始数据`）。
  - 流程：校验 → 显示预览 → 你确认 → 创建链接 → **写回 `原始路径.json` 的 `links` 和 `sources`** → 重新索引 → 记录操作日志。
- **改指向**（为智元迁 NAS 准备，补充 2）：
  - 把一组链接从旧前缀批量换到新前缀，例如 `/mnt/dataset1/agibot_world_2026` → `/mnt/nas/...`。
  - 两个视图里的链接和清单一起改。
  - 同样先预览、再确认。
- **体检**：扫描断链，以及链接和清单不一致的地方，只报告，不自动修复。

推荐的校验规则（在决策票里定稿）：
- 目标必须存在，并且位于某个已登记的存储根下。
- 目的路径必须在 `/mnt/datasets/按任务/` 或 `/mnt/datasets/按格式/` 之下。
- 目的路径已经存在时不覆盖，必须显式走"改指向"。
- 链接一律用绝对路径，与现状一致；跨盘的相对路径不可靠。
- 不修改目标里的任何东西。

**待你在票里决定**：
- 新增一个数据集时，系统要不要一次性建好两个视图的目录、链接和三个 JSON 骨架？
- `数据集信息.json` 的 14 项由谁生成？现在的做法和以后下载完成后自动入库的做法，可以放到下载里程碑再定，先放进迷雾。

## 五、Docker：平台本身不进 Docker

平台原生运行，用 uv 管理环境。原因是几乎每个功能都要碰宿主机：
- 网卡和 VPN 进程
- 两块盘和 NAS 的挂载
- SSH 密钥
- GPU 版 ffmpeg
- conda 里的 lerobot 环境
- 导航层软链接（软链接的目标路径必须和宿主机的挂载路径一致，放进容器很容易错位）

Docker 只在两种情况下用：
- 工作站需要 ROS 2 Jazzy 时（宿主机是 26.04，装不了 Jazzy）。
- 选了 PostgreSQL 时。

## 六、第 12、13 条的意见，以及第 1–11 条的推荐答案

### 第 13 条：Python 为主；Rust 只写独立工具；不用 Java

- **Python 3.12**：lerobot、rclpy、huggingface_hub、psutil 都在 Python 生态；只守一门主语言最省力；AI 写 Python 的质量最稳。
- **Rust**：只用于重计算的独立 CLI 工具，比如 mcap2lerobot。平台通过工具清单以子进程方式调用它，自己不需要两门语言并存。
- **Java**：机器人和 ML 生态都不在这边，单人维护负担太重。
- **架构：模块化单体，刻意少依赖。**
  - 一个 Python 包，按领域分模块：storage、datasets、links、downloads、netmon、robots、tasks、live、recording、conversion、tools。
  - 外面两层薄入口：CLI（Typer + Rich）和 Web（FastAPI）。
  - **不引入 Celery、Redis、MySQL，不做微服务。** 新增依赖要写理由并经你同意。

### 第 12 条：防屎山

1. **自动检查**：ruff（含 docstring 规则和函数复杂度、参数个数、语句数上限）、pyright 严格模式、pytest。另用 **import-linter** 强制模块之间单向依赖。全部汇总成 `make check`，挂到 pre-commit 框架上。
2. **评审规范**：`CODING_STANDARDS.md` 从 engineering-control 移植过来，由 `/code-review` 执行。
3. **函数契约先行**：见第七节。
4. **复盘**：每个里程碑跑一次 `/retro`，把犯过的错变成新的自动检查。
5. **安全**：
   - 开启 `/git-guardrails-claude-code`。
   - **数据盘只读。** 测试只能写临时目录，以及一个测试专用的假导航层，绝不碰真实的 `/mnt/datasets`。

### 第 1–11 条的推荐答案（在决策票里确认）

- **(1) 下载**：
  - 走 `HF_ENDPOINT=hf-mirror`：先列出文件、大小和 sha256，做容量预检，用 aria2 `-c` 续传下载，失败回退到 `curl -C - --retry`，校验 sha256 后入库。
  - 入库就是在导航层建目录、链接和 JSON。
  - 代理显式控制；aria2 跑 RPC 模式，供监控读取速度。
- **(2) 网络与资源**：
  - VPN 检查看三处：TUN 网卡、进程、代理变量。
  - 网速取 `/proc/net/dev` 的差值；资源用 psutil，并显示每个存储根的剩余空间。
  - 终端用 Rich Live 显示，标明当前是有线还是无线。
- **(3) 机器人**：身份用 MAC 或序列号；IP、端口、SSH 用户作为可变属性；型号单独建表；不存密码，用 SSH 密钥。
- **(4) 采集任务**：名称、用途、所用机器人、采集方式、场景；多对多关系用关联表；采集方式、用途、场景用受控词表。**子任务暂不处理。**
- **(5) 预览**：
  - 实时采集时能同时看目标和观测。R1 Lite 的目标话题是 `/motion_target/target_joint_state_arm_*`，反馈话题是 `/hdas/feedback_arm_*`；AutoLife 的状态 JSON 里两者都有。
  - 引入 **RobotProfile**，一份映射供预览、录制、转换共用。
  - 技术路线由 R-02 和 P-01 定。
- **(6) 录制**：
  - 统一的动作集：start / save / discard / stop，加一个统一的录制状态机。
  - 用两类适配器接入：原厂录制，以及自写采集器（复用它的管道协议）。
  - 键盘和网页按钮映射到同一组动作。
- **(7) 转换**：数据集记录"格式 + 血缘"。录制时转换和录制后转换都记成"这个产物怎么来的"。转换产物同样入库到导航层。
- **(8) 工具库**：
  - 目录约定 `tools/<输入格式>2<输出格式>[-<变体>]/`，每个工具带一份 `tool.toml` 清单，写明名称、版本、输入输出格式、适用型号、运行环境、命令模板、`configs/<型号>.toml`。
  - 清单是事实来源，数据库里只是索引。
- **(9) 数据库**：SQLite（WAL）+ SQLAlchemy 2 + Alembic。
  - **数据集的真相在导航层**，数据库只存可重建的数据集索引，加上机器人、采集任务、工具、作业记录。
  - 打开外键；时间用 UTC；改表结构一律走迁移；不存密码。
- **(10) 调试**：对齐 engineering-control。
  - 五段式诊断；显式状态，并和退出码一致。
  - 上下文在拥有身份的那一层补充；错误只打印一次。
  - 用 `raise … from e` 保留原因；rich 显示 traceback 和进度条；每个作业一份日志。
- **(11) 模块化**：按领域分模块，依赖方向由 import-linter 强制。

## 七、函数级工作法

**函数是写代码和审查的单位，但不是开工单的单位。**
- 工单仍然是能演示的垂直切片，否则写了几十个函数也跑不通一个功能。
- 函数级文档只写在代码的 docstring 里，代码和文档始终是同一份，不会过期。

每张工单分五步：

1. **契约骨架（Codex）**：只写签名、类型和完整 docstring，函数体是 `raise NotImplementedError`，单独提交一次。docstring 固定包含六项：职责、参数（含单位和取值范围）、返回值、异常及触发条件、副作用、时间语义。
2. **审骨架（我先审，你拍板）**：我对照工单、术语表、ADR 和规范审一遍，给你一页摘要：函数清单加问题点。你回"通过"或提出修改。你的精力只花在确认设计上。
3. **逐函数 TDD（Codex）**：用 `$tdd`，每个契约行为至少一个测试。
4. **逐函数核对（我）**：用 `/code-review` 检查实现是否和 docstring 一致、有没有多出工单以外的公开函数。
5. **机械检查兜底**：ruff 检查 docstring 和签名是否一致、复杂度是否超限，pyright 检查类型。**我自己重跑一遍，不采信 Codex 的自述。**

以软链接接口为例，骨架大概是这样（具体模板和阈值在 G-02 里定）：

```python
def plan_link(target: Path, link_path: Path, roots: StorageRoots, nav_root: Path) -> LinkPlan:
    """校验并生成建链计划，不产生任何副作用。

    参数:
        target: 链接目标（真实数据）的绝对路径，必须存在且位于某个已登记存储根之下。
        link_path: 链接位置的绝对路径，必须位于 nav_root/按任务 或 nav_root/按格式 之下，且尚不存在。
    返回:
        LinkPlan：将创建的链接，以及将写回 原始路径.json 的变更（供预览）。
    异常:
        LinkValidationError：任一规则不满足；消息包含对象、规则、实际值、期望值、下一步。
    副作用:
        无（只读文件系统）。
    """
    raise NotImplementedError

def apply_link(plan: LinkPlan) -> LinkResult:
    """执行已确认的计划：创建绝对路径软链接，并写回 原始路径.json。
    副作用：写导航层，不写数据盘。写回失败时删除刚建的链接，保证链接和清单一致。"""
    raise NotImplementedError
```

"先算计划、再执行"拆成两个函数，对应 engineering-control 的"规则计算 → 副作用执行"：预览和执行共用同一份计划。

| 评审 | 我 | 重跑检查、做两轴评审、核对文件归属；把结论写进工单的 `## Comments` |
| 拍板 | 你 | 骨架通过与否、合并与否，各说一句话 |
| 管理 | 我 | 维护工单状态和地图；每张工单结束给你一段进度汇报；每个里程碑结束跑 `/retro` |

### 每张工单的流水线

```
① 我：选票，改 Status: in-progress，建分支 t/<里程碑>-<NN>-<slug>
② 我→Codex（后台）：
   codex exec -C <仓库> -s workspace-write --json -o <输出> "<派工提示A：读 AGENTS.md 和工单，只写契约骨架并提交>"
   完成时我会收到通知，并记下 Codex 的 session id
③ 我：审骨架 → 给你一页摘要 → 你说"通过"或"改"
④ 我→Codex：codex exec resume <session id> "<派工提示B：按契约用 $tdd 逐函数实现，make check 全绿后提交>"
⑤ 我：
   · 重跑 make check
   · 用 git diff --name-only 核对文件归属
   · /code-review（Standards 轴对照 CODING_STANDARDS.md，Spec 轴对照工单）
   · 涉及同步、录制、转换的，再跑 algorithm-code-review
⑥ 有问题 → 写进工单 Comments → codex exec resume <id> "<修复清单>" → 回到 ⑤
   最多 3 轮；仍不过就停下来找你，不无限循环
⑦ 通过 → 给你汇报（改了什么、测试、风险）→ 你说"合并" → 我用 --no-ff 合并到 main
   （保留契约提交）→ Status: done
```

### 这套分工带来的保障

- **沙箱就是护栏**：
  - `workspace-write` 只能写仓库，物理上碰不到 `/mnt` 下的数据盘和导航层。
  - 这个沙箱默认不能联网，所以 Codex 装不了新依赖。需要新增依赖时，由你批准、我来装，"新依赖必须审批"这条规则因此是机器强制的。
- **交叉评审**：写代码和审代码的是两个不同的模型，比自写自审更容易发现问题。
- **只信自己跑出来的结果**：检查结果以我重跑的为准。
- **状态流转**沿用本地 tracker 的 `Status:` 行：
  - 主线：`ready-for-agent → in-progress → in-review → done`
  - 打回：`in-review → changes-requested → in-progress`
  - 我管两个 Claude 会话之间的衔接：每张工单做完我建议 `/clear`；状态都在文件里，不会丢。
- **派工模板固定**：放在 `docs/agents/codex-workflow.md`，我在 M0 写好，你过目后定稿。改模板也走 `/retro`。
