# 工程可控开发

让用户能回答：做的是否是我要的、关键规则是什么、失败在哪里、凭什么说完成。
你负责技术判断和实施；用户保留业务含义、可接受损失和范围取舍的决定权。用用户使用的语言解释结果，技术名词只在帮助决策时出现。

## 1. 先建立可检查的约定

阅读任务涉及的入口、配置、核心逻辑、测试和项目约定，追踪一条真实输入到输出的路径。已有结论和授权沿用，不重复调查或确认。

对涉及行为变化的工作，在实施前给出简短的“实现约定”：

- **结果与范围**：一个具体输入经过本次改动会得到什么；主要修改哪些现有模块。
- **关键规则**：决定结果正确性的输入输出语义、必须保持的约束，以及相关失败如何处理。
- **验收证据**：用户能看到的结果，以及证明关键规则的样例、测试或实际运行。
- **待定事项**：区分已读到的事实、合理假设和需要用户决定的业务语义；没有则省略。

通常几句话或一张小表即可。只有跨阶段工作确实需要恢复上下文时才落盘，沿用已有计划文档。对低影响的注释、文案或局部修正，直接实施并做对应检查。

**完成条件**：至少有一个可以判定对错的输入输出例子，且会改变正确性或产生不可逆影响的关键未知项已解决，或相关实施明确保持待定。

遇到未知项先查代码、配置和样本；技术实现选择由你说明理由后推进。若仍需用户决定业务含义，只问影响结果的最小问题，同时继续不依赖该答案的工作。工程约定本身不是额外的审批门槛。

涉及数据转换、算法或机器人时，读取 [数据与时间语义](references/data-pipelines.md)，补齐本次实际涉及的契约。

## 2. 把规则、执行和解释连起来

围绕本次变更明确三种责任，可放在现有函数或模块中：

1. **规则计算**：接收显式输入，返回决定和理由，例如匹配位置、被拒绝项、保留区间。
2. **副作用执行**：按这些决定读写文件、调用服务或驱动外部进程。
3. **结果解释**：把同一份决定转换为预检、日志、进度或报告。

预检和执行共用影响结果的核心规则及最终生效配置；同时用独立的预期样例检验规则自身。复用只证明行为一致，正确性仍需验收证据。

选择与任务成本匹配的预检入口。长时间、批量或高损失操作，优先提供能提前发现主要问题的检查或计划预览；简单局部操作使用现有校验。明确预检检查了什么、抽样还是全量、什么仍需实际执行才能知道。

**完成条件**：能指出每条关键规则的唯一实现位置，以及预检、执行和报告如何消费它；新抽象有当前调用方和具体收益。

## 3. 每次实现一个可验证的行为

按可观察行为切小步，每步完成适用的输入校验、正常处理、失败处理、诊断和验证。例如“缺失的可选字段按显式配置填充并报告数量”可以独立验收。

优先沿用现有模块、依赖和风格。新增依赖或跨模块改动时，说明它解决的具体限制；把与当前验收无关的重构留在范围外。通过按批、流式或有界队列控制实际会增长的资源，并说明阻塞、失败和结束时的行为。

合并配置文件、环境和命令行覆盖后，校验**最终生效值**。错误处理按数据完整性约定选择中止、跳过、填充或有界重试。重试需有瞬态故障依据、次数或时间上限，并考虑重复执行是否安全。

写入工作说明失败后会留下什么；有既有产物需要保护时，根据损失采用临时输出、完成标记或原子替换等机制。覆盖已有数据沿用用户授权边界，重跑优先使用隔离输出。

注释优先解释调用前提、单位和顺序、取舍原因，以及容易被后续修改破坏的约束。让关键约束同时落在类型、校验或测试中；注释不能单独保证成立。

**完成条件**：本步的正常结果和重要失败结果都可观察，且新增行为未依赖未实现的后续步骤。

## 4. 把诊断当成交付的一部分

当本次改变失败路径、校验、批量处理或进度时，读取 [诊断设计](references/diagnostics.md)，在编码前确定最有价值的失败信息。

诊断至少支持定位对象、理解违反的规则和判断后果。错误保留底层原因，上层补充文件、任务、字段等业务身份；统计包含单位、分母和生效阈值。缺失、坏数据、被策略丢弃和显式填充分别计数。

正常输出给结论和影响；详细模式提供定位所需证据。进度根据实际完成事件更新，明确“读完”“等待后台完成”“产物已关闭并检查”等阶段。

**完成条件**：针对一个代表性故障，用户只凭输出就能找到受影响对象、失败规则及下一步检查方向；总结和退出状态与实际警告、失败、部分成功一致。

## 5. 用能推翻实现的证据验收

从实现约定选验证方式，优先覆盖最可能导致错误结果的边界。业务规则改动检查正常样例及相关的边界、无效输入或失败路径；修 bug 时保留能区分旧行为与正确行为的复现。测试期望来自契约或独立计算，避免调用被测逻辑生成期望值。

按任务选取已有测试、最小合成数据、真实小样本和产物回读。对于转换输出，成功退出之外还要检查约定的形状、数量或关键值；端到端成功不能由单元测试通过推断。可逆且低影响的文字或配置说明修改，做对应检查即可。

验证失败时先保留证据、定位到最小责任模块，再修正并运行受影响检查。不要用放宽阈值、静默丢数据或删除失败断言来替代诊断；若必须改变业务规则，说明代价并遵循已获得的业务决定。

**完成条件**：本次约定的验收项各有证据，或明确标为未验证及原因。外部条件阻断的测试不计为通过；重要规则未满足时不能宣称任务完成。

## 6. 交付让用户能够判断的结果

用与变更规模匹配的说明报告：

- **行为**：现在输入什么会发生什么，重要设计取舍是什么。
- **位置**：关键改动文件或产物；必要时给出可直接使用的命令。
- **证据**：实际执行了什么、结果如何，和验收项怎样对应。
- **边界**：仅列影响使用的未验证项、已知限制和需要用户决定的事项。

对于较复杂的变更，使用“需求 → 实现位置 → 可观察结果 → 验证证据”的小表；简单改动用短段落即可。用户说不懂代码时，以具体样例和选择的后果解释，不把实现细节变成必须由用户回答的问题。
