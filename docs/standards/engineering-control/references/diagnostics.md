# 诊断设计：让输出支持下一步行动

用于新增或修改校验、失败路径、批量任务和进度。按实际风险选择下面的内容，不为普通函数统一搭建日志框架。

## 一个诊断事件应表达什么

| 信息 | 用途 | 例子 |
| --- | --- | --- |
| 对象和位置 | 找到受影响数据 | 文件、topic、字段、记录号或帧号 |
| 阶段和规则 | 知道在哪里、为什么失败 | 时间对齐；绝对时间差不得超过容差 |
| 实际值与期望 | 判断严重程度 | 98 ms；容差 10 ms |
| 后果与范围 | 判断是否能继续使用结果 | 丢弃 1/5 帧，拆为 2 个 episode |
| 下一步 | 缩小排查范围 | 检查该 topic 在指定时间附近是否缺失消息 |

下面是建议的诊断设计示例，数值用于说明，不是任何工具的固定输出格式：

```text
WARN stage=sync file=sample.mcap topic=/arm frame=2 t=0.200s
  实际 |Δt|=98.0ms，允许 <=10.0ms
  处理：丢弃该帧，在此处切分；本文件保留 4/5 帧，2 个 episode
  检查：查看 /arm 在 0.200s 附近的原始消息和时间戳
```

下一步应从证据导出。超出容差本身不能证明容差太小；检查原始消息、时钟、频率和丢帧情况后，才讨论放宽阈值造成的数据质量变化。

## 预检有明确的检查范围

对耗时较长的任务，按成本说明预检覆盖：

- 结构检查：配置、路径、编码、必需字段。
- 语义检查：字段能否解码、维度和顺序、缺失处理、时间规则。
- 运行环境检查：相关外部程序或服务是否具备实际所需能力。
- 产物检查：只能在执行后验证的数量、内容、索引与文件一致性。

这些是可选检查层，不要求每个工具都提供四个命令。报告写明执行层次及样本范围，例如“全部时间戳已检查；每个 topic 抽样 10 条数值记录；尚未验证视频完整解码”。

共享核心规则能防止预检和执行采用不同标准，但不能补上预检未检查的输入内容。最终配置变化后，旧预检结果的适用性也需重新判断。

## 聚合与退出语义

逐条错误保留适当数量的代表样例和总数。大量明细按需输出或写入单独报告；不能因截断明细而丢失错误总量。

批量校验中，各文件独立时可以继续收集失败，最后汇总。批量写入能否继续取决于共享索引和提交边界，不能直接照搬校验的继续策略。

明确状态：通过、带警告通过、部分成功、失败。若项目约定“有警告仍返回成功”，总结也应显示警告数量和损失。错误数、坏帧数、受影响 topic 数是不同统计口径，分别命名；逐 topic 坏帧相加可能重复计数，不能当作全局丢弃帧数。

默认输出结论、关键影响和定位入口。详细模式展示相关对象、阈值和样例。定位信息保留必要身份，避免将凭证或整份敏感载荷写入日志。

## 错误链和真实进度

在拥有上下文的层补充身份，例如“文件 → 相机 → 编码器 → 外部程序错误”。避免每层重复打印同一异常；由合适的命令或任务边界统一呈现。

进度计数名称对应真实事件：“已提交”不等于“已写入”，写入管道不等于编码完成。总量未知时显示已处理数量；等待后台任务时显示阶段；完成信号在相关资源关闭、后台错误取回和必要一致性检查之后发出。

当新增这类行为时，用代表性异常检查诊断是否兑现契约：例如一个超差记录、一个缺失字段、一个外部进程失败。断言关键身份、实际值、后果和退出结果，不必把所有空格或整段措辞固定成快照。
