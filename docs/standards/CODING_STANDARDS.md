## 1. 模块边界

- **1.1** 三层，只能从上往下依赖：入口层（`rdp.api`、`rdp.ops`）→ 领域层 → 基础层（数据库、配置、日志等）。〔机：import-linter〕
- **1.2** 领域模块之间默认互不 import。确实需要时，在 import-linter 合约里登记方向，不能成环。〔机：import-linter〕〔审：登记的方向在工单或 spec 里有依据〕
- **1.3** 领域层和基础层不 import 入口层，也不 import FastAPI（ADR 0001："核心函数不依赖入口"）。〔机：import-linter；FastAPI 装上以后加这条合约〕〔审：领域函数的参数和返回值里没有 `Request`、`Response`、`HTTPException` 这类 Web 类型〕
- **1.4** 进程边界（ADR 0005、0006）：Web 进程只读导航层本身，不写导航层，也不访问存储根。写导航层、碰存储根的代码只在 worker 的作业里运行。〔审：`rdp.api` 调用到的函数里，没有写导航层或访问存储根的〕模块划分定下来以后，用 import-linter 的 forbidden 合约把这条变成〔机〕。

## 2. 规则与副作用分离

适用于：写导航层、批量处理、作业，以及网页上先预览、再确认的操作。简单的局部操作用现有的校验即可，不必拆。

- **2.1** 先算计划，再执行（engineering-control §2）。`plan_*` 只读，接收显式输入，返回决定和理由：要建哪些链接、要改哪些字段、拒绝了什么、为什么。`apply_*` 只按计划执行，不重新做决定。〔审：`plan_*` 的 `Side Effects:` 是"无"；`apply_*` 里没有决策逻辑〕
- **2.2** 预览、执行、报告用同一份计划，不各自重算。每条关键规则只有一处实现。〔审：能指出每条关键规则实现在哪个函数里〕
- **2.3** 计划记下它是基于什么状态算出来的。执行时，拿到导航层写锁之后、写之前再核对一次；对不上就以"冲突"失败，什么都不写（ADR 0005）。〔审〕
- **2.4** 预览写明检查了什么：哪些是全量检查，哪些是抽样，哪些要执行之后才知道（engineering-control diagnostics「预检有明确的检查范围」）。〔审〕
- **2.5** 校验的是最终生效值：配置文件、环境变量、页面参数合并之后再校验，报错时指出生效值来自哪里。〔审〕
- **2.6** `apply_*` 的 `Side Effects:` 写明失败时留下什么。要保护已有产物时，用临时文件加原子替换、完成标记这类做法：失败时只留下认得出来的半成品，或者什么都不留。〔审〕
- **2.7** 随数据规模增长的东西要有上界：文件列表、工具输出、诊断明细，按批、流式或有界队列处理。规模参考 ADR 0006：agibot_world_alpha 一个数据集就有 753 万个文件和目录。〔审〕
- **2.8** 重试只用于有依据的瞬态故障，有次数或时间上限，并且重复执行是安全的。〔审〕
- **2.9** 新加的抽象（基类、协议、注册表、配置项）有当前的调用方。〔审〕

## 3. 函数契约

六项的格式、不适用的项写"无"、函数级文档只写在 docstring 里，见规则 4。本条补充适用范围、每项写到什么程度、例子和检查方式。

### 3.1 适用范围

- **公开函数**写六项。"公开"指名字不以 `_` 开头，所在的类和模块路径里也没有以 `_` 开头的部分（`__init__.py` 不算）。公开类的公开方法同样算公开函数。`__init__` 按它所在的类算：类是公开的，`__init__` 就按公开函数查。
- **私有函数**至少写一句职责。`@property` 也写一句，单位和取值范围写进这一句。
- **数据类**（`@dataclass`）写 `Attributes:`，每个字段写含义、单位和取值范围。
- 生成器用 `Yields:` 代替 `Returns:`。
- 不查：`@overload` 的签名（文档写在实现上）、嵌套函数、`tests/` 下的测试函数（测试的要求见第 7 条）。`src/` 里名字以 `test_` 开头的公开函数照样要写六项。

〔机：`scripts/check_contracts.py` 查小节有没有、顺序对不对、内容是不是空的；ruff 的 docstring 规则查 `Args:` 等小节和签名是否一致。`test_` 开头的函数，只有文件在仓库根的 `tests/` 下时才跳过，按解析软链接后的绝对路径判断〕

### 3.2 每项写到什么程度

〔审：逐项看内容是否合格，不只看有没有〕

- **首行**：一句话写职责，即做什么，不写怎么做。
- **`Args:`**：每个参数一条，写含义；单位（时间、大小、频率、角度等）；取值范围或约束（非空、绝对路径、≥ 0）；`None` 代表什么。
- **`Returns:`**：写含义，不只是重复类型。集合写顺序、会不会为空；`None` 代表什么。
- **`Raises:`**：写异常类和触发条件。新异常属于 6.2 的哪一类，由它的基类看出来。有意让它穿过的下层异常也写上。
- **`Side Effects:`**：写改了什么（文件、导航层、数据库、外部进程、网络），以及失败时留下什么。写运行日志不算副作用；写操作日志算，因为它写数据库。只读的函数写"无（只读 …）"，说明读了什么。
- **`Time Semantics:`**：时刻用什么时区；时长、超时的单位和取值；会阻塞多久；轮询或重试的间隔；对先后顺序的假设，例如"调用方已持有导航层写锁"。

### 3.3 骨架与实现

- **3.3.1** 骨架阶段函数体只有 `raise NotImplementedError`，这一句不写进 `Raises:`。它不是契约的一部分，写进去的话，实现时就得改契约。〔机：骨架阶段 `make check` 能全绿〕
- **3.3.2** 实现和 docstring 一致；没有工单之外的公开函数（0003 第七节）。〔审〕

### 3.5 前端 TSDoc

导出的函数、hook、组件写 TSDoc，同样六项：

- 首行写职责；然后是 `@param`、`@returns`、`@throws`。组件的 `@param` 写 `props`，props 类型的每个字段另写 TSDoc，含单位和取值范围。

- 不适用的项写"无"。

- 没有参数的函数不写 `@param`。

## 4. 中文注释

哪些地方必须写注释、用什么语言，见规则 5。本条给写法和检查方式。

- **4.1** 每个模块开头的 docstring 写：属于哪一层，负责什么，不负责什么，相关的 ADR 或工单。〔机：ruff D100、D104 查有没有〕〔审：写的是职责和边界，不是把模块名翻译一遍〕
- **4.2** 注释写"为什么"：原因、出处（ADR、工单或 brief 的编号）、不这样做会怎样。只复述代码的注释删掉。〔审〕
- **4.3** 关键约束同时落在类型、校验或测试里，注释只说明它为什么存在。〔审〕
- **4.4** 改了行为的地方，相邻的注释和 docstring 一起改。〔审：diff 里行为变了的地方，注释没有过期〕
- **4.5** 不用的代码直接删，要找回靠 git 历史。〔机：ruff ERA001〕
- **4.6** 反例和正例：

| 地方 | 反例 | 正例 |
|---|---|---|
| 常量和阈值 | `POLL_INTERVAL_S = 1.0  # 轮询间隔` | `# 网页每秒轮询一次（ADR 0001）；worker 每秒最多写一次进度（ADR 0005），再快也拿不到新数据。` |

## 5. 时间

- **5.1** 时刻一律用带时区的 `datetime`。程序内部、数据库、接口里都用 UTC，只在显示时换成本地时间：运行日志写带时区的本地时间，例如 `2026-10-21 16:15:02.123+08:00`（09）；网页按浏览器的本地时间显示。〔机：ruff DTZ〕〔审〕
- **5.2** SQLite 没有带时区的时间类型：带时区的 `datetime` 存进去会丢掉时区，读回来不带时区。由数据库层统一转换：写入前换成 UTC，读出时补上 UTC，其他层见不到不带时区的 `datetime`。在 M0 的数据库工单里落地。〔审〕
- **5.3** 时长优先用 `timedelta`。用数字表示时长、间隔、超时、大小时，名字带单位后缀（`timeout_s`、`interval_ms`、`size_bytes`），或者在 docstring 里写明单位。〔审〕
- **5.4** 同一进程里测时长、算超时、算速度，用 `time.monotonic()`。要存进数据库、或者跨进程比较的时间（心跳、作业的起止时间），用 UTC 墙钟：`monotonic()` 的起点没有定义，换个进程或重启以后就没法比。〔审〕
- **5.5** 会阻塞的调用（访问存储根、外部进程、网络）都有超时，超时值是带单位的具名常量或配置项。访问存储根超时，按离线处理（ADR 0006）。〔审〕
- **5.6** 处理数据里的时间戳（转换、同步、录制）时，另按 `docs/standards/engineering-control/references/data-pipelines.md` 写清时间戳的来源、单位、时钟关系和对齐规则。〔审〕

## 6. 错误与诊断

术语（诊断、警告、条目、作业结果、上报协议）见 `GLOSSARY.md`；工具和平台共用一套诊断，见 ADR 0004。6.1–6.11 依次对应 09 号票 Answer 里第 6 条的 11 个要点。

- **6.1 一种诊断对象**：字段是级别、类别、阶段、来源、对象（键值对）、规则、实际、期望、后果、下一步。运行日志里的文本、接口返回的 JSON、工具上报事件解析后的结果，都用它，不另起格式。〔审：新增的诊断由这个对象构造，没有另拼的报错字符串〕
- **6.2 四类异常**：新异常从四个基类之一派生：输入或数据问题、冲突、外部失败、程序缺陷。不按模块另建平行的异常体系。接口的统一异常处理按类别映射 HTTP 状态码，见下表。新的状态码先改这张表，再改代码。〔机：测试逐项核对异常类的状态码和这张表一致〕〔审：接口里没有绕过四类异常、直接返回错误状态码的地方〕

  | 状态码 | 类别 | 什么时候用 | 响应 |
  |---|---|---|---|
  | 400 | 输入或数据问题 | 默认：请求合格，但内容或数据有问题，例如数据集缺文件 | problem+json，带诊断 |
  | 404 | 输入或数据问题 | 要操作的对象不存在，例如数据集、账号、作业编号查不到 | problem+json，带诊断 |
  | 422 | 输入或数据问题 | 请求参数不合格（类型、范围、缺项）；不回显原值 | problem+json，带诊断 |
  | 409 | 冲突 | 和当前状态冲突，例如预览之后数据集被别的作业改过 | problem+json，带诊断 |
  | 502 | 外部失败 | 依赖的外部东西出错，例如存储根离线、外部工具失败；密码哈希资源繁忙、排队超时（第 6 张，Argon2 并发上限） | problem+json，带诊断 |
  | 500 | 程序缺陷 | 平台自己的 bug，以及任何没被归入前三类的异常 | problem+json，一句话加错误编号，不带内部细节 |
  | 401 | 输入或数据问题 | 没登录、会话过期或已被撤销（第 6 张）；登录时账号或密码错误也用 401，不区分哪一个错 | problem+json，带诊断；同时清掉会话 cookie |
  | 403 | 输入或数据问题 | 登录了但不允许：角色不够；必须先改密码；写请求的 `Origin` 缺失或不是本站（第 6 张） | problem+json，带诊断 |
  | 429 | 输入或数据问题 | 同一账号连续输错密码，等待期内又来登录（第 6 张 G2） | problem+json，带诊断；`Retry-After` 头写还要等几秒，向上取整 |
  | 404 | （框架） | `/api` 下的路径不存在（已登录时；没登录先得到 401） | 保持框架原格式 `{"detail": …}`；前端显示"请求失败" |
  | 405 | （框架） | `/api` 下路径存在但方法不对（第 6 张 S1），带 `Allow` 头 | 保持框架原格式；前端显示"请求失败" |
  | 405 | （框架） | `/api` 以外的页面路径用了 GET 以外的方法 | 保持框架原格式；前端显示"请求失败" |

  - 程序缺陷之外的三类，子类只能用表里本类别的状态码；输入或数据问题的子类在 400、401、403、404、422、429 里选，其他两类不能改。
  - `/api` 下请求的判定顺序（第 6 张）：写请求先查 `Origin`（403）→ 公开白名单（健康检查、登录）→ 认证（401）→ 必须先改密码（403）→ 角色（403）→ 路由（404、405）。
  - 每个错误响应都带 `error_id`，就是这次请求的请求编号（响应头 `X-Request-ID`），用来在运行日志里找完整报错。
- **6.3 补上下文**：在掌握对象身份的那一层补，例如"文件 → 相机 → 编码器 → ffmpeg 退出码"。重新抛出时一律写 `raise … from e`。中间层只补上下文、不打日志；只在三处边界记录和呈现：接口的统一异常处理、作业执行器的最外层、运维命令的入口。〔机：ruff B904〕〔审：三处边界以外，没有"先打日志再重新抛出"〕
- **6.4 logger**：每个模块写 `logger = logging.getLogger(__name__)`。消息写中文，上下文写成 key=value。作业编号和请求编号由日志配置通过 contextvars 自动带上，不在函数之间手工传递。〔机：ruff T20，禁止 print〕〔审〕
- **6.5 级别**：
  - ERROR：某个操作、作业或条目失败了。
  - WARNING：结果打了折扣，但作业继续。消息里必须写清后果。
  - INFO：生命周期节点，例如启动、阶段切换、作业结束摘要。
  - DEBUG：细节，默认不输出。

  〔审〕
- **6.6 聚合**：同一类诊断只保留前 N 条样例，N 用具名常量并注明含义，总数始终完整。不同口径的计数（失败条目、警告、丢弃帧）分开命名，不合并成一个"错误数"。〔审〕
- **6.7 进度**：只在真正完成的事件之后更新，例如数"已写入"，不数"已提交"。写入频率每秒最多一次。总数未知时留空，不编一个总数。〔审〕
- **6.8 作业结果**：只能由那一个计算函数根据计数得出，别处不直接赋值。〔审：diff 里没有直接给作业结果赋值的地方〕
- **6.9 外部进程**：完整捕获 stdout 和 stderr。失败时附上命令、退出码或信号、stderr 的最后几行。工具的上报事件是不受信任的输入：逐行校验，不合格的行原样保留并记一条警告，作业执行器不能因此崩溃。〔审〕
- **6.10 敏感信息**：密码、会话令牌、cookie、SSH 私钥不进日志和报错，也不把整份请求或载荷写进日志。〔机：ruff S（bandit）能抓到一部分硬编码的密码〕〔审〕
- **6.11 测试**：每新增一类诊断，至少写一个代表性故障的测试，断言对象身份、实际值、后果和最终的作业结果。不对整段文本做快照（engineering-control diagnostics）。〔审〕

## 7. 测试

测试只用临时目录和 `tests/` 里的假导航层，见规则 1。每个测试写明它验证哪条契约行为，见规则 5；写在测试函数的 docstring 里。

- **7.1** 只测关键行为（负责人 2026-11-01、2026-11-08）：工单的验收条件、权限和安全底线、会写坏数据或导航层的路径、用户能看到的报错。docstring 里的其他条目不要求逐条配测试，罕见情况的防御分支不写测试。〔审：对着验收条件逐条找到对应的测试〕
- **7.2** 期望值来自契约或独立计算（手算、换一种方法算、真实样本里的已知值），不调用被测逻辑来生成。〔审〕
- **7.3** 用边界值反推测试输入：先确定规则，再选能区分正确实现和错误实现的输入，例如阈值本身和阈值加一个单位、长度 N−1 和 N、整体缺失和局部断档。更多例子见 `engineering-control/references/data-pipelines.md` 的「验证例子从规则反推」表。平台里的例子：
  - 作业结果：失败 0 且警告 0、失败 0 且警告 1、部分条目失败、全部失败或中止，四种结果各一个用例（09）。
  - 断链：存储根在线、目标不存在，算断链；存储根离线时，同一条链接不算断链（ADR 0006）。
  - 进度：总数未知时 `total` 为空，界面不显示百分比（09）。

  〔审〕
- **7.4** 样本从真实数据里截取一小段，放在 `tests/fixtures/`（ADR 0003）。截自哪里、怎么截的，写在生成它的脚本或 `conftest.py` 的注释里。〔审〕
- **7.5** 时间相关的逻辑把时钟作为参数传入，测试里传固定的时钟。测试不联网，也不依赖执行顺序。〔审〕
- **7.6** 骨架阶段的测试先跳过（`pytest.skip`）；实现提交里不留骨架阶段的跳过。被外部条件挡住的测试不算通过，跳过时写明原因。〔审：看 `pytest -rs` 列出的跳过清单〕
- **7.7** 修缺陷时，留一个能区分旧行为和正确行为的测试。〔审〕
- **7.8** 测试没过时，先保留证据，定位到最小的责任模块再修。改阈值、删断言属于改契约，按 `docs/agents/codex-workflow.md` 的「契约变更」处理。〔审〕
- **7.9** 不设覆盖率门槛（03）。评审看 7.1，不看覆盖率数字。
- **7.11** 同一个行为只在一层测（2026-11-08）：后端优先在 API 层测，前端优先在页面层测；纯函数只在逻辑复杂（时间换算、边界判断、解析）时单独测。不在服务层、接口层、页面层重复测同一条规则。〔审〕
- **7.12** 不测实现细节（2026-11-08）：不断言内部函数的调用次数和参数、私有状态、日志原文、docstring 或注释文本；这类测试一重构就要改，又抓不到真缺陷。替身只用在系统边界（时钟、子进程、网络、真实数据盘）。〔审〕
- **7.13** 一个测试一个行为，名字直接写行为；同一规则的多组输入用参数化，不复制测试函数。不写只为记录过程的证据文件（如 `*_tdd_evidence.json`）。〔审〕
- **7.10** 先红后绿只用于修缺陷（2026-11-08 负责人同意）：修缺陷时先写能重现缺陷的测试，单独跑一次看到它失败，再修到通过，交付时贴出那次失败的输出。新功能不要求逐个测试先跑失败，测试是否真能抓错由评审的变异抽查验证。〔审：修缺陷票看失败输出；其余看变异抽查〕

## 8. 豁免

豁免只针对单条规则，并写明理由，见规则 6。本条写各工具的写法和检查方式。

- **8.1 写法**：
  - ruff：`# noqa: <规则码>`，理由写在同一行豁免后面的 `# 理由：…`，或者上一行的注释里。
  - basedpyright：`# pyright: ignore[<规则名>]`，理由的写法同上。不用 `# type: ignore`。
  - ESLint：`// eslint-disable-next-line <规则名> -- 理由`。
  - TypeScript：`// @ts-expect-error 理由`，不用 `@ts-ignore`。

  〔机：不带规则码的豁免、多余的豁免都会让 `make check` 失败。后端：ruff 的 PGH003、PGH004（禁止不带规则码的 `type: ignore` 和 `noqa`）、RUF100（多余的 `noqa`）；basedpyright 的 `reportIgnoreCommentWithoutRule`、`reportUnnecessaryTypeIgnoreComment` 设为 error，`enableTypeIgnoreComments = false`，所以 `# type: ignore` 不起作用。前端：`reportUnusedDisableDirectives` 让多余的 `eslint-disable` 失败；eslint-plugin-eslint-comments 的 `no-unlimited-disable`、`require-description` 让不写规则名、不写理由的 `eslint-disable` 失败；`ban-ts-comment` 禁止 `@ts-ignore`、`@ts-nocheck`，`@ts-expect-error` 必须带说明〕
- **8.2 配置里的豁免也算**：`pyproject.toml` 的 per-file-ignores、basedpyright 的规则开关、import-linter 的 `ignore_imports`、ESLint 配置里关掉的规则。每一条旁边用注释写理由。这些都在受保护文件里，只有工单允许时才能改（规则 3）。〔审〕
- **8.3 评审时**：把 diff 里新增的豁免全部列出来，逐条判断是否只针对单条规则、理由是否成立、能不能改代码消掉。〔审：`git diff <基准> | grep -nE 'noqa|pyright: ignore|eslint-disable|ts-expect-error|per-file-ignores|ignore_imports'`〕

## 9. 依赖

先用现成的、新增依赖要审批，见规则 7。本条写评审时怎么查，以及申请的流程。

- **9.1 重复造轮子**：diff 里每个自己写的通用功能（解析、重试、加锁、路径处理、时间换算、哈希、序列化、子进程管理、轮询……），按标准库 → 已批准的依赖 → 成熟的第三方库的顺序找现成的实现。有合适的，打回改用；确实要自己写的，看模块注释里有没有写为什么不用现成的。〔审〕常见的例子：

  | 要做的事 | 先看 |
  |---|---|
  | 读 TOML 配置 | `tomllib` |
  | 运行日志按天切分、保留 30 天 | `logging.handlers.TimedRotatingFileHandler` |
  | 单实例的排他文件锁 | `fcntl.flock` |
  | 会话令牌、令牌哈希 | `secrets`、`hashlib` |
  | 密码哈希 | argon2-cffi（已批准） |
  | 写文件时不留半截 | `tempfile` 加 `os.replace` |
  | 子进程带超时 | `subprocess.run(timeout=…)` |
  | 请求和响应的校验、序列化 | pydantic（随 FastAPI 一起装） |
  | 前端轮询和缓存 | TanStack Query 的 `refetchInterval`、`staleTime` |
  | 前端页签、筛选条件 | TanStack Router 的 search params |
  | 界面组件 | Ant Design（ADR 0002） |

- **9.2** import 的第三方包，必须是 `pyproject.toml`（前端是 `package.json`）里直接声明的依赖。传递依赖（例如随 FastAPI 来的 starlette）要直接 import 时，先用直接依赖的再导出；没有再导出的，走依赖申请。pydantic 已在 03 号票点名批准，第一次直接 import 时，由 Claude 把它声明为直接依赖即可。〔机：没装的包，basedpyright 报找不到模块〕〔审：有没有直接 import 传递依赖〕
- **9.3** 03 号票 Answer「M0 首批依赖清单」里的包已获批准，不用再申请。第一张用到它的工单派工前，由 Claude 安装并做依赖提交。
- **9.4** 申请和安装：
  1. Codex 停下，写依赖申请（内容见规则 7）。
  2. Claude 核实维护状况（最近一次发布、是否已归档）、许可证、体积、传递依赖（会不会带进 torch 这类重型包，见 ADR 0003）。
  3. 负责人批准。
  4. Claude 用 `uv add` 或 `pnpm add` 安装，单独做一次依赖提交（`docs/agents/codex-workflow.md`「提交」），记进工单的 Comments。锁文件入库。
- **9.5** Codex 的改动里没有依赖声明和锁文件的变化。〔机：评审时的文件归属检查〕

## 10. 前端

前端检查链是 `make check` 的第 7–11 步，全部是〔机〕：OpenAPI 和生成类型的过期检查（改了接口先跑 `make api-types`），TypeScript 严格模式加 `noUncheckedIndexedAccess`，ESLint 的 `strictTypeChecked` 加 react-hooks 和 jsdoc 规则，Prettier，Vitest 加 React Testing Library。v1 不做浏览器端到端测试（03）。TSDoc 见 3.5。

- **10.1** 请求统一经 openapi-fetch 生成的客户端发出，由 TanStack Query 管理。页面和组件里不直接调用 `fetch`。〔机：ESLint `no-restricted-globals` 禁止 `fetch`、`window.fetch`、`globalThis.fetch`，唯一的例外是 `src/api/` 里的客户端工厂〕
- **10.2** 接口类型只用 openapi-typescript 从 OpenAPI 生成的类型，不手写重复的接口类型。〔机：`make check` 检查生成的类型有没有过期（ADR 0001）〕〔审：没有手写的接口类型〕
- **10.3** 轮询间隔、缓存时间写成具名常量，单位写进名字（例如 `JOB_POLL_INTERVAL_MS`），注释写明出处（约 1 秒一次，ADR 0001）。〔审〕
- **10.4** 前端里的地址一律写相对路径（`/api/...`），不写协议和主机名（ADR 0001：M5 要上 HTTPS）。〔审〕
- **10.5** 诊断和报错，用同一个组件渲染接口返回的诊断对象（6.1）：输入或数据问题显示五段卡片，程序缺陷显示一句话加错误编号（09）。前端不自己拼报错文字。〔审〕
- **10.6** 需要能刷新、能分享的页面状态（页签、筛选条件）放在 URL 查询参数里，用 TanStack Router 的类型化 search params（ADR 0002）。〔审〕

### 10.1 样式（负责人 2026-11-01："前端的代码编写方式，也请工程规范化"；方案见 ADR 0010）

- **10.7** 颜色、圆角、间距、阴影、z-index 只用 `src/web/src/shell.css` 开头定义的 `--rdp-*` 变量，页面 CSS 里不写死色值和魔法数字。需要新值时，先在 `shell.css` 里加变量并写注释。〔审〕
- **10.8** 先用 antd 组件和它的属性（`Space`、`Flex`、`Typography`、`size`、`type`），不够用再写 CSS 类。不手写 antd 已有的组件。〔审〕
- **10.9** 静态样式写成 CSS 类，不写 `style={{…}}`。内联 style 只用于运行时才算得出的值（进度百分比、拖拽位置），而且写注释说明为什么。〔审；存量的内联 style 等其他线合并后另开票清理，届时加 ESLint 规则改成〔机〕〕
- **10.10** 每个模块的样式放在该模块目录下的一个 CSS 文件里，由该模块的组件 import，例如 `datasets/browser.css`。全局样式只放在 `shell.css`。类名用 kebab-case，以模块名开头（`browser-`、`creation-`、`app-`），选择器嵌套不超过三层，不按标签名或 DOM 位置写选择器。唯一的例外是给不能改 JSX 的第三方或既有结构套样式，这时要写注释。〔审〕
- **10.11** `!important` 只用于覆盖内联 style 或 antd 无法用变量改的规则，每处写注释说明原因。〔审〕
- **10.12** 样式不能改变可访问性和可测性：不用 CSS 隐藏 DOM 里已有的提示和诊断信息；`:focus-visible` 必须有可见的焦点环；当前状态不能只靠颜色区分；告警和错误的醒目程度不能调低。〔审〕
- **10.13** 深浅色模式、`prefers-reduced-motion`、`prefers-reduced-transparency` 的降级都只在 `shell.css` 里通过重定义变量实现，页面 CSS 不写自己的媒体查询（响应式断点除外）。〔审〕
- **10.14** 页面布局（负责人 2026-11-02 定，见 `.scratch/ui-style/layout-decisions.md`）：
  - 页面结构用 antd 现成组件搭：`Card`、`Flex`、`Row`/`Col`、`Descriptions`、`Collapse`、`Affix`、`Breadcrumb`、`Tag`。不自己写组件，也不用 CSS 按 DOM 位置拼结构。不引入新组件库。
  - 骨架统一为：页头 → 筛选卡 → 内容卡。页头是 `Breadcrumb` 小标签加 `Typography.Title`，操作按钮和标题同一行、靠右。
  - 组与组之间用一张卡片隔开，卡片里再细分用小标题加细分隔线，不套卡片。
  - 每块只有一个主样式按钮，其余是默认按钮或文字按钮，全部保持可见。不用"更多"菜单，因为按名字找按钮的测试会失败。〔审〕
- **10.15** 间距只用 `--rdp-space-*` 的七档：4/8/12/16/24/32/48。组内用 ≤16，组与组之间用 ≥24。质感参考 shadcn/ui：卡片用细边框、不用阴影；颜色以黑白灰为主；主按钮是墨色（深色模式反成近白），强调蓝只给链接、选中状态和焦点环（ui-style 第 08 张，负责人 2026-11-05 授权）；数字和标题用大字号，说明文字用灰色小字。小标签、表头、卡片标题、数字用等宽字体 `--rdp-mono`，正文用 `--rdp-font`；字体随前端打包在 `src/web/src/fonts/`，不从外网加载。〔审〕
