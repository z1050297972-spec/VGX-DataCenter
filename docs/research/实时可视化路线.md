# 实时可视化路线：机器人相机画面 + 目标/观测关节曲线

- 对应决策票：`.scratch/platform-v1/issues/06-live-viz-route.md`
- 调研日期：2026-10-21。文中的版本号和日期都以这一天为准。
- 一手来源：各项目的官方仓库（源码、README、LICENSE、发布记录）、官方文档、rosdistro、PyPI/npm registry，以及 ROS 2 官方文档源码。出处编号 `[S#]` 见文末。
- 本机核对：只读解析了 `/mnt/dataset2/R1_lite_table_withdrawing_mcap` 里的两份 MCAP，统计各话题的消息大小、频率和编码；从中拷出 30 帧 JPEG、60 帧 H.264 到 scratchpad，用 ffmpeg 做了重编码实验（方法见附录 A）。没有写 `/mnt`，没有安装任何包，也没有连接机器人。
- 输入约束：0002 的 F8、F10，0001 的原始需求 (5)，以及 02 票里负责人"前端用 React"的初步意见。

## 结论速览

1. **所有路线都要在机器人上放一个"桥"，Wi-Fi 上只走 TCP（WebSocket/HTTP/gRPC），不走 DDS。** ROS 2 官方文档写明：DDS 在 Wi-Fi 上传大消息会因 IP 分片丢失而"卡住"，组播发现在 Wi-Fi 上也不可靠 [S27]。工作站现在其实可以原生装 ROS 2 Lyrical（2026-05 发布，Ubuntu 26.04 为 Tier 1）[S29]。但 ROS 2 不保证跨发行版通信 [S28]，机器人上是 Jazzy，所以这条路也不改变上面的结论（§1.3）。
2. **R1 Lite 全帧率原样转发要约 107–112 Mbit/s。** 用的是三路相机：head_left 约 15 Mbit/s，两路腕部约 41–52 Mbit/s。头部相机话题虽然是 `sensor_msgs/CompressedImage`，但 `format = "h264"`（1920×1536，GOP 10，没有 B 帧）。腕部是 1280×720、质量约 95 以上的 JPEG [S34]。降到 640×360 的普通质量 JPEG 后，每帧从约 167 KB 降到约 9 KB（§1.1）。
3. **现成桥都不能直接覆盖两台机器人。**
   - web_video_server 和 Lichtblick 都解不了"装在 CompressedImage 里的 H.264"[S24][S15]。
   - foxglove_bridge 不做降采样或转码（转码只在付费的 remote access 网关里做）[S1][S5]。
   - AutoLife 的关节是 JSON 字符串。相机在 SHM 里，可选的 SHM→ROS 桥发出的是**未压缩** `bgr8`，一路 1280×720@30 约 663 Mbit/s [S31]。
   - 所以不管选哪条路线，都要自写一个机器人侧的小 relay，把话题规整成"降采样后的图像 + 标准的目标/观测关节"。
4. **推荐路线 A'：foxglove_bridge + 自写 `viz_relay` 节点（机器人侧），工作站自托管 Lichtblick，用 iframe 嵌进 React 页面。**
   - 依据：Foxglove WebSocket 协议是订阅制，只传前端正在看的话题。Lichtblick 现成提供话题选择、多序列曲线和 H.264 解码。两台机器人用同一个查看器和同一套布局。全部依赖都是 MIT/MPL-2.0/BSD，且都在活跃维护。
   - 代价：iframe 集成只能靠 URL 参数控制；H.264 解码要求 HTTPS 或 localhost；relay 要自己写和维护；Foxglove 协议的 JS 客户端库已经停止维护。
   - 备选是 Rerun（官方 React 组件，但 viewer 和 SDK 版本必须一致，且推送全部数据）。详见 §4。

## 1. 影响所有路线的共性事实

### 1.1 R1 Lite 的真实话题负载（本机 MCAP 实测）

数据来自两份录制：2026-10-11 一份 52.1 s，2026-10-09 一份 100.9 s。两份结果一致，下表取前者，括号里是后者 [S34]。录制内容和机器人上的实时话题应当一致，但**没有在真机上核实**，这一步交给 05 票。

| 话题 | 类型 / 编码 | 分辨率 | 平均每帧 | 频率 | 码率 |
|---|---|---|---|---|---|
| `/hdas/camera_head/left_raw/image_raw_color/compressed` | `CompressedImage`，`format="h264"`，High profile | 1920×1536 | 62 KB（I 帧 122 KB，P 帧 56 KB） | 30 Hz | 15.0 Mbit/s |
| `/hdas/camera_wrist_left/color/image_raw/compressed` | `CompressedImage`，`"bgr8; jpeg compressed bgr8"` | 1280×720 | 174 KB（184 KB） | 30 Hz | 41.5（44.1）Mbit/s |
| `/hdas/camera_wrist_right/color/image_raw/compressed` | 同上 | 1280×720 | 211 KB（219 KB） | 30 Hz | 50.1（52.4）Mbit/s |
| `/hdas/feedback_arm_{left,right}` | `JointState` | — | 204 B | 200 Hz | 各 0.33 Mbit/s |
| `/hdas/feedback_gripper_{left,right}` | `JointState` | — | 92 B | 200 Hz | 各 0.15 Mbit/s |
| `/motion_target/target_joint_state_arm_{left,right}` | `JointState` | — | 84 B | 约 190 Hz | 各 0.13 Mbit/s |
| `/motion_target/target_position_gripper_{left,right}` | `JointState` | — | 44 B | 约 20 Hz | 可忽略 |

其他观察：

- **头部 H.264 的码流结构**：每 10 帧一个关键帧（约 0.33 s）。关键帧消息里依次是 SPS、PPS、IDR 三个 NAL，切片只有 I 和 P，没有 B 帧。这正好满足 `foxglove_msgs/CompressedVideo` 的要求：Annex B、一条消息一帧、关键帧带 SPS、不支持 B 帧 [S9]。也满足 Rerun `VideoStream` 的要求（不支持 B 帧）[S19]。所以这一路可以**不重编码，只换个消息外壳**。
- **腕部 JPEG 的质量**：量化表的值是 1–2，说明质量约 95 以上。用 ffmpeg 按普通质量（`-q:v 5`）重编码：
  - 1280×720 时，平均每帧从 167 KB 降到 23.6 KB。
  - 缩到 640×360 时降到 8.9 KB。按 15 fps 算，一路约 1.1 Mbit/s。
- **头部 H.264 重编码**：缩到 640×512，用 libx264（`zerolatency`，CRF 28）重编码后约 0.25 Mbit/s。这份样本的画面基本是静止的桌面，运动多时码率会高不少，这个数只能说明量级。
- **合计**：R1 Lite 用到的三路相机（head_left + 两路腕部）全帧率原样转发约 **107–112 Mbit/s**。8 个关节话题合计约 **1.2 Mbit/s**（CDR 原样）。
- **mcap2lerobot 的同步基准**是 head_left，也就是 H.264 这一路 [S35]。实时画面里最该看到的恰好是现成工具最难处理的一路。

### 1.2 AutoLife 的相机与关节（来自 CB_Autolife_Data_Collector，main 分支，2026-10-19 推送）

- **相机都在 SHM 里**，路径是 `/dev/shm/camera_image_buffer_<名>`，另有元数据文件 `camera_metadata_struct_<名>`。SDK 还有一种较新的 SHM2 双缓冲格式 [S31: `camera_config.py`、`shm_camera.py`]。
  - 手部相机（`hand_left`、`hand_right`）在 SHM 里存的是 **JPEG**，读的是 `hand_*_jpeg` 这两路。默认 1280×720@30。
  - 头部的 `rgbd_head_color` 和 `rgbd_head_depth` 是**原生未压缩**格式（BGR/RGB/Z16）。
- **仓库里已经有一个 SHM→ROS 的可选桥** `shm_camera_topic_bridge.py`。它把帧发到 `/camera/<名>/image_raw`，消息类型是 `sensor_msgs/Image`，QoS 为 BEST_EFFORT、depth 1。注意它会**先把 JPEG 解码，再按 `bgr8` 原始像素发出去** [S31]。按 1280×720×3 字节×30 fps 算，一路约 663 Mbit/s，绝对不能直接跨 Wi-Fi 传。F8 说的"不一定有 ROS 图像话题"现在应该改成：有一个可选的桥，但它发的是原始图像。
- **关节**：状态话题 `/topic_arm_whole_body_and_gripper_current_joints_status_<id>` 是 JSON 字符串，**里面同时有实测值**（如 `left_arm_joint_state`）**和控制器目标值**（如 `left_arm_target_joint_state`）。另外还有两个目标命令话题：`/topic_arm_whole_body_target_joints_position_<id>` 和 `/topic_arm_gripper_target_joints_position_<id>` [S31: `recorder_config.py`、`robot_schema.py`]。这两个 JSON 话题的发布频率和消息大小在代码里查不到，交给 05 票实测。

### 1.3 为什么不让工作站直接进 DDS

- ROS 2 官方的 DDS 调优文档写道："Sending data over lossy (usually WiFi) connections becomes problematic when some IP fragments are dropped…"。丢分片后，内核默认要等 30 s 才放弃重组，256 KB 的缓冲占满后连接就像"挂起"一样。官方的对策是改用 best-effort QoS 和调内核参数 [S27]。
- Discovery Server 文档也写明，组播发现"may not work reliably in some scenarios, e.g. WiFi" [S27]。
- **ROS 2 Lyrical Luth**（2026 年 5 月发布，LTS，支持到 2031 年 5 月）把 Ubuntu Resolute（26.04）列为 amd64/arm64 的 Tier 1，提供 deb 包 [S29]。也就是说 F10 的"工作站要用 ROS 只能走容器"已经不准确了。但官方明确说"Nodes are not guaranteed to be able to communicate across distributions"[S28]，而 AutoLife 是 Jazzy（F8），所以工作站装 Lyrical 去订阅机器人话题仍然不受支持。
- 工作站上还开着 Clash Verge 的 TUN 网卡（F10），DDS 选网卡时可能被它干扰。这一点是推断，没有验证。
- **结论**：桥放在机器人上，机器人和工作站之间只走 TCP。下面每条路线都按这个前提评估。

### 1.4 浏览器侧的两条硬约束

- **H.264 解码靠 WebCodecs，只能在 secure context 里用**。`VideoDecoder` 在 MDN 上标的是"Limited availability"，并且"available only in secure contexts (HTTPS)" [S30]。Lichtblick 的 `VideoPlayer` 会先检查 `self.isSecureContext && "VideoDecoder" in globalThis` [S15]。Rerun 的 Web Viewer 也是用 WebCodecs 解码视频 [S19]。
  - `http://localhost`、`http://127.0.0.1` 算安全来源 [S30]。所以在工作站本机打开平台没有问题；通过局域网或 tailscale 从别的机器访问时，就需要 HTTPS。
- **HTTPS 页面里嵌 `http://` 的 iframe 会被当作混合内容拦下** [S30]。如果平台以后上 HTTPS，被嵌入的查看器也必须走 HTTPS。HTTPS 页面连 `ws://` 会怎样，MDN 没写，**未查实**。

### 1.5 安全：所有现成桥默认都可写、无鉴权

- foxglove_bridge 的默认 `capabilities` 里有 `clientPublish`、`services`、`parameters`，默认绑定 `0.0.0.0` [S1]。也就是说，浏览器能往机器人话题上发消息，包括 `/motion_target/*`。只读查看时应设 `capabilities:=[]`，并用 `topic_whitelist` 限定可见话题。
- rosbridge 协议本身就支持 publish、服务调用和参数操作 [S25]。
- Foxglove SDK 的 `start_server()` 默认只绑定 `127.0.0.1`，要远程访问得显式传 `host="0.0.0.0"` [S8]。

## 2. 候选路线逐条评估

每条路线按票里的五个问题作答。带宽数字以 R1 Lite 三路相机加关节为基准（§1.1）。延迟没有任何项目给出官方实测值，表中的延迟都是按机制推算的，标为"推算"，需要用原型实测。

### 路线 A：foxglove_bridge + Lichtblick（票里的候选 1）

**机器人上装什么、跑什么**

- `sudo apt install ros-$ROS_DISTRO-foxglove-bridge`，然后 `ros2 launch foxglove_bridge foxglove_bridge_launch.xml port:=8765`，默认端口 8765 [S1]。Humble、Jazzy、Kilted、Lyrical 的包都是 3.6.2 [S3]。
- ROS 2 版的 bridge 已经并进 `foxglove/foxglove-sdk` 仓库。原来的 `ros-foxglove-bridge` 仓库只剩 ROS 1 版，处于维护模式 [S4]。
- 工作站跑 Lichtblick 的 Web 版：`docker run --rm -p 8080:8080 ghcr.io/lichtblick-suite/lichtblick:latest` [S10]，或者把它的静态构建交给平台托管。
- **只靠 bridge，两台机器人都显示不全**：
  - R1 Lite 头部是 CompressedImage 里装 H.264，Lichtblick 把 ROS `CompressedImage` 交给 `createImageBitmap(new Blob(..., {type: "image/" + format}))` 解码，`image/h264` 解不出来。只有 `foxglove.CompressedVideo` 类 schema 才走 H.264/H.265 视频解码 [S15][S14]。
  - AutoLife 只能拿到原始 `bgr8`（要先跑 SHM 桥）和 JSON 字符串（§1.2）。

**带宽和延迟的量级**

- bridge 原样转发序列化后的消息，帧头只有 1 字节 opcode、4 字节订阅 ID 和 8 字节时间戳 [S6]。本地连接不转码，转码和 Draco 压缩只在 remote access 网关里做 [S5]。
- 协议是订阅制，客户端对每个 channel 单独 `subscribe` [S6]。Lichtblick 按面板实际需要的话题订阅、退订 [S11]。没打开的话题不占带宽。
- 三路相机全开就是约 **107–112 Mbit/s**（§1.1），bridge 没有按话题限频的参数 [S1]。
- 每个客户端的发送队列 `message_backlog_size` 默认 1024 条，满了就丢最旧的 [S1]。带宽不够时延迟会先上涨，直到队列满开始丢帧。具体能涨到多少取决于队列里的消息组成，未实测。
- 延迟（推算）：带宽充足时，主要是单帧传输时间（一帧 200 KB 在 50 Mbit/s 有效吞吐下约 34 ms）加上浏览器解码，量级是几十到一百多毫秒。

**能否在同一张图上显示目标和观测**

- 能。Plot 面板一个面板可以放多条序列，每条序列用 message path 指定，例如 `/hdas/feedback_arm_left.position[0]` 和 `/motion_target/target_joint_state_arm_left.position[0]`。横轴可选"接收时间"或 `header.stamp`，有"Range (seconds)"滑动窗口，还能导出 CSV [S14]。
- AutoLife 的 JSON 要先变成数值：
  - 一种办法是用 User Scripts（TypeScript）把输入话题变成合成话题 [S14]。用 `JSON.parse` 解析是推断，未用原型验证。
  - 另一种是在机器人侧先规整好（见路线 A'）。

**能否嵌进 React 页面**

- 只能用 **iframe**。Lichtblick 没有发布可嵌入的 React 组件，npm 上的 `@lichtblick/suite` 只是扩展 API 的类型定义（[npm registry](https://registry.npmjs.org/@lichtblick/suite)）。
- 可以用 URL 参数预置数据源和布局：`?ds=foxglove-websocket&ds.url=ws://<机器人IP>:8765&layoutUrl=<布局JSON>`。参数解析见 `appURLState.ts` 和 `FoxgloveWebSocketDataSourceFactory` [S13][S11]。
- 父页面和 iframe 之间没有文档化的 postMessage 控制接口（在源码里没找到，属于未查到，不等于确认没有）。

**许可证与维护**

- foxglove_bridge 是 MIT，最近的版本是 ros-v3.6.2（2026-10-16），仓库每周都有提交 [S1][S2]。
- Lichtblick 是 MPL-2.0，版权方是 BMW AG，从 Foxglove Studio 分叉而来。最近的版本是 v1.29.1（2026-09-08），仓库最后推送在 2026-10-16，大约每月发一版 [S10]。
- **兼容性坑**：foxglove_bridge 3.2 起换成了基于 SDK 的服务端，只接受 `foxglove.sdk.v1` 子协议 [S7]，老版本 Lichtblick 因此连不上（issue #750）。Lichtblick 在 PR #819（2025-12-09 合并，之后第一个版本是 v1.22.0）里同时声明了 `foxglove.websocket.v1` 和 `foxglove.sdk.v1` [S12][S11]。按 PR 里引用的 Foxglove 官方说法，这两个子协议目前内容完全相同 [S12]。所以 Lichtblick 必须 ≥ v1.22.0。
- 风险：`foxglove/ws-protocol` 仓库已归档，README 说这些库"deprecated and no longer maintained"[S6]。Lichtblick 仍依赖其中的 JS 客户端 `@foxglove/ws-protocol` 0.8.0（2025-03 发布）。以后 Foxglove 改协议时，Lichtblick 需要自己跟进。
- Foxglove 官方 app 从 2.0（2024-03）起闭源，首次启动要登录，免费版限 3 人 [S16]，所以不作为候选。

### 路线 A'：foxglove_bridge + 自写 `viz_relay` + Lichtblick（推荐，A 的补全版）

**机器人上装什么、跑什么**

- foxglove_bridge 和路线 A 一样，再加 `ros-$ROS_DISTRO-foxglove-msgs`（Jazzy 上和 bridge 同属一个 release，版本 3.6.2-1）[S3]。
- 另外加一个自写的 rclpy 节点 `viz_relay`。它把机器人话题规整成"可视化专用"话题，统一放在 `/viz/` 下，再由 bridge 用 `topic_whitelist` 只暴露 `/viz/.*`。
  - **R1 Lite**：
    - 头部 H.264 不解码，只把字节拷进 `foxglove_msgs/msg/CompressedVideo`（`format="h264"`）。消息的码流结构满足该 schema 的要求（§1.1）[S9]。
    - 腕部 JPEG 解码、缩放、按普通质量重编码，并限到 10–15 fps。
    - 关节话题原样转发，或降采样到 50–100 Hz。
  - **AutoLife**：
    - 直接读 SHM，复用 `shm_camera.py` 的读取规则。手部 JPEG 可以原样转发，也可以重编码。头部原始帧编码成 JPEG。
    - 订阅两个 JSON 话题，解析后发成标准 `sensor_msgs/JointState`。目标和观测各一个话题，关节名按 `robot_schema.py` 的顺序。
- 两台机器人对外的话题形态一样，Lichtblick 布局只需要换话题前缀。
- 也可以不用 bridge，直接用 Python 的 `foxglove-sdk` 在 relay 里起 WebSocket 服务：`foxglove.start_server(host="0.0.0.0")`，配 `Channel(..., message_encoding="json")` 和 `CompressedImageChannel` / `CompressedVideoChannel` [S8]。代价是失去 bridge 的"浏览任意话题"能力。Lichtblick 一次只连一个数据源，所以两种方式选一种，不要同时跑两个服务端。

**带宽和延迟的量级**

- 按 §1.1 的实验数字估算：
  - 头部 H.264 原样约 15 Mbit/s，或者重编码到约 0.3 Mbit/s 以上（取决于画面运动）。
  - 两路腕部各约 1.1 Mbit/s（640×360、15 fps）。
  - 关节约 1 Mbit/s 以内。
- 合计约 **18 Mbit/s**（头部原样）或 **3–5 Mbit/s**（头部重编码）。只看一路相机时更少。
- 延迟（推算）：每帧传输时间降到个位数毫秒，主要开销变成机器人侧的编解码（JPEG 编解码每帧几毫秒，H.264 原样转发没有额外开销）和浏览器解码。量级是几十毫秒到约 100 ms，需要实测。
- 机器人 CPU 能不能撑住三路 JPEG 解码加重编码，**未查实**，因为两台机器人的 CPU 型号和架构都还不知道（交给 05 票）。

**能否在同一张图上显示目标和观测**：能，而且两台机器人都不需要 User Script，因为 relay 已经把数据规整成 `JointState` 了。

**能否嵌进 React 页面**：同路线 A（iframe 加 URL 参数）。布局 JSON 可以由平台按机器人档案（14 票）生成，再通过 `layoutUrl` 传进去 [S13]。

**许可证与维护**：同路线 A。relay 由我们自己维护，规模估计在几百行内（推断）。

### 路线 B：Rerun（票里的候选 2）

**机器人上装什么、跑什么**

- `pip install rerun-sdk==<固定版本>`。PyPI 上有 manylinux_2_28 的 x86_64 和 aarch64 wheel，需要 Python ≥ 3.10。最新版是 0.39.0（2026-10-12）[S21]。
- Rerun 不认识 ROS 话题，所以同样要一个自写的 relay：rclpy 订阅，或者读 SHM，然后调 `rr.log(...)`。
  - 官方的 ROS 2 桥是 C++ 写的 proof-of-concept 外部示例 [S22]，不适合直接用。
  - 第三方的 Rewire 目前闭源 [S22]，不考虑。
- relay 里调 `rr.serve_grpc(grpc_port=9876, server_memory_limit=..., cors_allow_origin=[平台的源])`，Web Viewer 用 `rerun+http://<机器人IP>:9876/proxy` 连接 [S18][S17]。
- **建议放在独立的 venv 里**：LeRobot 0.6.1 的 `viz` extra 把 `rerun-sdk` 锁在 `>=0.24,<0.34` [S32]。和 AutoLife 采集器（依赖 lerobot）共用环境时，版本会冲突。

**带宽和延迟的量级**

- 图像用 `EncodedImage`（JPEG/PNG）[S19]，或者用 `VideoStream`（H.264/H.265，不支持 B 帧）[S19]。R1 Lite 头部的 H.264 可以原样作为 `VideoStream` 的 sample 发出去。降采样后的带宽和路线 A' 同一量级。
- **推送全部数据，不是订阅制**：gRPC 服务端"will buffer all log data in memory so that late connecting viewers will get all the data"，默认 `server_memory_limit="1GiB"` [S18]。也就是说：
  - 不管页面上看不看，logged 的东西都会推给 Web Viewer。
  - 新打开的页面会先把缓冲里的历史数据全部回放一遍，最多 1 GiB，在 Wi-Fi 上要很久。
  - 实时查看必须把 `server_memory_limit` 设小，或者设 `newest_first=True` [S18]。
- Viewer 端到内存上限后会丢最旧的数据，原生 viewer 默认用到系统内存的 75% [S23]。Web Viewer 在浏览器里的内存上限，文档没写，**未查实**。
- 延迟（推算）：和 A' 同一量级。官方视频文档推荐低延迟场景用 H.264，并说明原生 viewer 解码比浏览器慢 [S19]。

**能否在同一张图上显示目标和观测**

- 能。`TimeSeriesView` 会把一个 `origin` 下的多个实体画在同一张图里，例如官方示例里 `trig/sin`、`trig/cos` 同图 [S20]。
- 把目标和观测分别记成 `joints/left_arm/0/target`、`joints/left_arm/0/observed`，就能叠在一起（按示例模式推断）。
- 可以用 blueprint 在 relay 里预置布局。时间范围支持相对游标的滑动窗口 [S20]。

**能否嵌进 React 页面**

- 能，而且是**官方组件**：`@rerun-io/web-viewer-react`（MIT，0.39.0，peerDependencies 支持 React 18/19），用法是 `<WebViewer width height rrd="rerun+http://…/proxy" />` [S17]。
- 代价有三：
  - **包版本必须和 SDK 版本完全一致**："`@rerun-io/web-viewer-react@0.10.0` only connects to data sources produced by SDK 0.10.0" [S17]。机器人 relay 和前端每次都得一起升级。
  - 需要 Wasm 和 top-level await 的打包插件，Vite 下是 `vite-plugin-wasm` 和 `vite-plugin-top-level-await` [S17]。
  - gRPC 服务端默认只允许 localhost 和 rerun.io 的 CORS，平台的源要显式加进去 [S18]。

**许可证与维护**

- MIT OR Apache-2.0，open-core 模式：仓库内的东西承诺一直开源 [S21]。
- 发版很频繁：0.37.0 到 0.39.0 用了约 6 周 [S21]，属于 0.x 阶段，有破坏性变化。`VideoStream` 被明确标为 unstable："may change significantly in a way that the data won't be backwards compatible" [S19]。

### 路线 C：web_video_server（票里的候选 3）

**机器人上装什么、跑什么**

- `sudo apt install ros-${ROS_DISTRO}-web-video-server` [S24]。Jazzy 上是 3.1.0，仓库最新标签是 3.1.1（2026-05-07）[S3][S24]。默认端口 8080，绑定 `0.0.0.0` [S24]。
- 它只管图像。关节曲线要另找办法，通常配 rosbridge（路线 E）。
- AutoLife 要先跑 `shm_camera_topic_bridge.py`，才有 ROS 图像话题（§1.2）。原始图像只在机器人本机传，没问题。
- **R1 Lite 头部无法显示**：
  - `ros_compressed` 类型把 CompressedImage 原样透传，但只认 `format` 里含 jpeg/jpg/png 的消息，遇到别的格式就打 "Unknown ROS compressed image format" 并丢帧 [S24: `ros_compressed_streamer.cpp`]。
  - 其他类型走 image_transport 订阅后解码。`compressed` transport 解不了 H.264。
  - 要显示这一路，就得在机器人上自写一个 H.264 解码并重发的节点。

**带宽和延迟的量级**

- 带宽可以在 URL 上调：`type=mjpeg&default_transport=compressed&width=640&height=360&quality=80` 表示"订阅 JPEG 话题，在机器人上解码、缩放、重编码"[S24]。腕部每路大约 1–2 Mbit/s（按 §1.1 的实验推算，帧率由源决定，没有限帧参数）。
- `ros_compressed` 模式原样透传，一路腕部就是 41–52 Mbit/s。
- 延迟（推算）：MJPEG 和 `ros_compressed` 每来一帧就发一个 multipart 分片，订阅 QoS 是 `keep_last(1)` [S24 源码]，没有帧间缓冲，是几条路线里最低的。h264/vp8/vp9 类型经过 libav 编码器，延迟没有文档说明。

**能否在同一张图上显示目标和观测**：不能，它只有视频流。

**能否嵌进 React 页面**

- 最简单：`<img src="http://<机器人IP>:8080/stream?topic=...&type=mjpeg">` [S24]。
- 平台走 HTTPS 时会撞上混合内容的限制（§1.4）。

**许可证与维护**：BSD-3-Clause。ros2 分支最后一次提交在 2026-09-09，rosdistro 状态是 `maintained`，已经加了 Lyrical 的 CI [S24][S3]。

### 路线 D：自写 ROS 2 → WebSocket → React（票里的候选 4）

**机器人上装什么、跑什么**

- 一个 Python 进程：rclpy 订阅或读 SHM，OpenCV/PyAV 编码，再用 `websockets` 或 FastAPI 的 `@app.websocket` 往外发二进制帧 [S33]。
- 理由同 §1.3：这个进程放在机器人上，不放在工作站上。

**带宽和延迟的量级**：完全由自己控制，量级同路线 A'（每路相机约 1 Mbit/s，关节降采样后可忽略）。延迟取决于实现，"只保留最新一帧、丢旧帧"的背压策略要自己写。

**能否在同一张图上显示目标和观测**

- 能，自己画。uPlot（MIT，约 50 KB）用 Canvas 2D 绘制，官方基准是"updating 3,600 points at 60fps"时约 10% CPU，并说明 Chart.js 和 ECharts 在同一场景下分别是 40% 和 70% [S33]。
- 两条臂共 14 个关节，200 Hz、显示 10 s 窗口，单图点数在这个量级之内（推算）。

**能否嵌进 React 页面**：原生就是 React，界面风格和平台完全一致。

**许可证与维护**

- 代码是自己的。依赖 uPlot（MIT，1.6.32，2025-03 发布）和 FastAPI（MIT）[S33]。
- **代价都在自己身上**，下面这些都要自己写和测试：
  - 协议
  - 重连
  - 背压与丢帧
  - 时间对齐（用 `header.stamp` 还是接收时间）
  - 话题发现和选择界面
  - H.264 解码（WebCodecs 或在机器人上转 JPEG）
  - 断线诊断

  对一个人维护、代码交给 AI 写的项目（需求 (12)），这是维护面最大的一条路线。

### 路线 E（调研中加入）：rosbridge_suite + roslibjs，通常配合路线 C

**机器人上装什么、跑什么**：`ros-$ROS_DISTRO-rosbridge-suite`，然后 `ros2 launch rosbridge_server rosbridge_websocket_launch.xml`，默认端口 9090 [S25]。rosdistro 里 Jazzy 是 2.7.1，Lyrical 是 4.2.1 [S3]。

**带宽和延迟的量级**

- 默认按 JSON 传输。可选 `throttle_rate`（最小发送间隔，毫秒）、`queue_length`，以及 `compression`（`png`、`cbor`、`cbor-raw`）[S25]。关节数据加上 throttle 后很小。
- 图像走 JSON 很不划算，所以图像仍交给 web_video_server。
- Python 实现，没有官方性能数据。
- Jazzy 的 2.7.1 是否支持协议文档里的全部选项（文档是 ros2 分支 HEAD 的），**未逐项核对**。

**能否在同一张图上显示目标和观测**：数据能拿到，图要自己画（同路线 D 的前端部分）。AutoLife 的 JSON 字符串要在前端解析。

**能否嵌进 React 页面**：能，用 `roslib`（npm，BSD-2-Clause，2.1.0，2026-03-03）[S26]。

**许可证与维护**：rosbridge_suite 是 BSD，ros2 分支 2026-10 仍有提交，rosdistro 状态是 `developed` [S25][S3]。

### 没有纳入比较的选项

- **Foxglove 官方 app**：2.0 起闭源，需要登录，免费版限 3 人 [S16]。
- **Rewire**：闭源 [S22]。
- **Rerun 官方 C++ ROS 2 桥**：proof-of-concept 外部示例 [S22]。
- **LeRobot 自带的实时显示**：0.6.1 中 `--display_mode` 可以选 `rerun` 或 `foxglove` [S32]。但它只在 LeRobot 自己的控制循环里生效，AutoLife 采集器和 R1 Lite 原厂录制都不走这个循环。它可以作为旁证：LeRobot 生态同时支持 Rerun 和 Foxglove 两种协议，无论选哪个都不偏离生态。

## 4. 推荐

**选路线 A'：机器人侧跑 foxglove_bridge 和一个自写的 `viz_relay` 节点，工作站自托管 Lichtblick，平台的 React 页面用 iframe 嵌入。**

依据：

1. **Wi-Fi 是瓶颈，订阅制最省带宽**。Foxglove WebSocket 协议按 channel 订阅 [S6]，Lichtblick 只订阅面板正在用的话题 [S11]。Rerun 推送全部数据，新页面还会先回放缓冲 [S18]。只有 Wi-Fi 的工作站（F10）最怕后者。
2. **两台机器人都必须有一个规整层**（§1.1、§1.2），这一点在任何路线里都躲不开。A' 让这个规整层的产物是**标准 ROS 消息**：`JointState`、`CompressedImage`、`foxglove_msgs/CompressedVideo`。好处有三：
   - Lichtblick 不需要任何脚本就能画"目标 vs 观测"。
   - 同一批 `/viz/*` 话题以后可以直接录成 MCAP。
   - 将来要换成路线 D 的自写前端时，机器人侧不用改。
3. **需求 (5) 里像 rqt 那样"选话题看画面"的交互是现成的**：Image 面板的话题下拉框、Plot 面板的 message path 补全、滑动窗口、CSV 导出都不用写 [S14]。对一个人维护的项目（需求 (12)），这是最小的前端维护面。
4. **一个查看器两种用途**：同一个 Lichtblick 还能离线打开 MCAP（R1 Lite 原厂录制格式、EgoProStandard），数据集板块可以复用。
5. **许可证和维护都没问题**：bridge 是 MIT，每周有提交；Lichtblick 是 MPL-2.0，由 BMW AG 维护，约每月一版 [S1][S2][S10]。

要付出的代价：

- **集成度**：iframe 只能用 `ds`、`ds.url`、`layoutUrl` 这几个 URL 参数控制 [S13]。Lichtblick 的界面风格和平台不一致，也没有找到文档化的父子页面通信接口。
- **要自写并维护 `viz_relay`**（每台机器人一份配置）。它的规模和测试要求应当在 M5 的 spec 里写清楚，包括降采样参数、重编码 CPU 预算和断线重连。
- **访问方式受限**：H.264 解码要求 secure context（§1.4）。平台在工作站本机用 `http://localhost` 打开时没有问题；要从别的机器访问，就得给平台和 Lichtblick 都上 HTTPS（tailscale 的证书或反向代理），机器人侧的 bridge 也要开 `tls` [S1]。
- **MPL-2.0**：只用不改，没有任何义务。修改了 Lichtblick 的源文件并对外分发时，要公开这些文件的修改。平台是内部使用，风险低。
- **协议风险**：`@foxglove/ws-protocol` 客户端库已经停止维护 [S6]，而 bridge 的升级曾经让旧版 Lichtblick 连不上 [S12]。所以 bridge 和 Lichtblick 的版本要一起锁定，升级前先在一台机器人上试。
- **安全配置是必须项**：`capabilities:=[]`、`topic_whitelist:=['/viz/.*']`，防止浏览器往 `/motion_target/*` 发消息（§1.5）。

**什么时候改选别的路线**

- 如果负责人把"平台里原生的 React 组件、风格统一"看得比带宽和升级成本更重，选 **B（Rerun）**。前提是接受 viewer 和 SDK 版本锁死、每次升级两边联动 [S17]，并且在 relay 里把 `server_memory_limit` 设小 [S18]。
- 只想先尽快在页面上看到手部或腕部 JPEG 画面、暂时不要曲线时，**C（web_video_server 的 mjpeg 模式）**是最快的过渡方案。但它覆盖不了 R1 Lite 头部，也没有关节曲线。
- 长期如果 iframe 的集成度不够，可以从 A' 平滑过渡到 **D**：`/viz/*` 话题契约不变，只替换前端。

**建议的下一步（不在本票范围内）**

在 05 票拿到实测的 Wi-Fi 吞吐和延迟以后，先做一个 prototype：在 R1 Lite 上跑 bridge 加一个最小的 relay，只做头部 H.264 转封装和一路腕部降采样，测端到端延迟。测法可以是拍屏幕上的时钟对比。用实测结果确认 §2 里标为"推算"的数字。

## 5. 未能查实的问题

- **工作站和机器人之间 Wi-Fi 的实际吞吐和延迟**：决定头部 H.264 能不能原样转发（约 15 Mbit/s）。交给 05 票。
- **实时话题是否和 MCAP 录制一致**：编码、分辨率、频率。另外，AutoLife 两个 JSON 话题的频率和消息大小，以及头部 RGB 的分辨率，也都没有核实。交给 05 票。
- **两台机器人的 CPU、架构和 ROS 发行版**：决定 relay 里的 JPEG 重编码能不能撑住，以及能不能用硬件编码。R1 Lite 的发行版也没有官方资料可查。
- **端到端延迟**：所有项目都没有官方实测值，§2 里的数字都是推算。
- **Lichtblick 的 User Script 能否用 `JSON.parse` 解析 `std_msgs/String`**：文档只说明 User Script 能做变换，没有现成示例。A' 用 relay 规整 JSON，绕开了这个问题。
- **HTTPS 页面连 `ws://`**：MDN 没写，浏览器之间可能有差异。
- **Rerun Web Viewer 在浏览器里的内存上限**：文档只写了原生 viewer 的 `--memory-limit`。
- **Lichtblick 的 iframe 父子页面通信**：源码里没有找到文档化的接口，可能是没找到，不等于确认没有。

## 附录 A：本机 MCAP 统计和重编码实验的方法

- 文件：
  - `/mnt/dataset2/R1_lite_table_withdrawing_mcap/20261011_table_withdrawing/RBB60624A002_20261011151735482_RAW/RBB60624A002_20261011151735482_RAW.mcap`（52.1 s）
  - `/mnt/dataset2/R1_lite_table_withdrawing_mcap/20261009_table_withdrawing/RBB60624A002_20261009202503536_RAW/RBB60624A002_20261009202503536_RAW.mcap`（100.9 s）
- 统计脚本只用 Python 3.14 标准库：
  - 按 MCAP 规范读 Footer → Summary（Schema、Channel、Statistics、ChunkIndex），再逐个读 Chunk，用 `compression.zstd` 解压后统计每个 channel 的消息数、字节数和时间跨度。
  - 消息大小是 CDR 负载的字节数。
  - 文件以只读方式打开。脚本放在会话 scratchpad 里，没有进仓库。
- 编码识别：
  - 从 CDR 里找 `format` 字段，JPEG 读 SOF 段拿到宽高，H.264 用 `ffprobe` 读出 codec、profile 和宽高。
  - 按 Annex B 起始码统计每条消息里的 NAL 类型，用来确认 GOP 和关键帧结构。
  - 解析切片头的 `slice_type`，确认没有 B 帧。
- 重编码：从录制中段拷出 30 帧腕部 JPEG 和从关键帧开始的 60 帧头部 H.264，用本机 ffmpeg 8.0 处理：
  - `-vf scale=640:360 -q:v 5`
  - `-q:v 5`（保持原分辨率）
  - `-vf scale=640:512 -c:v libx264 -preset veryfast -tune zerolatency -bf 0 -g 30 -crf 28`
  - 取输出的平均大小。
