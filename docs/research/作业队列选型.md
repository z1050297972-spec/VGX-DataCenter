## 结论速览

1. **建议自己写作业表和 worker，不引入任务队列库。**
   - 六个候选里，没有一个能明显减少要写的代码。
   - 平台要写的大头都不在这些库的职责里：六种状态、按类型的中断恢复、停止外部工具、GPU 名额、进度、心跳、永久记录。
   - 用了库，这些照样要写，还要多协调一套库自己的状态。（第 3 节的对照表，Codex 判定，Claude 抽查）
2. **决定性的几条事实**（均已核对，出处见各节）：
   - **huey**：领取任务时就删掉 SQLite 里那一行，worker 被 `kill -9` 或断电时，任务直接丢失。官方文档写明不保证 at-least-once；`revoke` 只能撤销还没开始执行的任务。
   - **APScheduler 3.x**：官方 FAQ 写明，不能让多个进程共享一个作业存储。
   - **APScheduler 4.0**：
     - 至今仍是预发布，README 写着不要用于生产。
     - 跨进程需要 PostgreSQL、Redis 或 MQTT 事件代理。
     - 源码警告：多个 scheduler 共享数据存储时不要用 SQLite。
   - **litequeue 0.14**：拒绝打开含有其他表的数据库，与"作业表和业务表同库"直接冲突。
   - **persist-queue**：只是一个队列数据结构，没有 worker。`SQLiteAckQueue` 默认在打开队列时，把所有未确认的消息重新投递，不区分作业类型。
   - **DBOS**：
     - 支持 SQLite，并发上限、定时、崩溃恢复都有。
     - 恢复只有一种方式：从上一个完成的步骤接着跑。
     - 取消只是把状态改成 `CANCELLED`，不会停下正在运行的同步步骤。
     - 官方建议生产环境用 Postgres；即使用 SQLite，也要装 `psycopg[binary]`。
3. **可以借鉴的设计**：
   - litequeue 用 `claim_id` 拒绝过期领取者回写；
   - persist-queue 的 `unack` 状态；
   - APScheduler 4 的 `acquired_by` 加租约。

## 1. 需求清单

从 ADR 0005 整理，编号在全文通用。

- **R1 独立 worker 进程，只经作业表通信**：
  - worker 独立于 Web，Web 重启不影响正在跑的作业。
  - 两者只通过 SQLite 里的作业表联系：提交作业就是插一行，取消作业就是在那一行上写取消请求。
  - worker 每秒查一次新作业和取消请求。
- **R2 六种作业状态**：排队中、运行中、正在取消、已完成、已取消、已中断。
  - 只有"已完成"带作业结果，共四种，由计数算出。
  - "已取消""已中断"也要显示做到了哪一阶段、多少条目。
- **R3 中断识别与按类型恢复**：
  - worker 启动时，要识别出上一个实例留下的"运行中"作业（包括被 `kill -9`、整机断电），判为中断，并写明中断在哪一步、最后进度是多少。
  - 然后按作业类型三选一处理：
    - 续跑：下载；
    - 重跑：重新扫描；
    - 标记中断：转换、写导航层的作业。写导航层的作业还要先跑完恢复流程，才放行别的写操作。
  - 排队中的作业，重启后照常排队。
- **R4 取消**：
  - 排队中的作业，取消后立刻变成"已取消"。
  - 运行中的作业先进入"正在取消"：先请工具停下，约 10 秒后还没停就强制结束。
  - 正在写导航层的那一步不打断。
  - 取消不清理产物。
- **R5 按类型的并发上限**：
  - 每类作业有各自的上限，默认 1，可在配置里改。
  - 不同类型之间可以并行。
  - 满额类型的作业继续排队，不能占住别的类型的执行位。
- **R6 GPU 名额**：
  - 两张卡算两个名额，一张卡同一时间只给一个作业。
  - worker 分配卡，作业结束后收回。
  - 没有空卡就排队。
- **R7 进度**：
  - 写进数据库里的作业记录，每秒最多写一次。
  - 一直保留最后一次进度，工具突然退出时靠它补诊断。
- **R8 心跳**：worker 定时写心跳；心跳过期时，网页提示 worker 不在线。
- **R9 单实例文件锁**：
  - worker 启动时先拿状态目录里的排他文件锁，拿不到就退出。
  - 运维命令也拿这把锁。
- **R10 定时提交作业**：worker 到点提交定时作业，提交人记为"系统"，和普通作业走同一张表。
- **R11 作业记录永久保留**：
  - 参数、提交人、状态、进度、计数、诊断样例、结尾摘要都永久保留。
  - 重新提交会新建一个作业，并注明"重新提交自 #N"。
- **R12 同库、同步写法**：
  - 作业表和业务表在同一个 SQLite（WAL）库里，表结构由同步 SQLAlchemy 2 + Alembic 管理。
  - 不用 async，不加服务。

以下由平台自己负责，不计入评分：导航层写锁、写前冲突核对、存储根在线检查、作业日志文件、systemd 托管。

- **① R1 的判定口径**：按"作业表里的一行，就是提交、取消、执行的唯一记录"判定。
  - 用这些库都会多出一张库自己的队列表，平台作业表和库的表要双写。
  - 如果只要求"经 SQLite 通信"，huey、persist-queue、litequeue、DBOS 都能做到。
  - APScheduler 两代都做不到：3.x 不支持多进程共享作业存储；4.0 跨进程唤醒依赖外部事件代理（见 3.1 节）。
- **②** 4.0 的 `max_running_jobs` 按 task 限流，默认 1。但领取时先 `LIMIT` 再跳过满额的 task，满额类型排在队首时，会挡住别的类型。

  - "补"的格子，Claude 抽查了 R3、R4、R5、R11、R12，其余未逐格核对。

### 3.1 各库的关键依据

**huey 3.4.0（`SqliteHuey`）**

- **R1**：领取任务的 `dequeue()` 在同一个排他事务里先选出一行，再把它从 `task` 表删掉。库的表只是一张待投递消息表，不能当作业记录。（[S9]，已核对）
- **R5**：
  - consumer 的 `--workers` 是全局的 worker 数。（[S11]，已核对）
  - `lock_task` 是领取之后的互斥：抢不到锁时抛 `TaskLockedException`，任务不执行，配置了重试才会重试，并不是继续排队。（[S12]，已核对）
  - 推论：要按类型限流，就得每类一个队列、各起一个 consumer 进程。这和 ADR 0005"导航层写锁放在唯一的 worker 进程里"冲突。（未核对）
- **R12**：
  - 可以指向现有的 SQLite 文件，默认 WAL，支持 `create_tables=False`，所以兼容的表结构可以交给 Alembic 预建。
  - 但它用自己的 `sqlite3` 连接和 `begin exclusive` 事务，不进平台的 SQLAlchemy Session。（[S13]，已核对）

**APScheduler 3.11.3（`SQLAlchemyJobStore`）**

- **R1**：
  - 官方 FAQ 原话："How do I share a single job store among one or more worker processes? Short answer: You can't."
  - 原因是缺少进程间的同步和通知，会导致重复执行或漏掉作业。
  - 官方给的变通办法是用 RPyC、gRPC、HTTP 远程调用 scheduler，这违反"不另开通道"。（[S15]，已核对）
  - 用户指南也写着："Job stores must never be shared between schedulers."（[S19]，已核对）
- **R5**：`max_instances` 按单个 job 计数。达到上限时，这次触发直接跳过（`MaxInstancesReachedError`），随后照样推进下次触发时间或删除 job，不会留队等待。（[S16]，已核对）
- **R11、R12**：
  - 表只有 `id`、`next_run_time`、`job_state` 三列，`job_state` 是 pickle。
  - 启动时自动建表（`checkfirst`）。
  - 反序列化失败的 job 会被直接删除。（[S18]，已核对）

**APScheduler 4.0.0a6（`SQLAlchemyDataStore`）**

- **是否可用于生产**：README 警告"provided as a **pre-release** … do NOT use this release in production!"。PyPI 上至今没有比 4.0.0a6 更新的 4.x 版本。（[S2][S20]，已核对）
- **R1**：
  - 文档写明，多个 scheduler 共用数据存储时"a shared *event broker* must be configured"；内置的事件代理只有 PostgreSQL、Redis、MQTT。（[S20][S25]，已核对）
  - 源码里，worker 领取作业的循环只在收到 `JobAdded`、`JobReleased` 事件时才醒来，没有定时轮询兜底。（[S24]，已核对）
  - 由此推出：不配跨进程事件代理时，Web 进程插入的作业不会唤醒 worker。（推论，未核对）
  - 数据存储的文档字符串写着："Do not use SQLite when sharing the data store with multiple schedulers, as there is an unresolved issue with that (#959)"。（[S21]，已核对）
- **R5**：
  - `max_running_jobs` 默认 1。（[S26]，已核对）
  - 领取的 SQL 按创建时间排序后先 `LIMIT`，再在 Python 里跳过满额 task，会被队首阻塞。（[S22]，已核对）
- **R11**：
  - 作业结束后删掉 jobs 表里的那一行。
  - 结果默认保留时长是 0，取一次结果就删除。（[S23][S26]，已核对）

**persist-queue 1.1.0（`SQLiteAckQueue`）**

- **是什么**：一个持久化队列容器，没有 worker、调度器、取消机制。
- **状态**：只有投递状态 `inited/ready/unack/acked/ack_failed`。（[S28]，已核对）
- **R1、R7**：
  - 阻塞式 `get()` 等待的是进程内事件，每 10 秒醒来一次查库。Web 在另一个进程里插入的消息，最多要 10 秒才被看到；要做到每秒响应，得自己写非阻塞轮询。（[S29]，已核对）
  - `update()` 会整块替换载荷，可能抹掉并发写入的取消请求。（Codex 报告 §2.4，未核对）
- **R12**：
  - 构造时总是执行建表语句，没有关闭开关。
  - 自己开 `sqlite3` 连接并设 WAL，没有 SQLAlchemy、Alembic 集成。
  - 默认用 pickle 序列化。（[S29]，已核对）

**litequeue 0.14**

- **R12**：
  - 构造函数扫描 `sqlite_schema`，只要有 `Queue` 以外的表就抛 `ValueError`："These versions do not allow multiple queues or database sharing with other applications"。
  - 业务表、`alembic_version` 都会触发。
  - 它还会把连接设成 `PRAGMA synchronous = NORMAL`。（[S30]，已核对）
- **R5**：`pop()` 不带参数，按顺序领取最早的 READY 消息，不能按类型挑选；分库分类型又违反 R12。（[S31]，已核对）

**DBOS Transact 3.3.0**

- **SQLite 支持**：
  - 不配置 `system_database_url` 时，默认用 `sqlite:///<应用名>.sqlite`。（[S33]，已核对）
  - 官方配置文档："This may be either Postgres or SQLite, though Postgres is recommended for production."（[S32]，已核对）
  - `psycopg[binary]` 是必选依赖，用 SQLite 也会装上。（[S5]，已核对）
- **R1**：
  - `DBOSClient` 能在另一个进程里入队；`enqueue_in_transaction()` 还能在调用方的同步 SQLAlchemy 事务里入队。（[S39]，已核对）
  - 但作业状态和取消都写在 DBOS 自己的 workflow 表里，平台作业表只能另行同步，所以按 ① 的口径判 ✗。
- **R5**：
  - 每类作业一个 queue，`worker_concurrency`、`global_concurrency` 分别控制单个 worker 和全局的并发。
  - 每个 queue 由各自的线程轮询，默认间隔 1 秒，满额的 queue 不挡别的 queue。（[S39]，已核对）
- **R12**：
  - 自己管理表结构，版本记在 `dbos_migrations` 表里。
  - 默认序列化是 pickle 再转 base64。（[S40]，已核对）
  - 要把它的迁移协调进 Alembic。（Codex 报告 §2.6，未核对）

## 4. worker 崩溃时，正在执行的任务会怎样

"丢失"指库里不再留有能恢复这次执行的记录，**不表示已经写出的文件会消失**。断电后能保住哪一笔提交，还取决于 SQLite 的 `synchronous` 设置和存储设备。

**huey：硬崩溃时丢失。**

- **优雅停止**：
  - `SIGINT`：等 worker 跑完手上的任务再退出。
  - `SIGTERM`：立即退出，中断正在跑的任务，并对每个任务发出 `SIGNAL_INTERRUPTED`。
  - 两个信号的语义可用 `--graceful-signal=TERM` 对调；`--shutdown-timeout` 可以给优雅停止设上限。（[S10][S11]，已核对）
  - 这两个选项是 3.4.0 才加的。（[S14]，已核对）
- **和 systemd 的配合**：
  - 文档提醒：几乎所有进程管理器默认都用 `SIGTERM` 停进程，而 huey 默认把它当作"立即停止"。（[S10]，已核对）
  - 所以放在 systemd 下，必须配 `-g TERM`，否则每次重启服务都会中断正在跑的任务。
- **硬崩溃**：
  - 文档原话："A task interrupted by `SIGKILL` (or a power loss) is lost."（[S10]，已核对）
  - 另一处："Huey does not guarantee at-least-once delivery of messages, and does not do acknowledgement of completed tasks."（[S11]，已核对）
- **决定行为的代码**：
  - 领取时已经删行。（[S9]，已核对）
  - "正在执行"只记在进程内存里的 `_tasks_in_flight` 集合中。（[S8]，已核对）
  - `SIGNAL_INTERRUPTED` 只在进程还活着时触发，断电后无从补发。

**APScheduler 3.x：通常丢失这一次执行。**

- **优雅停止**：`shutdown(wait=True)` 等正在跑的任务结束，"Does not interrupt any currently running jobs"。（[S17]，已核对）
- **硬崩溃**：
  - 到期的 job 一交给执行器，存储里就推进下次触发时间；一次性的 job 则直接删除。
  - 崩溃时没有"运行中"的记录可查。（[S16]，已核对）
- **重复执行的窗口**：提交执行器与更新存储不在一个原子操作里。如果恰好崩在两者之间，旧记录留下，重启后会再执行一次。（Codex 报告 §3.1，由 [S16] 推出，未核对）

**APScheduler 4.0.0a6：留下可识别的标记，但会被判为"已放弃"并删除，不会自动重投。**

- **领取**：写入 `acquired_by` 和租约到期时间 `acquired_until`。（[S22]，已核对）
- **同一身份重启**：scheduler 用同一个身份重启时，先把自己名下的遗留作业以 `abandoned` 结果释放。（[S24]，已核对）
- **其他 scheduler**：等租约过期后，在 `cleanup()` 里做同样的处理。（[S23]，已核对）
- **释放的结果**：
  - 释放会删除 jobs 表里那一行。
  - 结果默认不保留，所以平台不能靠它长期展示"中断在哪一步"。（[S23][S26]，已核对）

**persist-queue `SQLiteAckQueue`：留下 `unack`，默认重新打开队列时自动重投。**

- 构造参数 `auto_resume=True` 是默认值，构造时把所有 `unack` 一律改回 `ready`。（[S28]，已核对）
- 它不检查 worker 是否真的死了。（推论，由 [S28] 推出，未核对）
  - Web 进程重建队列对象，也会把 worker 正在执行的任务重新投递，造成重复执行。
  - 所以所有客户端都要显式关掉 `auto_resume`。
- 普通的 `SQLiteQueue` 不一样：取出时就删行，崩溃即丢失。（[S29]，已核对）

**litequeue：留下 `LOCKED` 标记，不会自动恢复。**

- `pop()` 把消息标成 `LOCKED`，并记下 `lock_time`。（[S31]，已核对）
- 打开数据库时不做任何恢复。要靠 `list_locked()` 找出遗留消息，再用 `retry()` 或 `retry_expired()` 显式放回队列。（[S30][S31]，已核对）

**DBOS：留下 `PENDING`，启动时有条件地自动接着跑。**

- **恢复**：
  - 启动时，后台线程查出 `executor_id` 和 `application_version` 都匹配的 `PENDING` workflow，重新入队。（[S35][S36]，已核对）
  - README 说明，恢复后从上一个已完成的步骤接着跑。（[S34]，已核对）
- **和 ADR 0005 的冲突**（由上面的源码推出，未核对）：
  - 应用版本变了，旧作业不会被自动恢复，要另行处理。ADR 0005 要求升级重启后按中断处理。
  - 转换要求"标记中断"，不能自动接着跑；DBOS 只有这一种恢复方式。
- **重复执行**：外部工具已经写了文件、但步骤结果还没落库时崩溃，恢复时这一步会再执行一次。（Codex 报告 §3.1，未核对）
- **优雅停止**：`destroy()` 等待活动 workflow 的时长默认是 0 秒。（[S35]，已核对）

## 5. 能否取消正在运行的任务

结论：**六个库都不能原生满足 R4。**

R4 要的是一套和库无关的子进程监督协议：

1. Web 写取消请求。
2. worker 把作业改成"正在取消"。
3. 如果正在写导航层，等这一步写完。
4. 发 `SIGTERM`，约 10 秒后发 `SIGKILL`。
5. 确认子进程已经退出后，再写"已取消"。

**huey**

- 文档原话："Any task can be canceled ("revoked"), provided the task has not started executing yet."（[S12]，已核对）
- 执行前才检查撤销标记。（[S8]，已核对）
- 任务超时（`timeout`）是另一套机制，不能当作取消用：
  - process worker 用 `SIGALRM`；
  - thread worker 不支持硬超时，只能在任务里自己检查。（[S12]，已核对）
  - 推论：`SIGALRM` 会在任务执行到任意位置时抛出 `TaskTimeout`，它不知道哪一步在写导航层。（未核对）

**APScheduler 3.x**

- `remove_job` 只是"preventing it from being run any more"。
- `pause_job` 只是把下次触发时间清空。
- 都不会停止已经在跑的函数，执行器也没有中止运行中任务的接口。（[S17]，已核对）

**APScheduler 4.0.0a6**

- 同步任务经 thread executor 放进 `anyio.to_thread.run_sync` 执行，线程不能被强行停止。（[S27]，已核对）
- 异步任务可以在 `await` 处被取消。（Codex 报告 §4，未核对）

**persist-queue、litequeue**

- 没有执行层。`ack`/`nack`、`done`/`retry` 只改数据库里的状态。（[S28][S31]，已核对）
- 取消要由自己的 worker 全部实现。

**DBOS**

- `cancel_workflow()` 直接把状态写成 `CANCELLED`，不会等外部工具退出。（[S37]，已核对）
- 同步步骤不支持 `preemptible=True` 和 `timeout_seconds`，源码里直接报错 "Preemption is only supported for async steps"。（[S38]，已核对）
- 平台不能把库的 `CANCELLED` 直接显示成"已取消"，因为此时工具可能还在写文件。

## 7. 结论和建议

### 7.1 推荐：自己写

继续按 ADR 0005 自己写"一张作业表 + 一个单实例 worker"。

理由：

- 第 3 节的对照表里，除 DBOS 的 R5 外全是"补"或"✗"。库能省下的只是入队、领取、确认这几条 SQL，加上 consumer 循环和周期触发。
- 平台真正的工作量在这些库的职责之外，用了库照样要写：
  - 六种状态和四种结果；
  - 按类型的中断恢复和导航层恢复屏障；
  - 停止外部工具；
  - 类型名额和 GPU 名额的联合准入；
  - 进度、心跳、永久记录。
- 用库还要多处理库自己的状态和恢复行为。第 4 节的"自动重投"和"自动接着跑"，都要专门关掉或绕开。

（依据第 3–5 节，已核对的事实加上 Codex 的工程判断）

### 7.2 如果用库，还要自己补什么

| 库 | 能省下的 | 仍要自己写的 |
|---|---|---|
| huey | consumer 循环、全局并发、重试、周期触发 | 永久作业记录、六种状态、崩溃识别和三种恢复、取消、按类型和 GPU 准入、进度、心跳、实例锁 |
| APScheduler 3.x | 日历触发、执行器包装 | 几乎整个作业系统，而且 Web 不能直接往作业存储里提交 |
| APScheduler 4.0.0a6 | 作业模型、租约、按 task 限流、调度 | 平台作业记录、恢复方式、取消、GPU、进度、心跳；跨进程通知要另写一个不依赖外部服务的事件代理；而且是预发布 |
| persist-queue | 持久投递、`unack` 状态、确认和重投 | 整个 worker、业务状态、调度、取消、恢复分类、进度、心跳、永久记录 |
| litequeue | 领取事务、`LOCKED` 标记、`claim_id` 校验 | 上面的大部分，还要先解决不能同库的冲突 |
| DBOS | 持久工作流、步骤结果复用、按 queue 限流、定时 | 业务六态、取消时停止工具、按类型的恢复方式、导航层恢复屏障、GPU、进度、心跳、作业记录映射 |

出处：Codex 报告 §6.2，Claude 按第 3–5 节核对过的事实复看。APScheduler 4.0.0a6 一行里"另写事件代理"是 Claude 补的。

### 7.3 用库相对自己写的新增风险

1. **两份状态事实来源**。
   - "库已领取""函数已返回""平台已完成""工具已退出"不是一回事。
   - 平台作业表和库的队列表并存，就要处理两者之间的每个窗口。例如库已经自动重投，而平台判定这类作业必须保持中断。
   - DBOS 的事务内入队只解决了提交那一个窗口。（Codex 报告 §6.3，推论，未核对）
2. **pickle 序列化**。huey、APScheduler 3.x 和 4.0、persist-queue、DBOS 默认都用 pickle：
   - 作业参数和 Python 对象、代码版本绑在一起；
   - 也不适合当永久记录。（[S8][S18][S26][S29][S40]，已核对）
   - litequeue 只收字符串。（[S30]，已核对）
3. **表结构归属**：
   - huey 能关掉自动建表；
   - APScheduler 3.x 和 persist-queue 启动时自动建表；
   - litequeue 直接拒绝同库；
   - DBOS 用自己的 `dbos_migrations` 管版本。
   - 结论："都用 SQLite"不等于"表结构都归 Alembic 管"。（[S13][S18][S29][S30][S40]，已核对）
4. **同库写锁竞争**：
   - WAL 下同一时刻只有一个写事务。库的领取、确认、租约、检查点写入，要和进度、心跳、业务写入抢写锁。
   - huey 的写事务用 `begin exclusive`。（[S13]，已核对）
   - 实际竞争有多严重，要实测。（未核对）
5. **升级会改变停止和恢复语义**。本次就有实例：
   - litequeue 0.9 以后的版本改成单表独占；
   - huey 到 3.4.0 才加入 `--graceful-signal` 和 `--shutdown-timeout`；
   - APScheduler 两代存储模型不同；
   - DBOS 按应用版本匹配恢复。
   - 引入库以后，每次升级都要重新审一遍这些行为。（[S14][S20][S30][S36]，已核对）

### 7.4 自己写的最小部件

以下是设计建议，不是核对过的事实（出处：Codex 报告 §6.4，Claude 审阅后保留）。

| 部件 | 职责 | 用什么 |
|---|---|---|
| 作业模型和迁移 | 参数、提交人快照、六种状态、取消请求、结果、进度、计数、诊断、摘要、重新提交来源、执行尝试 | 已批准的 SQLAlchemy 2、Alembic；`enum`、`dataclasses`、`json` |
| 状态转换接口 | 校验转换；领取、取消、结束都用条件 `UPDATE`，处理领取与取消的竞争 | SQLAlchemy 事务 |
| 单实例入口 | 启动先拿锁；运维命令复用同一把锁 | `fcntl.flock` |
| 调度循环 | 每秒查一次；只领取同时有类型名额和 GPU 名额的作业，满额类型不挡别的类型 | `threading`、`time.monotonic` |
| 子进程监督 | 启动工具、设 `CUDA_VISIBLE_DEVICES`、发 `SIGTERM`、约 10 秒后发 `SIGKILL`、确认退出 | `subprocess`、`signal`、`os` |
| 启动恢复 | 持锁后扫描遗留的"运行中""正在取消"，先存中断诊断，再按类型续跑、重跑或标记中断；导航层恢复成功后才放行写操作 | SQLAlchemy；恢复流程由「软链接接口规则」定 |
| 进度写入 | 合并进度，每秒最多写一次，结束时写最终快照；不覆盖取消请求 | `time.monotonic`、SQLAlchemy |
| 心跳 | 与有没有作业无关，定时更新 worker 行 | `datetime`、SQLAlchemy |
| 定时提交 | 到点通过统一的提交函数创建"系统"作业，持久去重，定好错过时刻怎么办 | "每天几点"这类计划用 `datetime`、`zoneinfo`；将来要复杂日历，再按依赖申请评估 APScheduler 3.x |

给 M0 工单的三个提醒（Codex 报告 §6.4，未核对）：

1. **先准入，再派发**。不要先把作业交给线程池，再让线程去等名额。
2. **用条件更新，不做整块覆盖**。领取、取消、结束都用条件更新，避免进度写入抹掉 Web 刚写的取消请求。
3. **先存旧诊断**。续跑和重跑之前，先把上一次尝试的诊断存下来。

### 7.5 对 ADR 0005 的建议

可以在 Considered Options 里补一条，由主会话和负责人决定：

> **现成的 SQLite 任务队列（huey、APScheduler、persist-queue、litequeue、DBOS）**：放弃。
> - 崩溃语义、运行中取消、按类型恢复都不符合要求。
> - 用了它们，作业表、恢复、取消、名额、进度这些代码照样要写。
> - 理由见 `docs/research/作业队列选型.md`。
